Running Bits MFS Middleware with Docker

How to start the whole middleware (15 Spring Boot services, the one-shot seeder, the admin console and the platform) from deploy/docker-compose.yml on one laptop, and how to test it. This is a demo footprint for exploring the features; it is never used for load tests.

1Prerequisites

  • Docker Desktop (or Docker Engine with Compose v2.20+). Give it 8 GB of RAM: the memory limits of the full profile add up to 8,176 of the 8,192 MiB budget (15 JVMs, Kafka, PostgreSQL 18, Keycloak, OpenBao, Valkey, APISIX, etcd, GreenMail, softhsm). Measured use is about 6 GB. 4 CPU cores or more.
  • JDK 25 on the host, to build the jars. You don't need to install Gradle: the repo ships ./gradlew.
  • For the test suites in step 11: Node.js 22+ with npx, and bash, curl, jq.
  • These host ports must be free: 443 (the edge), 8081–8095, 3000, 3001, 5432, 6379, 9094, 8180, 8200, 8025, 3025, 5657 and 5658 (step 7 says how to move one).
docker --version && docker compose version
java -version   # must report 25
node --version  # 22 or newer

2Build the service jars

The images don't compile code. Each services/<module>/Dockerfile copies build/libs/<module>.jar, so build the jars first. Run this from the repository root:

./gradlew clean build

One Gradle build: every module's tests (unit, slice, contract, Testcontainers and conformance, in one JVM per module; the three adapters also run their Camel partner route tests, since Camel is used only there and every other module uses Spring Kafka), every jar, and the repo checks (module isolation, no field injection, contracts lint, the compose memory budget, the shell tests). It worked when the last line is BUILD SUCCESSFUL. The Testcontainers tests need Docker running; without it they are skipped, not failed.

The build cache is on (gradle.properties). After clean, a module whose inputs did not change restores its jar and test results instead of running again. To run everything again:

./gradlew clean build --rerun-tasks   # or --no-build-cache
./gradlew clean build --continue      # list every failure, not just the first
At most 4 modules' tests run at once (mwDockerTests=4, sized for 8 cores: each runs a test JVM, a PostgreSQL and a Kafka). On a smaller host or with Docker short of memory use ./gradlew clean build -PmwDockerTests=2. Build with the stack stopped (docker compose --profile core --profile seed --profile tester stop), or the test containers and the running stack compete for memory.

The two web consoles (ui/mw-admin-ui, ui/mw-test-console) are not Gradle modules: their Dockerfiles build them in step 4. Their unit tests run with pnpm, no stack needed: (cd ui/mw-admin-ui && pnpm install && pnpm test).

3Create the environment file

The .env file holds the dev credentials (database, Valkey, Keycloak admin and test users, client secrets, simulator HMAC secrets, the console session key, the softhsm token PINs, the dev partner SFTP login bits / SFTP_DEV_PASSWORD), the short test timers (including short PIN lockout levels) and the dev-only switches (mw-auth's seed API for the first app PINs, mw-crypto's payShield test API). Compose reads it to fill in the containers' settings. All values are fixed, obviously fake dev values committed in deploy/dev.env.defaults; deploy/.env itself is gitignored.

cd deploy
cp dev.env.defaults .env

Run every docker compose command below from inside deploy/. Compose reads .env there on its own, so no --env-file flag is needed.

The logins a tester types: ops ops-test-pass, app PIN 13579, portal portal-test-pass, Keycloak admin kc-admin-test-pass, OpenBao token dev-root-token (OPENBAO_DEV_ROOT_TOKEN), test-route apikey e2e-test-apikey. Once the stack runs (step 4), the test console pages /tester/credentials (every login with a live one-time code) and /tester/seed-data (everything the seeder created) show them all; in a terminal scripts/creds.sh and scripts/totp.sh (testing guide, section 1).

The volumes are initialised with these values. If you change a credential in .env, reset everything (./reset.sh, step 10) before the next start.

4Start the full platform

docker compose --profile core --profile seed --profile tester up -d --build --wait

One command for everything: the platform (PostgreSQL, Kafka, Valkey, Keycloak, OpenBao, APISIX, SoftHSM, GreenMail), every mw-* service, the admin console, the test console, the seed and the test-only gateway routes. Compose builds the images (mfs-mw/<service>:local, both consoles included), then starts everything in dependency order, and --wait returns only once every container is healthy and the seeder has exited 0 (a non-zero exit: step 12). Each service waits until what it needs is healthy or has finished:

postgres · valkey · openbao · keycloak · softhsm·kafka→kafka-init (topics)· etcd→etcd-init→apisix→apisix-init (routes)· provision (schemas, OpenBao secrets, AppRoles, service certificate CA)→mw-crypto→ mw-auth·the other 13 services + admin console→mw-seeder (one-shot)· apisix-init-tester (test-only routes)→mw-test-console
  • The profiles: core = every service and the admin console, seed = the seeder, tester = the test console plus apisix-init-tester, which turns on the test-only routes (/test/…, /tester). The seeder runs once, after apisix-init has finished and every service is healthy. It goes through the services' own APIs and maker-checker, like an operator would. It is idempotent, so running the same command again is safe (also after a reboot).
  • Without the test console: docker compose --profile core --profile seed up -d --build, then docker compose --profile core --profile seed wait mw-seeder (there nothing else waits for the seeder, so leave out --wait). A later up without --profile tester also removes the test-only routes again.
  • The short test timers (status inquiry, reversal, retry topics, IPN, partner limits) come from .env; the API suite in step 11 needs them. For the production timers, delete the "Test timers" block from .env and run docker compose --profile core up -d.
  • The provision one-shot runs on every up and creates missing database roles, schemas and OpenBao secrets, so a new service's schema appears without wiping the volumes. On the first run it also creates the dev certificate authority for service mTLS (OpenBao pki and pki_int), copies the softhsm token PINs into the secrets of mw-crypto and mw-simulators, and registers the partner simulator's private_key_jwt key in Keycloak.
  • Memory limits are knobs (APP_MEM_LIMIT, APP_XMX, KAFKA_MEM, …; the table is the header of deploy/docker-compose.yml): set one in .env to give a container more room.

On a warm Docker cache the whole command, seeding included, takes about 1–2 minutes. The first run pulls the platform images and builds every local image, so it takes a few minutes more.

Then open the test console at https://localhost/tester (step 11) or the admin console at https://localhost/console. The edge certificate is self-signed for localhost, so accept the browser warning. Sign in as ops-maker01 with ops-test-pass and the one-time code scripts/totp.sh ops-maker01 prints (or copy it from the test console's Logins & secrets page): every ops user has a pre-set code, no authenticator app.

5Check the seed

The start command in step 4 runs the seeder and waits for it. To follow it or check it afterwards:

docker compose --profile core --profile seed --profile tester logs -f mw-seeder
docker compose --profile core --profile seed --profile tester ps -a mw-seeder   # must show: exited (0)

The test suites sign in as the seeded personas, so they need mw-seeder at exited (0). What you get:

  • At start-up: mw-core-mock creates 1,000 customer wallets 01711000001…, 50 agents 01811000001…, 20 merchants 01911000001… and 2 orgs 01311000001…. The core holds no PIN: mw-auth keeps the PINs and builds its own copy of the wallet list from the core's wallet events. Keycloak imports its realms (ops, portals, services, partners) with test users. App users don't log in at Keycloak; they log in at mw-auth.
  • From mw-seeder: the personas seed-ops-maker, seed-ops-checker, seed-ops-viewer, seed-ops-compliance, seed-org-maker, seed-org-checker, seed-customer01/02, seed-agent01, seed-merchant01 with their wallets (01712000001…), the ocs partner baseline (enabled, call timeout) through maker-checker, the USSD main menu and the P2P SMS template. Its seed-app-pins step gives every seeded customer, agent and merchant wallet the app PIN 13579. It encrypts the PIN the way an app does and sets it through mw-auth's dev-only seed API.
  • From mw-admin-api (dev profile): the three dev partners ocs (top-up), billagg (bill pay) and c2wbank (add money). Each one is a partner route (Camel YAML DSL on the shipped mw-* Kamelets, ADR D28) at version 0 ("seed"), identical to the one its adapter loads at start-up.

6Verify it is running

# every container should show "healthy" (init jobs and the seeder show "exited (0)")
docker compose --profile core --profile seed --profile tester ps -a
# readiness of one service
curl -s localhost:8081/actuator/health/readiness
# readiness of 8081-8093 (mw-crypto 8094 and mw-auth 8095 are mTLS-only; their readiness is on the in-container port 8081, which the compose healthcheck reads)
for p in $(seq 8081 8093); do printf "%s " $p; curl -s localhost:$p/actuator/health/readiness; echo; done
docker compose --profile core ps mw-crypto mw-auth softhsm   # all three: healthy
# mw-auth's public keys through the edge (the app login path)
curl -sk https://localhost/auth/v1/.well-known/jwks.json
# the edge and the two consoles
curl -sk https://localhost/healthz
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/console/api/health
# memory and CPU per container, one service's JSON log
docker stats --no-stream
docker compose logs -f mw-orchestrator

7Services and ports

Every service listens on 8080 inside the Compose network and publishes a port on 127.0.0.1 for poking at it directly. Those direct ports skip the edge policies (JWT, HMAC, quotas, the error envelope): clients, the consoles and the test suites go through APISIX on https://localhost. To move a port that is already taken, set MW_PORT_<NAME> in .env (for example MW_PORT_POSTGRES=15432, MW_HTTPS_PORT=8443).

Security modules in the dev stack

  • softhsm: SoftHSMv2 standing in for the HSM. It serves two PKCS#11 tokens over p11-kit RPC: mw-crypto on 5657 and paysim (the payShield simulator's LMK) on 5658. The token files never leave its container (deploy/softhsm/README.md).
  • mw-crypto: the only process that talks to an HSM. Callers reach it over mTLS and may use only the key purposes their caller policy allows. In dev it creates any missing key at start; in production, keys come only from the dual-control key ceremony. Operators see the keys, rotations and the ceremony in the console under Keys.
  • mw-auth: the app login path. It handles the OTP, device binding, login and RS256 tokens (APISIX checks them against mw-auth's JWKS), PIN set, change and reset, lockout levels (short in dev) and the ES256 transaction assertion the core trusts. A PIN only ever arrives as RSA-OAEP ciphertext under the PIN transport key (GET /auth/v1/pin-key).
  • mTLS: at start, mw-crypto, mw-auth and their callers each issue their own certificate from OpenBao pki_int. That is why port 8094 and mw-auth's internal API refuse a plain curl.
  • The design decisions: docs/adr/ D20 (PIN custody) to D24 (service mTLS).

8Alternative: the minimal profile

To start only the P2P and cash path on less RAM: the 10 services marked "minimal" above (mw-crypto and mw-auth included, because every P2P needs mw-auth's assertion) and softhsm:

docker compose --profile minimal up -d --build

The minimal profile starts unseeded, because the seeder also seeds services that minimal doesn't run. The built-in wallets and Keycloak users are there. For a seeded stack, use the step 4 command.

10Stop and reset

# stop the containers, keep the data
docker compose --profile core --profile seed --profile tester stop
# remove the containers, keep the volumes
docker compose --profile core --profile seed --profile tester down
# wipe ALL state together (every volume of every profile), then start again and re-seed
./reset.sh
docker compose --profile core --profile seed --profile tester up -d --build --wait
Never reset a single store. PostgreSQL, Kafka, Valkey, OpenBao, Keycloak and the core-mock ledger describe the same state, so they are always reset together with ./reset.sh.

Test console (every feature by hand, dev/test only)

The start command in step 4 already runs it at https://localhost/tester, with the test-only routes on. scripts/tester.sh adds it to a stack started without --profile tester.

scripts/tester-e2e.sh             # its Playwright suite (scripts/tester-e2e.sh @auth: wallet authentication and the account tools only)

The test console plays the mobile app, a USSD handset, the partner simulators and core faults, the checkout shop, the org portal and wallet authentication (its Auth page: OTP, binding, login, PIN change, lockout and reset on fresh wallets); each action shows every API call, the balances before and after and the SMS, and each txnId links to its Transactions explorer (timeline, partner calls, audit trail). Logins & secrets gives every password with a live one-time code, the PINs and an OTP lookup; Seed data lists the seeded users, wallets (real-looking names, live balances), organisations and partners, with tools to unlock a user or wallet, reset a password, a one-time code or a PIN, unbind a device and set a balance. It shows the dev secrets, so it runs only on this laptop stack. The walkthrough of every feature is docs/testing-guide.html; a demo script per milestone is docs/demo.md.

Partner routes

Partners are routes as config (ADR D28): a Camel YAML DSL route on the shipped mw-* Kamelets, onboarded and changed through maker-checker on the console's Partners page. It goes live only after its dry-run against mw-simulators passes. Examples to start from are in deploy/partner-routes/examples/ (REST with an API key, OAuth2 or an async callback, SOAP, an SFTP reconciliation file, an SFTP payment file). The steps, with the OpenBao secrets, are in docs/runbook.md ("Onboard a biller", "Batch partner over SFTP"). The console's partner checks run with scripts/ui-e2e.sh @partners.

No load tests on a laptop: scripts/suite.sh perf and scripts/chaos.sh need a bigger host and a fresh stack.

12Troubleshooting

  • COPY build/libs/…jar fails: you skipped step 2. Run ./gradlew clean build (or ./gradlew bootJar) from the repo root.
  • A fix doesn't show up in the running stack: the images copy the jar, and --build doesn't rebuild it. Run ./gradlew bootJar first, then step 9.
  • The build passes but the *IT tests were skipped: Gradle could not reach Docker. Start Docker and run ./gradlew clean build --rerun-tasks.
  • A timing test failed once: run that class alone (./gradlew :mw-x:test --tests '*TheClassIT'). If it keeps failing on a small host, lower the test concurrency with -PmwDockerTests=2.
  • required variable … is missing a value: cp dev.env.defaults .env: you skipped step 3.
  • "port is already allocated": another process holds one of the ports in step 7 (lsof -i :5432). Stop it, or move the port with MW_PORT_<NAME> in .env. Port 443 moves with MW_HTTPS_PORT (the APIs work, the console login needs 443).
  • Containers exit with code 137: Docker is out of memory. Give Docker Desktop 8 GB, or use the minimal profile.
  • A one-shot (provision, kafka-init, etcd-init, apisix-init, apisix-init-tester) exits non-zero: docker compose logs provision names the service and step. Usually volumes created with other credentials (an .env from before dev.env.defaults, or an edited value): run ./reset.sh and start again.
  • A service stays "starting": docker compose logs <service>. It is usually waiting on postgres, kafka, keycloak, openbao or provision.
  • mw-crypto or mw-auth stays "starting": mw-auth waits for mw-crypto, and mw-app-gateway, mw-ussd, mw-checkout and the seeder wait for mw-auth. Check docker compose --profile core ps softhsm (must be healthy) and docker compose --profile core logs mw-crypto. A certificate error from pki_int, or a token login error, means volumes from an older start: run ./reset.sh and start again.
  • softhsm or mw-crypto fails after you edited a SOFTHSM_* PIN in .env: the token was created with the old PIN on the softhsm-tokens volume. Run ./reset.sh.
  • An app login fails with a lock after wrong PINs: that is mw-auth's lockout. In dev, levels 1 and 2 last a short time (MW_AUTH_LOCK_* in .env); level 3 needs a PIN reset (test console Auth page), an unlock in the console under Wallets, or Unlock on the wallet's row of the test console's Seed data page.
  • The seeder exits non-zero: docker compose --profile core --profile seed --profile tester logs mw-seeder; the line seed.step.failed names the step. open change request of <operator> means a pending request on a partner, menu or template: approve or reject it in the console, then run step 4 again.
  • A partner route stays waiting for its dry-run or turns REJECTED: the partner page lists the problems (for example HTTP_5XX from the simulator); the adapter's log has the rest (docker compose --profile core logs mw-adapter-billpay). The last LIVE version keeps serving.
  • An SFTP batch route stops logging in after partner-sftp was recreated: the container made new host keys. Write the known_hosts lines into the partner's OpenBao secret again (docs/runbook.md, "Batch partner over SFTP").
  • 404 on /test/... or /tester: the stack was started without --profile tester. Run the step 4 command again (or scripts/tester.sh); scripts/api-test.sh adds the test-only routes by itself.
  • up --wait exits non-zero: docker compose --profile core --profile seed --profile tester ps -a shows the container that failed (a one-shot not at exited (0), or a service not healthy); its logs tell why (the seeder: next item).
  • Timer scenarios of the API suite fail: .env lacks the "Test timers" block. Copy it back from deploy/dev.env.defaults and run the step 4 command again.
  • docker compose logs shows nothing for a service: services in a profile are listed only when you pass it: docker compose --profile core logs <service>.
