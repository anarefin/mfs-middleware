Running Bits MFS Middleware with Docker

How to build, start, seed and test the whole middleware (14 Spring Boot services, the admin console and the platform) from deploy/docker-compose.yml on one laptop, for exploring and demoing the features. This is a demo footprint; it is never used for load tests.

1Prerequisites

  • Docker Desktop (or Docker Engine with Compose v2.20+). Give it 8 GB of RAM: the memory limits of the full profile add up to 7.9 GB (14 JVMs at 160 MB heap, Kafka, PostgreSQL 18, Keycloak, OpenBao, Valkey, APISIX, etcd, GreenMail). Measured use is about 6 GB.
  • 4 CPU cores or more. Each container is capped at 1 CPU (Keycloak at 2), so the stack never takes the whole laptop.
  • JDK 25 on the host, to build the jars. You don't need to install Gradle: the repo ships ./gradlew.
  • Node.js 22+ with npx, for the API suite in step 10. bash, curl, jq.
  • Host port 443 must be free. It is the only published port: APISIX, the edge. Every other container is reachable only inside the Compose networks.
docker --version && docker compose version
java -version   # must report 25
node --version  # 22 or newer
lsof -i :443    # must print nothing

2Build: choose an option

The images don't compile code. Each services/<module>/Dockerfile copies build/libs/<module>.jar (a fixed name, so a stale jar is never picked up), so the jars must exist before step 4. Every build is one Gradle build, run from the repository root with the bundled ./gradlew. Pick the row that matches what you want; each one is explained step by step below.

2.1 Before the first build

  1. Start Docker. Each module's tests include Testcontainers classes (*IT and the conformance suite): every module's test JVM starts its own PostgreSQL and Kafka and removes them when it ends. Without Docker those classes are skipped, not failed, so the build still says BUILD SUCCESSFUL but it is not a gate run.
  2. Prefer the stack stopped (docker compose --profile core --profile seed stop from deploy/): the test containers need Docker's memory and CPU. The build works with the stack up, just slower.
  3. Open a shell in the repo root and check Java: java -version must report 25.
docker info --format '{{.NCPU}} CPUs, {{.MemTotal}} bytes'   # Docker is up
java -version                                              # 25

The first build downloads Gradle and every dependency (a few minutes, once). Later builds use the local caches.

2.2 The everyday gate: ./gradlew clean build

  1. Run it: 
    ./gradlew clean build
  2. Gradle compiles every module (8 tasks at a time), then runs each module's one test task: unit, slice, contract, Camel route, Testcontainers and conformance tests in one JVM, at most 4 modules' tests at a time (sized for an 8-core host). It builds each jar and runs the repo checks: module isolation, no field injection, contracts lint, the compose memory budget and the shell tests.
  3. It worked when the last line is BUILD SUCCESSFUL. The jars are at services/<module>/build/libs/<module>.jar; each module's test report is services/<module>/build/reports/tests/test/index.html.
  4. Run it again with nothing changed and it takes seconds: the build cache restores every module whose sources (and the contract files its tests read) did not change, even after clean. Change one module and only that module, plus the checks that read its files, runs again.
The everyday gate leaves out the slow-wait tests (2.3). Use it before every pull request; a milestone needs 2.3.

2.3 The milestone gate: -PwithSlow

About 140 tests spend most of their time waiting on purpose to prove an outcome: that nothing arrives within a window, that a timeout or a retry delay runs out, that a deadline moves a transaction on. They are tagged slow-wait and the everyday gate skips them (ADR D19). A milestone gate runs everything:

  1. ./gradlew clean build -PwithSlow
  2. Same as 2.2, plus the slow-wait tests: 4,465 tests in all, about 5 minutes.
  3. Then the API suite on a fresh stack: ./reset.sh, step 4 with test-timers.env, and scripts/api-test.sh (step 10).

-PwithSlow works with any test command, for example ./gradlew :mw-orchestrator:test -PwithSlow.

2.4 Jars only: ./gradlew bootJar

For starting the stack without waiting for the tests (a demo, or after someone else ran the gate):

  1. ./gradlew bootJar
  2. Every module's jar lands in services/<module>/build/libs/, with no tests run. Seconds on a warm Gradle, under a minute cold.
  3. Go on with step 3; step 4's --build turns the jars into images.

2.5 One module

While you work on one service, build and test only that module (:mw-<name>:, any folder in services/):

./gradlew :mw-notify:build                          # its tests, then its jar
./gradlew :mw-notify:test                           # its tests only
./gradlew :mw-notify:test --tests '*SmscFlowIT'     # one class; a method: '*SmscFlowIT.aThrottled*'
./gradlew :mw-notify:bootJar                        # its jar only, no tests
./gradlew :mw-notify:test --rerun-tasks             # again, even though nothing changed

Then put the new jar into the running stack with step 9.

2.6 Force a cold run, measure it, see every failure

  1. Gradle skips work whose inputs did not change. To run everything again (to measure, or to rule out the cache): 
    ./gradlew clean build --rerun-tasks                 # run every task again
./gradlew clean build --no-build-cache              # or: do not restore from the build cache
  2. To see where the time goes, add --profile and open the newest report in build/reports/profile/.
  3. By default Gradle stops scheduling new work after the first failure. To see every failure in one run: 
    ./gradlew clean build --continue

2.7 Tests and repo checks without jars

./gradlew check                 # every module's tests plus the repo checks, no jars
./gradlew :checkIsolation       # modules depend on no other module, no shared build logic
./gradlew :checkFieldInjection  # no @Autowired fields
./gradlew :contractsLint        # contracts/, every contracts.yml, API suite traceability
./gradlew :composeCheck         # memory limits of the core profile add up to 8 GB or less
./gradlew :scriptTests          # the shell tests of scripts/, the repo layout and these docs

The shell tests can also run straight from the shell: scripts/test/run.sh (every file) or scripts/test/run.sh scripts/test/test_repo_docs.sh (one file). They run three files side by side; SCRIPT_TESTS_JOBS=1 scripts/test/run.sh runs them one at a time.

2.8 Tune the build for your machine

  • Test concurrency: at most 4 modules' tests run at once (mwDockerTests=4 in gradle.properties), sized for 8 cores: each one runs a test JVM, a PostgreSQL and a Kafka. On a bigger host try more while watching docker stats; on a smaller one, fewer: 
    ./gradlew clean build -PmwDockerTests=6     # 12+ cores
./gradlew clean build -PmwDockerTests=2     # 4 cores, or Docker short of memory
  • Compile and jar concurrency: org.gradle.workers.max=8 in gradle.properties.
  • More than 4 test modules at once on 8 cores makes timing-sensitive tests flaky; lower the number before suspecting a test.

2.9 The images

Step 4's up --build builds every image it needs from the jars, so you rarely build images on their own. To do it anyway, from deploy/:

docker compose --env-file .env --profile core build                       # every core image
docker compose --env-file .env --profile core build mw-notify             # one image
docker compose --env-file .env --profile core build --no-cache mw-notify  # from scratch
docker compose --env-file .env --profile tester build mw-test-console     # the test console

Images are tagged mfs-mw/<service>:local. The two web consoles (mw-admin-ui, mw-test-console) are not Gradle modules: their Dockerfiles build them. Their unit tests run with pnpm, no stack needed:

(cd ui/mw-admin-ui && pnpm install && pnpm test)
(cd ui/mw-test-console && pnpm install && pnpm test)

3Create the environment file

deploy/.env holds every dev credential: database, Valkey, Keycloak admin and test-user passwords, client secrets, simulator HMAC secrets and the console session key. It is never committed, and every docker compose command below reads it. The logins a tester types are fixed, documented values (ops ops-test-pass, app app-test-pass, portal portal-test-pass, Keycloak admin kc-admin-test-pass, apikey e2e-test-apikey: testing guide, section 1); every other value is random.

cd deploy
../scripts/gen-dev-env.sh

Run every docker compose command below from inside deploy/. Running the script again keeps existing values and only adds missing ones.

Never delete .env on its own: PostgreSQL and Keycloak keep the old passwords in their volumes and the stack will not come up. To rotate everything: ./reset.sh, delete .env, then step 3 again.

4Start the full platform

docker compose --env-file .env --env-file test-timers.env \
  --profile core --profile seed up -d --build

Compose builds the images (mfs-mw/<service>:local), then starts everything in dependency order. Each service waits until what it needs is healthy or has finished:

postgres · valkey · openbao · keycloak·kafka→kafka-init (topics)· etcd→etcd-init→apisix→apisix-init (routes)· provision (every service’s schema, OpenBao secret, AppRole)→14 services + admin console→ mw-seeder (one-shot)
  • Always pass --profile seed with --profile core. The seeder runs once, after apisix-init has finished and every service is healthy. It goes through the services' own APIs and maker-checker, like an operator would. It is idempotent, so running the same command again is safe.
  • --env-file test-timers.env loads the short test timers (status inquiry, reversal, retry topics, IPN, bulk), which the API suite in step 10 needs. Leave it out for the production timers.
  • The provision one-shot runs on every up and creates missing database roles, schemas and OpenBao secrets, so a new service's schema appears without wiping the volumes.
  • Memory limits are knobs (APP_MEM_LIMIT, APP_MEM_LIMIT_LARGE, APP_XMX, KAFKA_MEM, ...; the table is the header of docker-compose.yml): set one in the shell or in .env to give a container more room.

On a warm Docker cache the whole command, seeding included, takes about 1–2 minutes (step 13). The first run pulls the platform images and builds 16 images (14 services, the one provision image and the console), so it takes a few minutes more.

5Wait for the seed to finish

The start command in step 4 already runs the seeder. Follow it until it exits:

docker compose --profile core --profile seed logs -f mw-seeder
docker compose --profile core --profile seed ps -a mw-seeder   # must show: exited (0)

The seeder commands need both profiles (it depends on the core services); the other services work without them.

What you get:

  • At start-up (no seeder needed): mw-core-mock creates 1,000 customer wallets 01711000001…, 50 agents 01811000001…, 20 merchants 01911000001…, 2 orgs 01311000001…, all with the fake PIN 1234. Keycloak imports its realms (ops, customers, portals) with test users. The simulators, USSD menus, templates and partner configs load their dev data.
  • From mw-seeder: the personas seed-ops-maker, seed-ops-checker, seed-ops-viewer, seed-ops-compliance, seed-org-maker, seed-org-checker, seed-customer01/02, seed-agent01, seed-merchant01 with their wallets (01712000001…), the OCS partner at its baseline, and a first version of the USSD main menu and the P2P received SMS.
The test suites in step 10 sign in as the seeded personas; they need mw-seeder at exited (0).

6Verify it is running

# every container should show "healthy" (init jobs and the seeder show "exited (0)")
docker compose --profile core --profile seed ps -a
# the edge (the only published port)
curl -sk https://localhost/healthz
# readiness of one service (services publish no host port: ask from inside its container)
docker compose exec -T mw-orchestrator bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080; printf "GET /actuator/health/readiness HTTP/1.0\r\n\r\n" >&3; tail -1 <&3'
# memory and CPU per container
docker stats --no-stream
# follow one service's JSON log
docker compose logs -f mw-orchestrator

Then open the admin console at https://localhost/console. The edge certificate is self-signed for localhost, so accept the browser warning. Sign in as ops-maker01 with the password KC_OPS_TEST_PASSWORD from .env (grep KC_OPS_TEST_PASSWORD .env); the first sign-in asks you to enrol TOTP with an authenticator app.

8Alternative: the minimal profile

To start only the P2P and cash path (the 8 services marked "minimal" above) on less RAM:

docker compose --env-file .env --env-file test-timers.env --profile minimal up -d --build

The minimal profile starts unseeded, because the seeder also seeds services that minimal doesn't run. The built-in wallets and Keycloak users are there. For a seeded stack, use the step 4 command.

9Rebuild one service after a code change

Build the module (step 2.5), then replace its container. From deploy/:

(cd .. && ./gradlew :mw-notify:build)   # its tests and jar; :mw-notify:bootJar for the jar only
docker compose --env-file .env --env-file test-timers.env --profile core up -d --build mw-notify
docker compose restart apisix   # APISIX still points at the old container's IP

11Stop and reset

# stop the containers, keep the data
docker compose --profile core --profile seed stop
# remove the containers, keep the volumes
docker compose --profile core --profile seed down
# wipe ALL state together (every volume), then start again and re-seed
./reset.sh
docker compose --env-file .env --env-file test-timers.env --profile core --profile seed up -d --build
Never reset a single store. PostgreSQL, Kafka, Valkey, OpenBao, Keycloak and the core-mock ledger describe the same state, so they are always reset together with ./reset.sh (every profile, every volume).

12Troubleshooting

  • COPY build/libs/<module>.jar fails: you skipped step 2. Run ./gradlew clean build (or ./gradlew bootJar for the jars alone) from the repo root.
  • The build passes but the Testcontainers tests were skipped (the test report shows the *IT classes as skipped): Gradle could not reach Docker. Start Docker and run ./gradlew clean build --rerun-tasks.
  • A timing test failed once (an assertion about a reply, timeout or budget): run that class on its own, ./gradlew :mw-x:test --tests '*TheClassIT'. If it passes, run the gate again; if it keeps failing on a small host, lower the test concurrency with -PmwDockerTests=2 (step 2.8).
  • The build is much slower than step 13 says: the stack is probably still running and competing for Docker (docker stats). Stop it, or lower -PmwDockerTests. --profile shows which task takes the time.
  • required variable … is missing a value: run scripts/gen-dev-env.sh: you skipped step 3.
  • "port is already allocated" on 443: another process holds it (lsof -i :443). Stop it, or start with MW_HTTPS_PORT=8443 in front of the command (the APIs work, the console login needs 443).
  • Containers exit with code 137: Docker is out of memory. Give Docker Desktop 8 GB, or use the minimal profile.
  • A one-shot (provision, kafka-init, etcd-init, apisix-init) exits non-zero: docker compose logs provision (it names the service and step), or that one-shot. Usually volumes created with other credentials (a deleted .env, see step 3) or OpenBao not yet unsealed; docker compose down and start again.
  • A service stays "starting": docker compose logs <service>. It is usually waiting on postgres, kafka, keycloak, openbao or provision.
  • The seeder exits non-zero: docker compose --profile core --profile seed logs mw-seeder; the line seed.step.failed names the step. open change request of <operator> means someone left a pending request on a partner, menu or template: approve or reject it in the console, then run step 4 again.
  • 404 on /test/... routes: expected after a start; scripts/api-test.sh and scripts/tester.sh add the test-only routes.
  • scripts/smoke.sh reports a partition mismatch after upgrading from a stack started with 3 partitions per topic: run ./reset.sh once (Kafka cannot shrink existing topics).

Recovery and operations in depth: docs/runbook.md.
