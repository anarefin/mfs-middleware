mw-simulators and mw-seeder: the outside world, faked

A mobile-money middleware talks to many outsiders: telcos for top-ups, billers, banks, an SMS centre, the USSD gateways of four mobile operators. None of them is on a developer's laptop. mw-simulators plays all of them in one Spring Boot app, and mw-seeder fills the stack with known test data before anyone starts.

In plain English

In plain English

Think of a film set. The street looks real from the camera, but the shops are fronts and the extras do what the director tells them. mw-simulators is that set. The adapters call a "telco" or a "biller" exactly as they would in production, and behind the front is code that answers the way a test asked it to.

The director has two tools. Magic values are inputs that always trigger a known behaviour: a phone number ending in 999 always fails. The control API changes behaviour on the fly: "the bank is down from now on". Every request is also recorded, so a test can check what was sent.

mw-seeder is the stage crew that sets the props before the first take: users, wallets, PINs and partner settings, the same every time.

Why we use it here

ADR M5 starts from the problem: "Real partner APIs and test accounts are not available yet; the adapter framework must still be proven end to end." The decision gives each partner type one generic contract, "with magic values and a control API for scenarios (timeouts, errors, callbacks, replays)."

Spec section 22.2 asks for the same: behaviour chosen "by magic values (e.g. amount ending .13 → timeout, MSISDN suffix 999 → business failure) and by a control API", and simulators that "record every request for assertions and can replay a callback on demand." A real partner can never be told to time out on demand. The simulators can, so every hard path (timeouts, lost callbacks, duplicates) has a test.

The simulators never ship to production. Real partners replace them through adapter configuration, not code changes.

  • Who calls the simulators. The adapters (mw-adapter-telco to the OCS, -billpay to billagg, -bank to c2wbank), mw-notify (SMPP to the SMSC), mw-ussd (bound to the USSD SMPP port), mw-checkout (IPNs) and mw-crypto (payShield).
  • Who controls them. Tests and testers, through the test-only edge route /test/sim/* (deploy/apisix/routes-test/test-simulators.json, test API key from scripts/creds.sh), which reaches only the /sim/... control API, and /test/mock-control/* (deploy/apisix/routes-test/test-mock-control.json) for the mock-control API. On the laptop the direct port 8085 works too.
  • Callback secrets. The bill aggregator and bank sign their callbacks with HMAC-SHA256, using secrets the provision one-shot writes to Vault.
  • One timer knob. How long a simulated timeout holds its reply: MW_SIM_TIMEOUT_DELAY (30 s by default, shorter in deploy/dev.env.defaults).

Partner simulators and magic values

The OCS, bill aggregator and bank share the same mechanics. The magic values:

InputOCS top-upBill aggregatorC2W bank
Normal200, code 0000200, code 000202 PENDING, then a SUCCESS callback
Ends in 999MSISDN: 422 business failurebill number: 422 refused by the billeraccount: FAILED callback
Amount .13Timeout: the operation is applied, the reply is held (the bank sends no callback at all)
Amount .77500 after the operation was applied
Amount .99An unknown error code 9876
Amount .55A malformed body (operation applied)

The bill aggregator also invents bills: the amount due is Tk 100 plus the last three digits of the bill number, a number ending 404 is "not found" and one ending 000 is "already paid". So no bill ever needs to be set up.

Those magic values are the default triggers (FRS MCK-03). Every mock party also runs on one mock-control engine (ADR D33, ticket 102; contract contracts/api/mw-simulators/mock-control.v1.openapi.yaml), which overrides them on demand. It exists only in the Spring profile mock-control (the dev stack sets it); the test route is /test/mock-control/*.

  • GET /mock-control/parties: the parties (ocs, billagg, c2wbank, merchant), their operations and scope keys.
  • POST /mock-control/{party}/scenarios {operation?, behaviour, code?, delayMs?, httpStatus?, key?, nextN?}: SUCCESS, BUSINESS_ERROR, TIMEOUT, DELAY, HTTP_5XX, MALFORMED_RESPONSE, CONNECTION_RESET, PARTIAL_SUCCESS, and the callback behaviours DUPLICATE_CALLBACK, LATE_CALLBACK, OUT_OF_ORDER_CALLBACK, NO_CALLBACK. Scoped to one key (an MSISDN, account, biller, bill number or transaction id), to the next N calls, or global. GET lists, DELETE clears.
  • PUT /mock-control/{party}/switch {state: UP|DOWN|MAINTENANCE|SLOW, latencyMinMs, latencyMaxMs, ratio}: DOWN closes the connection unanswered, MAINTENANCE answers 503 5030, SLOW draws a latency in the range.
  • PUT /mock-control/{party}/settings {callbackUrl, callbackOnly, timeoutDelayMs}: where callbacks go.
  • GET /mock-control/{party}/journal[?path=&contains=&afterSeq=]: what the adapter really sent, raw (Authorization and Cookie headers dropped); DELETE clears it and resets the party (scenarios, switch, settings, ledgers).
  • POST /mock-control/{party}/callbacks/{reference}/replay: send a callback again, to prove the adapter ignores duplicates.

Per call the engine picks, for the outcome, the delay and the callback each, the most specific matching scenario: next-N first, then per key, then per operation, then party-wide; with none, the magic value decides, and with no magic value it is SUCCESS. The old /sim/{partner}/scenario and /sim/{partner}/requests still work for one release as aliases of the engine (one deprecation line in the log).

Every partner simulator also answers a status inquiry (GET /ocs/v1/topup/{transactionId} and the like) with the real outcome. That is what lets the orchestrator settle a timed-out transaction correctly.

The SMS centre

client/SmscServer is an SMPP 3.4 server built on jSMPP. mw-notify binds to it like to a real operator's SMSC, submits each SMS, and gets a delivery report (DLR) back 300 ms later. It decodes GSM-7 (English) and UCS-2 (Bangla) and reassembles long messages. Magic suffixes on the destination number:

Number ends inWhat happens
999 / 998DLR UNDELIV / EXPIRED
997The first two submits are refused as throttled, then accepted
996The submit is refused
995Accepted, but no DLR ever comes
anything elseDELIVRD

GET /sim/smsc/messages?msisdn=01711000001 lists what was sent to a number, with text, encoding, segments and DLR status. The test console's SMS & email page shows the same list next to the email from GreenMail.

The USSD gateway

A USSD session is a conversation: the phone dials its operator's code (*268# on Grameenphone), sees a menu, presses a key, sees the next screen. The simulator plays the operator's gateway in both of the ways real operators connect:

  • HTTP mode (Robi, Banglalink, Teletalk): it POSTs each step to APISIX's /ussd/<mno> route with that operator's basic-auth login, just as the real gateway would.
  • SMPP mode (Grameenphone, gp): mw-ussd holds SMPP binds to port 2776. The simulator sends each key press as a deliver_sm and reads each screen from mw-ussd's submit_sm. /sim/ussdgw/smpp/... can throttle, refuse or drop the binds.

Either way you drive it with one call, POST /sim/ussdgw/sessions {mno, msisdn, serviceCode, inputs[]}, and get every screen back. USSD sessions are deliberately not recorded: their inputs carry PINs.

Two more fakes live here: the merchant IPN receiver (/merchant/ipn/**, plays a shop's server for mw-checkout's webhooks; it can be told to fail the next ones), and the payShield 10K simulator on port 1500, described on the HSM page.

mw-seeder: the stack's starting data

Tests need a known world: personas that can log in, wallets with money, PINs that work. mw-seeder builds it in one pass and then exits. It is a Spring Boot app with no web server, no database and no Kafka. It runs its steps in order, each one idempotent, so a second run changes nothing:

  1. await-platform-ready: wait until APISIX, Keycloak and every mw-* service report ready.
  2. seed-identities: the ops and portal personas in Keycloak, with roles and a pre-set one-time-code secret.
  3. seed-core-accounts: the wallets in mw-core-mock, through its test-only create-if-absent PUT. An existing wallet keeps its balance.
  4. seed-app-pins: the dev app PIN on every seeded customer, agent and merchant wallet. It fetches GET /auth/v1/pin-key, encrypts the PIN with RSA-OAEP exactly as an app would, and calls mw-auth's dev-only POST /internal/v1/seed/pins. The PIN is the fake, documented MW_SEED_APP_PIN=13579 from deploy/dev.env.defaults.
  5. seed-partner-configs: each partner's baseline in mw-admin-api, through the real maker-checker (a seed maker asks, a seed checker approves).
  6. seed-admin-content: a first admin-made version of the USSD menu and some SMS templates.
  7. write-manifest: a JSON list of everything seeded (personas, wallets, partners), with no secrets.

The manifest lands on the seed-manifest volume. scripts/api-test.sh and scripts/ui-e2e.sh copy it to build/seed/manifest.json, and Newman, Playwright and the test console read their users from it. Check the run from deploy/: docker compose --profile core --profile seed ps -a mw-seeder must show exited (0). A failing step stops the run, and later steps never run.

Worked example: a USSD payment from a fake handset

Play customer 01711000001 on Grameenphone, dialing *268# and sending Tk 10 to 01711000002 (as Newman folder 20 does):

  1. Start the session. Body {"mno":"gp","msisdn":"01711000001","serviceCode":"*268#","inputs":["9","1","01711000002","10","1","13579"]}, with the test API key.
  2. gp runs over SMPP, so the simulator sends the dial to mw-ussd on its SMPP bind.
  3. mw-ussd answers with the main menu, in Bangla by default.
  4. The simulator sends one input per screen: 9 switches to English, 1 Send Money, the recipient, the amount, 1 Confirm.
  5. The last input is the PIN.
  6. mw-ussd encrypts the PIN and asks mw-auth for a transaction assertion (see HSM).
  7. It publishes the request with the assertion on Kafka.
  8. The final screen comes back with the end flag.
  9. The simulator returns every screen it saw, so a test can compare them.
  10. The saga completes and mw-notify gets the status event.
  11. mw-notify submits the SMS over SMPP to the SMSC simulator, which sends a DLR back.
  12. The tester reads the SMS. Both customers' balances (Tk 15 less, Tk 10 more) can be checked on mw-core-mock.

  • Users of the control API: tests/api/lib.js (MW.sim) and the test console's page Simulators & faults.

What can go wrong

What can go wrong
  • A scenario from an earlier test is still active. Scenarios last until reset. Reset with DELETE /sim/{partner}/scenario, or "Reset everything" in the test console. A restart of mw-simulators also clears them (and every recorded request).
  • An amount like Tk 50.13 "hangs". That is the timeout magic value, not a bug. Pick amounts with other fractions for happy paths, and keep test phone numbers away from 995-999 endings.
  • USSD over gp shows {status: -1}. No screen came back in time or mw-ussd is not bound. GET /sim/ussdgw/smpp/binds shows the binds; a drop or throttle scenario from another test may still be set.
  • You looked for a USSD session in /sim/.../requests. It is never recorded, because the inputs carry PINs.
  • mw-seeder exited 1. Read its log: each step logs seed.step.completed or why it stopped. Typical causes are a service not yet healthy past the step's time limit, or a pending change request of another operator for the same partner. Run the up again: the steps are idempotent.
  • Logins with the app PIN fail after a reset. deploy/reset.sh destroys the HSM keys and every stored PIN with them. Start with the seed profile again so seed-app-pins sets them anew.
