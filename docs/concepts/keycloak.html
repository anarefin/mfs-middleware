Identity

Keycloak: who is logging in

Staff in the ops console, users of the organisation portal, our own services calling each other, and partner systems all get their tokens from one place: Keycloak. The services never check a password themselves. They only check that a token is genuine and carries the right role. Wallet app users are the one exception, and this page explains why.

In plain English

In plain English

Think of the badge office at a large company. You show your ID once at the office, and they print you a badge with your name, your department and an expiry time. After that, every door just looks at the badge. The doors do not know your password and do not need to. Keycloak is that badge office. It is an identity provider: it checks who you are and hands out a signed token that says so.

The badge here is a JWT (JSON Web Token): a small JSON document with a digital signature. Anyone with Keycloak's public key can check the signature, so a service can trust the token without calling Keycloak on every request.

A few Keycloak words you will see everywhere:

WordMeaningExample here
RealmA separate world of users, roles, clients and login rules. Realms share nothing.ops for staff, services for our own services
ClientAn application that asks Keycloak for tokens.mw-admin-ui (the ops console), mw-app-gateway (a service)
RoleA label on a user that a service turns into permissions.ops-maker may raise a change request, ops-checker may approve it
GrantThe way a client gets a token.Authorization Code + PKCE for a browser; client credentials for a service
Issuer (iss)The claim in a token that says who made it.https://localhost/realms/ops

TOTP"Time-based one-time password": the six-digit code an authenticator app shows, new every 30 s.second factor of every ops and portals login

Why we use it here

The decision record D9 starts from one sentence: "Identity, secrets and resilience are cross-cutting and must not be invented per service." Logins, two-factor codes, lockout after failed attempts, password rules and key rotation are hard to get right. Keycloak is a mature open-source product that does all of it, so no Spring service in this repo stores a staff password.

Later, D21 narrowed its job: "Keycloak keeps ops (TOTP), portals (TOTP added), partners (private_key_jwt instead of shared secrets) and services; every realm gets brute-force detection and a password policy."

Two rules follow from this:

  • Every service checks the token again. APISIX checks staff tokens at the edge, and the service behind it checks the signature, issuer and roles once more (defence in depth). The gateway is the first lock, not the last.
  • Roles are enforced in the service. Keycloak only says "this person has role ops-checker". What that role may do is decided in the Spring Security config of the service.

How it is wired

Keycloak is one container in deploy/docker-compose.yml. It has no profile, so it starts with every stack:

ContainerKindWhat it does
keycloaklong-runningKeycloak 26 in production mode on PostgreSQL (its own keycloak database). Plain HTTP on port 8080 inside the stack, published on 127.0.0.1:8180 (knob MW_PORT_KEYCLOAK). Browsers reach it only through APISIX on 443. Health on management port 9000.
provisionone-shot, profiles minimal and coreWaits for a healthy Keycloak, then registers the certificate of the partner client partner-sim in realm partners (see OpenBao for the rest of its job).

The image is built from deploy/keycloak/Dockerfile. It runs kc.sh build once at image build time, so each start can use start --optimized --import-realm and skip about ten seconds of start-up work. There is no custom plugin and no theme.

Realms as files

Nobody clicks a realm together in the Keycloak admin screen. Each realm is a JSON export in Git:

deploy/keycloak/realms/
  ops-realm.json        staff of the ops console (password + TOTP)
  portals-realm.json    organisation and service-provider portal users (password + TOTP)
  services-realm.json   one client per calling service (client credentials)
  partners-realm.json   partner systems (private_key_jwt)

The folder is mounted read-only into the container, and --import-realm loads each file on start when the realm does not exist yet. Secrets are never in the JSON. The files hold placeholders such as ${KC_MW_ADMIN_API_SECRET} or ${KC_OPS_TEST_TOTP_SECRET}, and Keycloak fills them from environment variables on import. Compose passes those variables from deploy/.env, a copy of the committed fake dev values in deploy/dev.env.defaults.

The fixed settings (database URL, proxy headers, health) are in deploy/env/keycloak.env. KC_PROXY_HEADERS=xforwarded tells Keycloak to trust the X-Forwarded-* headers APISIX sets, and KC_HOSTNAME is left unset on purpose: Keycloak builds its URLs (and the iss claim) from the request. That is why the same realm can issue http://keycloak:8080/realms/ops to a caller inside the stack and https://localhost/realms/ops to a browser.

The four realms

RealmWhoClientsHow they log in
opsBits staff using the ops consolemw-admin-ui (public, PKCE S256); mw-e2e-ops (dev only, for automated tests) Browser flow browser-mfa: password form, then TOTP form (HmacSHA256, 6 digits, 30 s)
portalsUsers of the organisation and service-provider portalsmw-portal Password + TOTP, the same browser-mfa flow
servicesOur own services calling each other's internal APIsmw-portal-api, mw-admin-api, mw-audit-dw, mw-auth, mw-app-gateway, mw-ussd, mw-checkout Client credentials: client id + client secret, no user at all
partnersPartner systemspartner-sim (the simulated partner) private_key_jwt: the partner signs a short JWT with its own private key; there is no shared secret

Roles in ops follow the jobs in the spec: viewer, ops-maker, ops-checker, ops-emergency, integration-maker, integration-checker, recon-maker, recon-checker, compliance-officer, security-admin and auditor. A maker proposes a change and a checker approves it, so no single person can change money on their own. In portals the roles are org-maker, org-checker and sp-viewer. In services every service account has the one role internal-api.

Every realm has the same safety settings: a temporary lockout after 5 failed logins (not a permanent one), passwords of at least 12 characters that differ from the user name and the last five passwords, and access tokens that live 5 minutes. A short token limits the damage if one leaks; the console refreshes it quietly in the background.

Two ways a service checks a Keycloak token

  • A staff token (mw-admin-api, mw-portal-api). Spring's NimbusJwtDecoder fetches the realm's JWKS on the first token and checks signature and expiry. A small RealmIssuerValidator then accepts the token only if iss ends with /realms/ops (or /realms/portals). It compares only the end, because the host part depends on how the client reached Keycloak. Each path then needs certain roles.
  • A service token on an /internal/v1 API (mw-orchestrator, mw-audit-dw, mw-auth, mw-crypto). The token must name the called service in aud (audience), and its azp claim (the client id that asked for it) must be on that service's allow-list. An InternalCallerPolicy class holds these rules. mw-auth and mw-crypto also require mTLS: azp must equal the name in the caller's client certificate, which comes from OpenBao.

Why app users are not in Keycloak

Customers, agents and merchants using the wallet app are not Keycloak users. Until ticket 73 there was a realm customers with a password login, but a wallet has millions of users whose real login factor is their PIN plus a bound phone. Keeping a copy of every wallet user in Keycloak, and teaching Keycloak to check a PIN, would mean a second user database and a custom plugin to maintain. So D21 moved the job to our own service mw-auth:

  • The app logs in at mw-auth with phone number (MSISDN) + PIN on a bound device.
  • mw-auth issues an access token signed with an RS256 key held by mw-crypto (5 minutes), plus a refresh token.
  • mw-auth publishes the public keys at its own JWKS URL. APISIX's app-v1 route and mw-app-gateway check app tokens against that JWKS. mw-app-gateway expects header typ = at+jwt, issuer exactly mw-auth and audience mw-app.

The customers realm and its APISIX token route are gone. The old route id routes/auth-customers-token is listed in deploy/apisix/retired.txt, so APISIX deletes it if an old etcd still has it. So when you see "token" in this repo, ask first: a Keycloak token (staff, portal, service, partner) or an mw-auth token (app user)?

Worked example: an operator lists transactions

An operator opens https://localhost/console, signs in and opens the transactions page. The ops console (mw-admin-ui, a Next.js app using Auth.js) never sees the password; Keycloak does. Here is the whole trip:

  1. The console sends the browser to Keycloak. mw-admin-ui starts the Authorization Code flow with PKCE: the browser is redirected to /realms/ops/... with a one-time challenge. PKCE ("proof key for code exchange") means a stolen code is useless without the secret the console kept back.
  2. APISIX passes the login pages through. The route auth-ops-browser forwards /realms/ops/* to Keycloak and sets X-Forwarded-Host, -Proto and -Port to the public host on 443. The client's own Host header is never trusted, so nobody can trick Keycloak into building links to another site.
  3. Two factors. The browser-mfa flow asks for the password, then the TOTP code. Five wrong tries lock the user for a while.
  4. Code for tokens. Keycloak redirects back with a code. mw-admin-ui swaps it for tokens on the server side, inside the stack. The tokens stay in an encrypted, HTTP-only cookie; the browser's JavaScript never sees them. The token's issuer is https://localhost/realms/ops, because that is the host Keycloak was told by APISIX.
  5. The API call. mw-admin-ui calls GET /admin/v1/transactions through APISIX with the token. The route admin-v1 runs openid-connect in bearer-only mode against the ops realm's keys. It accepts two issuers, the internal http://keycloak:8080/realms/ops and the public https://localhost/realms/ops.
  6. The service checks again. mw-admin-api decodes the token with the realm's JWKS, runs RealmIssuerValidator, then its SecurityConfig asks: does this operator have a role that may read transactions?
  7. A service token for the next hop. mw-admin-api needs data from mw-orchestrator's internal API. It cannot forward the operator's token there; it gets its own token from realm services with the client-credentials grant (client mw-admin-api, secret from OpenBao). That token's audience includes mw-orchestrator.
  8. The orchestrator checks the caller. mw-orchestrator checks the realm services signature and issuer, that aud contains mw-orchestrator, and that azp is one of mw-portal-api, mw-admin-api, mw-app-gateway. Then it answers.
Where it lives
  • deploy/keycloak/realms/ops-realm.json, portals-realm.json, services-realm.json, partners-realm.json: the four realms.
  • deploy/keycloak/Dockerfile (the pre-built image) and deploy/env/keycloak.env (database, proxy and health settings).
  • Edge routes: routes/auth-ops-browser.json, routes/admin-v1.json, lua/ops-token-grant.lua.
  • Staff token checks: mw-admin-api config/SecurityConfig.java, security/RealmIssuerValidator.java; the same pattern in mw-portal-api.
  • Service token checks: mw-orchestrator security/InternalCallerPolicy.java, mw-auth (with the mTLS rule).
  • The console's login: ui/mw-admin-ui/src/auth.ts.
  • The partner certificate upload: deploy/provision/lib.sh (partner_sim_client_key).

What can go wrong

What can go wrong
  • You edited a realm file and nothing changed. Realms are imported only when they are missing. Keycloak keeps an imported realm in PostgreSQL, so an edit needs deploy/reset.sh (which wipes every volume) and a fresh start.
  • You changed a KC_* value in deploy/.env and the stack will not come up. Same cause: the old realm in the old volume still holds the old value. Run deploy/reset.sh.
  • A password grant to https://localhost/realms/ops/.../token answers 403. On purpose. lua/ops-token-grant.lua lets only authorization_code and refresh_token through the public route, so nobody can guess staff passwords against the token endpoint. Automated tests use the dev-only client mw-e2e-ops on a test-only route.
  • 401 from mw-admin-api with a token that looks fine. Look at iss. A token from another realm (say portals) has a valid signature shape but fails the realm check. An expired one fails too: access tokens live only 5 minutes.
  • The console login breaks on another port. auth-ops-browser pins the forwarded port to 443, so a stack on another HTTPS port gets broken redirect links.
  • An operator lost their authenticator app. On the dev stack every test user has a pre-set TOTP secret, so scripts/totp.sh prints the current code. On a real host the TOTP credential is reset with kcadm.sh; the steps are in docs/runbook.md ("An operator lost their TOTP device").
  • "Which password do I type?" Never guess and never copy one into code. scripts/creds.sh prints every dev login, and the test console's Logins & secrets page shows them with live codes.
