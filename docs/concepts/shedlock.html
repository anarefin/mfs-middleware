ShedLock: one run of a scheduled job at a time

Spring's @Scheduled runs a method on a timer in every copy of a service. ShedLock adds a lock row in the service's own database, so only one copy runs the job at a time. Today every service runs as one instance, but the lock is already there for the day a second one is added.

In plain English

In plain English

Think of the one key to a shared meeting room, hanging on a hook. Whoever wants the room takes the key; if the hook is empty, you don't wait, you just come back next time. And if someone walks off with the key, there is a rule: after a set time the key counts as returned anyway. ShedLock is that hook and that rule, kept as a row in a database table.

A scheduled job is a method Spring calls on a timer (@Scheduled). A lock here is a row in the shedlock table saying "job X is taken until time T, by host H".

Why we use it here

The spec's technology table (section 3) lists "ShedLock + Spring scheduler ... Cluster-safe jobs (TSQ sweeps, file pulls)", and section 7.1 says saga deadlines are "swept every second by a ShedLock-guarded job."

Then ADR D11 decided on one instance of everything. Spec section 19.3 explains why ShedLock stays anyway: "Stateful edges (SMPP binds, SFTP pulls, scheduled jobs) run in the single instance; ShedLock stays in place so a second instance could be added later without code change." It is cheap: one small table and one annotation per job.

How it is wired

From services/mw-adapter-telco/build.gradle.kts (versions inline, ADR D13):

// Scheduled jobs run on one instance only (ShedLock on this service's schema, 4.4).
implementation("net.javacrumbs.shedlock:shedlock-spring:7.10.1")
implementation("net.javacrumbs.shedlock:shedlock-provider-jdbc-template:7.10.1")

Each service turns it on in config/SchedulingConfig:

@Configuration(proxyBeanMethods = false)
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30M")
public class SchedulingConfig {

  @Bean
  public LockProvider lockProvider(DataSource dataSource) {
    return new JdbcTemplateLockProvider(
        JdbcTemplateLockProvider.Configuration.builder()
            .withJdbcTemplate(new JdbcTemplate(dataSource))
            .usingDbTime()
            .build());
  }
}
  • JdbcTemplateLockProvider keeps locks in a plain SQL table over the service's own datasource. No extra infrastructure.
  • usingDbTime() uses PostgreSQL's clock, not the JVM's, so two hosts with slightly different clocks still agree.
  • defaultLockAtMostFor = "PT30M" (an ISO-8601 duration: 30 minutes) is the safety rule from the analogy, for jobs that do not set their own.

The table comes from a Flyway migration in the service's own schema, V3__shedlock_and_purge.sql:

CREATE TABLE shedlock (
  name        varchar(64)  NOT NULL PRIMARY KEY,
  lock_until  timestamp    NOT NULL,
  locked_at   timestamp    NOT NULL,
  locked_by   varchar(255) NOT NULL
);

Every service except mw-seeder (a one-shot with no timer) has the dependency, its own SchedulingConfig and its own shedlock table. No service ever reads another's (root CLAUDE.md: never touch another service's schema).

How the lock works

A job is a @Scheduled method with a @SchedulerLock next to it. The purge job every service has:

@Scheduled(cron = "${mw.retention.cron}")
@SchedulerLock(name = LOCK_NAME)
public void purge() {
  retention.purge();
}
  1. The timer fires. Before the method runs, ShedLock tries to update the row name = 'outbox-inbox-purge' to lock_until = now + lockAtMostFor, but only if lock_until is already in the past (inserting the row the first time).
  2. Got it: the method runs. When it ends, ShedLock sets lock_until to now (or to locked_at + lockAtLeastFor if that is later). The row stays.
  3. Did not get it: another instance holds the lock. The method is skipped for this tick. Nothing is queued.
  4. The holder crashed: nobody releases the row, but once lock_until passes, the next tick anywhere takes it.
SettingMeaningPick it as
lockAtMostForHow long the lock lasts if the holder dies.Clearly longer than one normal run, short enough that a crash does not stall the job for long.
lockAtLeastForKeep the lock at least this long, even after a quick run, so a second instance whose clock ticks a little later does not run it again.PT0S for jobs that run every second or so.

Two jobs are left without a lock on purpose, because each instance needs its own run: mw-crypto's HsmProbeJob (each instance reports its own HSM sessions) and mw-core-mock's AssertionKeyRefreshJob (an in-memory key cache every instance needs). Both say so in their class comment.

Worked example: the saga timer sweep

Every saga step in mw-orchestrator has a deadline, stored in saga_timer. Something has to notice when one passes. That is SagaTimerJob:

@Scheduled(fixedDelayString = "${mw.orchestrator.timer.period:1s}")
@SchedulerLock(name = LOCK_NAME, lockAtMostFor = "PT30S", lockAtLeastFor = "PT0S")
public void sweep() {
  timers.sweep();
}
  1. fixedDelay means "1 s after the last run ended", so sweeps never overlap inside one instance.
  2. ShedLock takes saga-timer-sweep for at most 30 s. A sweep handles a batch of 50 timers, far quicker than that, so 30 s is plenty. If the orchestrator crashes mid-sweep, the restarted one can sweep again at most 30 s after the crash, not 30 minutes.
  3. lockAtLeastFor = "PT0S": the lock is released as soon as the sweep ends, so the next tick is not blocked.
  4. service/SagaTimerService.sweep() reads the due timers with FOR UPDATE SKIP LOCKED. That is a second safety net: even two sweepers running at once would never pick the same timer.
  5. For each due timer it fires DeadlineExpired; the state machine decides what that means (VALIDATING to FAILED, POSTING to UNKNOWN, ...), and an UNKNOWN transaction's inquiry timer starts a status inquiry (see Resilience4j).

The conformance test conformance/OutboxInboxPurgeConformanceIT (in every service) proves the skip: it writes a shedlock row as if other-instance held the purge lock, calls the job, and checks that nothing was deleted.

Where it lives
  • config/SchedulingConfig.java: the lock provider (same in every service).
  • scheduler/OutboxInboxPurgeJob.java and V3__shedlock_and_purge.sql.
  • mw-orchestrator scheduler/SagaTimerJob.java, service/SagaTimerService.java, repository/SagaTimerRepository.java (the SKIP LOCKED query).
  • Unlocked on purpose: HsmProbeJob.java, AssertionKeyRefreshJob.java.
  • Test: OutboxInboxPurgeConformanceIT.java.

What can go wrong

What can go wrong
  • "My job did not run." A held lock means the run is skipped, not delayed. With one instance that usually means the previous run is still going (or crashed and its lock has not expired yet). Look at the row: select * from shedlock in the service's schema.
  • A crash stalls a fast job for 30 minutes. A job without its own lockAtMostFor gets the 30-minute default. Give every frequent job a short one, as SagaTimerJob (30 s) and BulkDispatchJob (1 min) do.
  • lockAtMostFor shorter than a real run. The lock expires mid-run and a second instance could start the same job. Size it from the slowest run, with room to spare.
  • A new service has no shedlock table. ShedLock does not create it. It must come from a Flyway migration in the service's own schema, like V3__shedlock_and_purge.sql.
  • You deleted the lock row to "unstick" a job. Don't: ShedLock keeps its row and updates it. Wait for lock_until to pass, or set it to the past. The purge conformance test does exactly that instead of deleting.
  • A job that must run on every instance got a lock. Then only one instance would do it. Leave such jobs unlocked and say why in the class comment, as HsmProbeJob does.
