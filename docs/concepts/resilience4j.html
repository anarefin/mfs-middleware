Resilience4j: timeouts, circuit breakers and bulkheads

A partner that is slow or down must not drag the middleware down with it. Resilience4j wraps each outbound call with a time limit, a circuit breaker and a cap on calls in flight. And one rule matters more than any setting: a payment call is never retried automatically.

In plain English

In plain English

Think of the fuse box in a house. If one appliance shorts, its fuse blows, so the rest of the house keeps its power. After a while you try the switch again. A circuit breaker does that for calls: when too many calls to one partner fail, it stops calling for a while and fails at once instead.

Three more tools come in the same box. A time limiter is a kitchen timer: if the answer is not back in time, stop waiting. A bulkhead (named after the walls that keep one flooded part of a ship from sinking it) is a cap on how many calls may be in flight to one partner. A retry tries again after a failure, which is only safe when doing the same thing twice is harmless.

WordMeaning
Closed / open / half-openThe breaker's states. Closed: calls go through. Open: calls fail at once with CallNotPermittedException. Half-open: a few trial calls decide whether to close again.
Sliding windowThe recent calls the breaker looks at: the last N seconds (TIME_BASED) or the last N calls (COUNT_BASED).
Slow callA call that succeeded but took longer than slow-call-duration-threshold. Too many of them also open the breaker.
InstanceOne named breaker, bulkhead or retry with its own counters, for example ocs or billpay.
IdempotentSafe to repeat: doing it twice has the same effect as once. A read is; a top-up is not.

Why we use it here

Spec section 19.2 sets the defaults, with a per-partner override:

PolicyDefault (spec 19.2)
Time limiterPartner timeout from 11.1
Circuit breaker60 s time-based window, minimum 50 calls; open at 50% failure or 50% slow calls (> 80% of timeout); open 30 s; 5 half-open probes
BulkheadSemaphore, 200 concurrent calls per partner
Retry"Only for idempotent calls (status inquiry, fetch-bill, GET): 2 retries, 200 ms → 1 s exponential + jitter"

Spec 12.2 adds that every adapter is wrapped by the framework "with: bulkhead, circuit breaker, time limiter, audit of raw request/response (masked), correlation headers, metrics."

Why no retry on payments? If a top-up times out, the OCS may already have applied it. Sending it again could top up twice. So a payment gets exactly one attempt, and an unclear outcome becomes UNKNOWN, which a later status inquiry resolves (see UNKNOWN in tutorial chapter 3). Partners also deduplicate on our stable reference, which covers the rare duplicate that slips through.

How it is wired

From services/mw-adapter-telco/build.gradle.kts (every module writes its versions inline, ADR D13):

implementation(platform("io.github.resilience4j:resilience4j-bom:2.4.0"))
...
// Resilience4j for client/ calls (19.2); annotations need AspectJ.
implementation("io.github.resilience4j:resilience4j-spring-boot4:2.4.0")
implementation("org.springframework.boot:spring-boot-starter-aspectj")

The defaults sit under resilience4j in each service's application.yml. The telco adapter's, shortened:

resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-type: TIME_BASED
        sliding-window-size: 60
        minimum-number-of-calls: 50
        failure-rate-threshold: 50
        slow-call-rate-threshold: 50
        # 80% of the default partner timeout (30 s, 11.1); partners override both.
        slow-call-duration-threshold: 24s
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 5
    instances:
      ocs:
        base-config: default
        slow-call-duration-threshold: 16s
  bulkhead:
    configs:
      default:
        max-concurrent-calls: 200
        max-wait-duration: 0
    instances:
      ocs:
        base-config: default
        max-concurrent-calls: 100
  timelimiter:
    configs:
      default:
        timeout-duration: 30s
  retry:
    configs:
      default:
        max-attempts: 3
        wait-duration: 200ms
        enable-exponential-backoff: true

A few things to notice. max-attempts: 3 means one try plus the spec's two retries. max-wait-duration: 0 means a full bulkhead refuses at once instead of queueing. The OCS breaker counts a call as slow after 16 s, 80% of its 20 s timeout. The file's own comment says it plainly: "never annotate a payment call with @Retry."

Every service except the one-shot mw-seeder has the dependency. They use it in two styles:

StyleWhereInstances
Programmatic: code asks a registry for a breaker and calls executeSupplier the circuitBreaker step of the mw-http-call / mw-soap-call Kamelets in the three adapters (Camel's Resilience4j EIP); client/AuthClient in mw-app-gateway, mw-ussd and mw-checkout; client/CryptoClient in mw-auth; client/PayShieldProvider in mw-crypto one per partner (ocs, ...), mw-auth, ...
Annotations: @CircuitBreaker and @Retry on a method client/BillPayClient (mw-app-gateway; mw-ussd breaker only), client/OrchestratorQueryClient (mw-app-gateway, mw-admin-api, mw-portal-api), client/AuditQueryClient (mw-admin-api) billpay, orchestrator, audit-dw

Partner calls: inside the Kamelet

Every partner call is a step of the partner's route (Camel): kamelet:mw-http-call (or mw-soap-call). The Kamelet wraps the send in Camel's circuitBreaker EIP, configured for Resilience4j: breaker, time limit and bulkhead in one step. From src/main/resources/kamelets/mw-http-call.kamelet.yaml:

- loop:
    doWhile: true
    simple: "${exchangeProperty.mwAttemptAgain} == true"
    steps:
      - to: "kamelet:mw-auth-{{auth}}?..."          # signed again before every attempt
      - circuitBreaker:
          resilience4jConfiguration:
            circuitBreaker: "mw-cb-{{partnerId}}"     # the partner's own breaker
            timeoutEnabled: true
            timeoutDuration: "{{timeoutMs}}"          # from the record
            bulkheadEnabled: true
            bulkheadMaxConcurrentCalls: "{{bulkhead}}"
          steps:
            - to: "{{url}}?throwExceptionOnFailure=false&followRedirects=false&..."
            - bean: { ref: mwHttp, method: response }   # a 5xx throws here, inside the breaker
          onFallback:
            steps:
              - bean: { ref: mwHttp, method: fallback } # what the failure means

MwHttpStep.fallback turns the failure into an outcome:

What happensOutcomeReply code (via mapper/PartnerReplyMapper)
Bulkhead fullNOT_SENT BULKHEAD_FULLFAILED MW-SYS-PARTNER_BUSY, retryable
Circuit openNOT_SENT CIRCUIT_OPENFAILED MW-SYS-PARTNER_CIRCUIT_OPEN, retryable
Connect failedNOT_SENT CONNECT_FAILEDFAILED MW-SYS-PARTNER_UNAVAILABLE, retryable
Time limit passedUNKNOWN TIMEOUTUNKNOWN MW-TMO-PARTNER_TIMEOUT
Partner answered 5xxUNKNOWN HTTP_5XXUNKNOWN MW-TMO-PARTNER_HTTP_5XX

NOT_SENT means nothing left the building, so the caller may safely try again later. UNKNOWN means the partner may have acted.

  • A PAY is sent once. The loop sends again only an INQUIRY or STATUS_QUERY, at most the record's inquiryRetries times, after a timeout, 5xx, reset or failed connect. A payment is not idempotent from our side, so it is never re-sent (the one exception: an OAuth2 token the partner refused with 401, where nothing was applied; ADR D28).
  • Names. The breaker is the Resilience4j instance named by the partner id (the record's resilience overrides its settings), bound in Camel's registry as mw-cb-<id> by partner/route/PartnerRoutes. So the ocs instance under resilience4j.circuitbreaker.instances applies to the ocs partner, and its state survives a route swap. A dry-run uses its own breaker mw-cb-<id>~candidate, so a failing dry-run never opens the live one.
  • Time limit from the record, not YAML. The loader injects timeoutMs, connectTimeoutMs, readTimeoutMs and bulkhead into the Kamelet from the partner record; a route cannot set them. The OCS dev seed sets timeout-ms: 20000 and read-timeout-ms: 22000 (the read timeout sits above, so the time limit decides first). An approved mw.config.changed.v1 record changes them without a restart.
  • Only exceptions count. Transport failures, 5xx (thrown on purpose inside the breaker) and timeouts count. A business refusal ("subscriber barred") is a normal answer and does not open the breaker.

Internal calls: annotations in client/

Calls between our own services that are safe to repeat use annotations. From mw-app-gateway's client/BillPayClient:

@Retry(name = "billpay")
@CircuitBreaker(name = "billpay")
public List<Biller> billers() {
  return json.readValue(send(request("/billpay/v1/billers").GET().build()), BILLERS);
}

The annotations are applied by a Spring proxy built with AspectJ (hence spring-boot-starter-aspectj). The instance tells the breaker which exceptions count:

billpay:
  base-config: default
  minimum-number-of-calls: 20
  record-exceptions: mfs.mw.app.gateway.exception.BillPayUnavailableException
  ignore-exceptions: mfs.mw.app.gateway.exception.BillPayRefusedException

So "the adapter is down" counts, while "this bill number does not exist" (BillPayRefusedException) does not. mw-ussd's copy of the same client has @CircuitBreaker only: the MNO holds the USSD screen open, so there is time for one short attempt and no retry.

Worked example: the OCS does not answer

A customer buys airtime and the OCS hangs.

  1. The bulkhead lets the call in (fewer than 100 OCS calls in flight) and the breaker is closed.
  2. The breaker's time limit (timeoutDuration, 20 s from the record) waits for the OCS. After that it gives up and MwHttpStep.fallback reports UNKNOWN with reason TIMEOUT; a PAY is not sent again. The OCS may or may not have topped up the phone, so the middleware does not guess.
  3. The breaker records a failure. One timeout does nothing; at least 50 calls in 60 s with half failing (or slower than 16 s) would open it.
  4. The orchestrator moves the transaction to UNKNOWN and arms an inquiry timer (swept by its ShedLock-guarded SagaTimerJob, see ShedLock).
  5. The inquiry is a STATUS_QUERY with the same stable reference, through the same breaker and limits. Unlike the PAY it may be sent once more after a timeout (inquiry-retries: 1 in the OCS seed).

If the OCS is really down, the breaker opens after enough failures. For the next 30 s calls fail fast with MW-SYS-PARTNER_CIRCUIT_OPEN and the OCS is not called at all. route/TelcoRequestRouteIT proves this with a 4-call COUNT_BASED window: four 500s, then the fifth request is refused without reaching WireMock.

Where it lives
  • services/mw-adapter-telco/src/main/resources/kamelets/mw-http-call.kamelet.yaml: the breaker, time limit, bulkhead and loop; partner/kamelet/MwHttpStep.java: what a failure means (fallback).
  • partner/route/PartnerRoutes.java (binds mw-cb-<id>), partner/config/PartnerConfig.java (timeout defaults).
  • mw-adapter-telco application.yml and mw-app-gateway application.yml: the resilience4j blocks.
  • mw-app-gateway client/BillPayClient.java: the annotation style.
  • Tests: client/ResilienceDefaultsIT (the 19.2 defaults are wired) and route/TelcoRequestRouteIT (timeout and open circuit).

What can go wrong

What can go wrong
  • Someone adds @Retry to a payment. A timed-out top-up retried is a possible double top-up. Retry is for idempotent reads only. Review catches it; the YAML comment warns about it.
  • A business error opens the breaker. Only exceptions count. If your client throws for a normal "no" answer, list that exception under ignore-exceptions, or return the answer instead of throwing.
  • The read timeout is shorter than the time limit. Then the HTTP client gives up first and the limiter never decides. Keep the read timeout a little above it (the default is timeout + 2 s).
  • An annotation does nothing. Annotations work only through the Spring proxy: they need the AspectJ starter, and a call from inside the same class (this.billers()) bypasses the proxy.
  • Tests interfere through a breaker. Breakers keep their state for the life of the Spring context. A test that trips one leaves it open for the next test. TelcoRequestRouteIT calls breakers.circuitBreaker("ocs").reset() before each test.
  • A full bulkhead looks like an outage. With max-wait-duration: 0, call 101 to the OCS fails at once with MW-SYS-PARTNER_BUSY. That is by design: waiting would only pile up threads.
