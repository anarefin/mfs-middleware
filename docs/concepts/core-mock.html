Test double

mw-core-mock: a small core with a real ledger

The middleware never moves money itself. It asks the core, the bank-grade wallet system, over Kafka. The real core is not available to us, so mw-core-mock plays it: a double-entry ledger that answers the same commands with the same events, plus switches that let a test break it on purpose.

In plain English

In plain English

Picture a flight simulator. Pilots train on it because it reacts like the real plane, and the instructor can switch on an engine fire whenever they like. mw-core-mock is our flight simulator for the core: it keeps real balances and real rules, and a test can tell it to "lose the next reply" or "refuse the next transfer".

A ledger is the book of every money movement. Double-entry means every movement is written twice, a debit on one wallet and an equal credit on another, so the total of all balances never changes. If it ever does, something is broken.

WordMeaningExample here
CommandA request to the core, sent on Kafka.PostTransfer on core.wallet.command.v1
Result eventThe core's answer, on the paired event topic.TransferPosted or TransferRejected on core.wallet.event.v1
commandIdThe id that makes a command idempotent: the same id twice has one effect and gets the same answer.<txnId>:post for the orchestrator's PostTransfer
HoldMoney reserved but not yet moved, while a partner (biller, telco) is called.HoldFunds, then CommitHold or ReleaseHold
PoishaOne hundredth of a taka. Every amount is an integer in poisha ("minor units").1000 = Tk 10.00

Why we use it here

ADR M4 says why a stub that always says yes is not enough: "a stub that always says yes would hide the hard paths (holds, insufficient funds, lost replies)." So the mock has a real ledger, fees, limits and fault injection. The same ADR sets the boundary: "It is a test double: it never ships to production and is replaced by the real core without orchestrator change."

That last part is the point. mw-core-mock speaks only the Kafka contract of spec section 6.3. If the orchestrator works against it, it should work against the real core, which will speak the same contract. Tests also read its balances to prove money never moves twice.

How it is wired

ContainerPortsNotes
mw-core-mock8080 inside, published as 127.0.0.1:8084Profiles minimal and core. Its own schema coremock in PostgreSQL. Reads and writes only Kafka for the money path; the HTTP API is for tests.

Two dev-only switches in its deploy/docker-compose.yml block:

  • MW_COREMOCK_SEED_API_ENABLED: turns on PUT /core-mock/v1/wallets/{walletId}, the create-if-absent call mw-seeder uses. Off by default (then a PUT is 405).
  • MW_COREMOCK_WALLET_SNAPSHOT: on every start, publish a WalletStateChanged SNAPSHOT for every wallet, so mw-auth's copy of the wallets catches up.

On every start it seeds itself from versioned files (service/WalletSeeder, src/main/resources/seed/v1/, idempotent; ticket 94): 1,000 customers from 01711000001 (the last 100 with BASIC KYC), 50 agents from 01811000001, 10 distributors from 01611000001, 20 merchants from 01911000001, 3 organisations from 01311000001 (the wallet id is the MSISDN), the system wallets FEE_INCOME, VAT_PAYABLE, COMMISSION_PAYABLE, SETTLEMENT (money going to or coming from outside when no partner is named) and one settlement wallet per partner (SETTLEMENT_OCS_GP, SETTLEMENT_NPSB, SETTLEMENT_UCB_IMT, ...), plus the tariff sheet (fee per txnType and amount slab, VAT 15 % inside the fee, agent and distributor commission) and the limit sheet (per txnType, wallet type and KYC level: per transaction, daily and monthly amounts and counts). A hold not committed within 30 minutes is released by the core with the event HoldExpired. A customer starts with Tk 10,000. There is no PIN here: mw-auth holds PINs, and the core only checks the signed approval (see HSM).

Commands and the ledger

It listens on core.wallet.command.v1 and core.payment.command.v1 (Camel routes route/CoreWalletCommandRoute and route/CorePaymentCommandRoute) and answers on the paired event topic:

CommandWhat it does
ValidateTransactionRuns every check, works out the fee, moves nothing.
PostTransferDebit the payer, credit the payee, debit the fee, split into FEE_INCOME, VAT_PAYABLE and COMMISSION_PAYABLE: one transaction, all or nothing.
HoldFunds, CommitHold, ReleaseHoldReserve amount + fee; later move it to SETTLEMENT, or free it.
CreditWalletMoney in from SETTLEMENT (add money from a bank), once per transaction.
ReverseTransactionUndo every entry of an earlier transaction, fee included.
QueryTransaction"What really happened?" Reads the ledger and the command log, never the outbox, so it tells the truth even when a reply was lost.
UnlockWallet, VerifyCustomerFactorsA core-side account unlock; the KYC check of a self-service PIN reset.

The checks run in a fixed order, and the first failure is the reason code: wallets exist, wallet types fit the transaction type (for example CASH_OUT must be customer to agent), status, assertion, amount, limits (Tk 5,000 per transaction and Tk 15,000 per day by default), funds.

Three rules keep it trustworthy:

  • Idempotent on commandId. The first result event is stored in command_log. A repeat gets the same event again, with one ledger effect.
  • Outbox. The ledger change, the command_log row and the reply event commit in one database transaction. The reply is sent afterwards by the outbox relay. So a crash never leaves money moved with no reply recorded.
  • The assertion is checked like a real core would. service/AssertionCheck verifies the ES256 signature against mw-auth's public key set (client/AssertionJwksClient, fetched at start and every 30 s), recomputes txnHash from the command, and claims the jti in used_assertion so one approval pays once. Every refusal is the reason MW-AUTH-046.

Its tables: wallet, hold, entry (the ledger lines), command_log, reversal, used_assertion, plus the outbox and inbox.

Fault injection

A small HTTP API (in memory, not a product contract) arms faults that match a commandType and/or a txnId, for times uses or until reset:

ModeEffectWhat it tests
DELAYThe reply is sent delayMs later.Deadlines and timeouts in the saga.
DROP_REPLYThe command takes effect, but no reply is sent.The unknown-outcome path: the orchestrator must ask.
DUPLICATE_REPLYThe reply is sent twice with the same eventId.The orchestrator's inbox dedup.
REJECTThe command is refused without effect, with reasonCode (default INJECTED_REJECT).Failure handling and error mapping.
  • POST /core-mock/v1/faults {mode, commandType?, txnId?, delayMs?, reasonCode?, times?} arms one; GET lists; DELETE clears all.
  • GET /core-mock/v1/wallets/{walletId} (id or MSISDN) shows balanceMinor, heldMinor and availableMinor.
  • From the host, use the test-only edge route /test/core-mock/v1/* (deploy/apisix/routes-test/test-core-mock.json, GET, POST and DELETE only, test API key in an apikey header from scripts/creds.sh), or the direct dev port 8084. The test console page Simulators & faults uses the same API.

Worked example: a lost reply

A tester wants to see what happens when the core moves the money but its answer never arrives. They arm a fault, then send Tk 10 from 01711000001 to 01711000002:

  1. Arm the fault. {"mode":"DROP_REPLY","commandType":"PostTransfer","times":1}: the next PostTransfer loses its reply.
  2. The tester sends the P2P payment.
  3. mw-app-gateway publishes the request (with mw-auth's assertion) on Kafka.
  4. The orchestrator asks the core to validate.
  5. The mock runs its checks and answers normally: Tk 10 plus a Tk 5 fee.
  6. The orchestrator asks it to post.
  7. The mock writes the ledger entries and the command_log row, but the fault suppresses the reply.
  8. The POSTING deadline runs out (2 s in the dev timers, 5 s in production), and the transaction becomes UNKNOWN.
  9. The app gets 202 PROCESSING: "we are not sure yet".
  10. On the inquiry schedule the orchestrator sends QueryTransaction.
  11. The mock reads its ledger, not the outbox, and answers POSTED.
  12. The transaction is COMPLETED. GET /test/core-mock/v1/wallets/01711000001 shows Tk 15 less, exactly once.
Where it lives
  • services/mw-core-mock/CLAUDE.md: every command, reason code and rule. Read this next.
  • Service: service/CoreCommandService (dispatch), service/PostingOperations, service/HoldOperations, service/AssertionCheck, service/FaultRegistry, service/WalletSeeder.
  • Assertion keys: security/AssertionKeys, client/AssertionJwksClient.
  • Settings (fees, limits, seed balances): application.yml, under mw.coremock.
  • Contracts: commands in contracts/events/mw-orchestrator/core.command.v1.schema.json, events in contracts/events/mw-core-mock/core.event.v1.schema.json (owned by mw-core-mock until the real core takes them over).

What can go wrong

What can go wrong
  • Every payment is refused with MW-AUTH-046. That is the single code for any assertion problem: bad signature, wrong hash, expired, reused jti. The real cause is in the mock's WARN core.assertion.refused.
  • Right after mw-auth rotated its assertion key, payments fail for up to 30 s. The mock fetches the key set at start and every 30 s, never on a command. An unknown kid is refused until the next refresh.
  • A fault keeps firing. A fault without times lasts until reset. DELETE /test/core-mock/v1/faults clears them all. They are in memory, so a restart clears them too.
  • Balances are not what the seed said. The seed only creates missing wallets and never resets a balance, so earlier tests leave their traces. deploy/reset.sh gives a clean ledger.
  • A REJECT fault seems ignored on a retry. A repeated command is answered from command_log; REJECT does not re-decide it. Arm the fault before the first send.
  • Do not build business rules on the mock. It approximates a core (a small tariff and limit sheet). Real fees, limits and KYC belong to the real core vendor.
