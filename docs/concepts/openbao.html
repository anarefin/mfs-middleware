Secrets

OpenBao: where the secrets live

No password, client secret or key is ever written in code, a config file or a test. Every service reads its secrets from OpenBao when it starts, using a login that lets it read its own secrets and nothing else. OpenBao also hands out the short-lived certificates that some services use for mTLS.

In plain English

In plain English

Think of a bank's safe-deposit room. Each customer has their own box and their own key. The key opens that one box and no other, and the guard writes down every visit. OpenBao is that room for secrets. Each service has its own "box" (a path such as secret/mw-app-gateway) and its own login that opens only that box.

OpenBao is an open-source fork of HashiCorp Vault with the same API. Spring Cloud Vault, the Spring library we use to talk to it, works with both. So when you read "Vault" in a property name or in the spec, it means OpenBao here.

A few OpenBao words you will see everywhere:

WordMeaningExample here
Secrets engineA plug-in at a path that stores or makes secrets.secret/ (key-value), pki_int/ (certificates)
KV v2The key-value engine, version 2 (keeps old versions). The API puts data/ into the path.read secret/mw-app-gateway, policy path secret/data/mw-app-gateway
PolicyA list of paths and what a token may do on them.mw-app-gateway may read its own secret and update (issue) its own certificate role
AppRoleA login method for machines: a role-id (like a user name) plus a secret-id (like a password).one AppRole per service, named after it
Seal / unsealOpenBao starts locked ("sealed") and cannot read its own data until it gets the unseal key.the dev entrypoint unseals it on every start
PKI"Public key infrastructure": the engine that acts as a certificate authority (CA) and issues certificates.72-hour certificates for mw-auth, mw-crypto and their callers

Why we use it here

The same decision record as Keycloak, D9, picks "OpenBao for secrets (KV, per-service AppRole, config binding at start)". The spec (section 18.4) is short about it: "Vault/OpenBao is the only secret store." A secret in a YAML file ends up in Git, in images and in logs. A secret in OpenBao is read at start-up into memory and nowhere else.

D24 added a second job: "OpenBao PKI issues service certificates (an intermediate CA, one role per service, 72 h, renewed at two thirds of their life)." mTLS is mandatory on mw-crypto (it fronts the HSM) and on mw-auth's internal API (PINs and assertions). mTLS ("mutual TLS") means both sides of a connection show a certificate, not only the server.

What OpenBao does not do here, even though the engines are switched on:

  • No encryption keys in the transit engine. The keys for PINs, token signing and envelope encryption live in the HSM behind mw-crypto (spec 18.4, decision 2026-11-14). transit is enabled but unused.
  • No dynamic database passwords yet. The database engine is enabled but unused. Each service's PostgreSQL password is a fixed random value in its KV secret, created once by the provision one-shot.

How it is wired

Two containers in deploy/docker-compose.yml do the work, plus one small volume per service:

ContainerKindWhat it does
openbaolong-running, no profileOpenBao 2.7 on port 8200, published on 127.0.0.1:8200 (knob MW_PORT_OPENBAO). Data on the openbao-data volume. Its entrypoint is deploy/openbao/dev-unseal.sh. Healthy only once it is unsealed and the engines exist (the script writes a dev-ready file).
provisionone-shot, profiles minimal and coreStarts once PostgreSQL, OpenBao and Keycloak are healthy. Writes every service's secrets, database role, certificate role, policy and AppRole, then exits 0. Every mw-* service waits for it.

Three files configure OpenBao itself:

  • deploy/openbao/config.hcl: Raft storage on the data volume and a plain-HTTP listener on 8200 (tls_disable; the stack's internal network only).
  • deploy/openbao/dev-unseal.sh: starts the server, and on the first start initialises it with one key share, then enables secret/ (KV v2), transit, pki, database and the approle login. It also creates the fixed tester token (scripts/creds.sh prints it). On every start it unseals the server with the key it saved.
  • deploy/provision/: the one-shot's image and scripts, described next.

Every mw-* service gets two shared settings from the x-jvm-env block: VAULT_ENABLED (true) and VAULT_ADDR (http://openbao:8200). Each one also mounts its own AppRole volume read-only at /run/mw/approle, for example app-gateway-approle for mw-app-gateway. Services that need a certificate also get MW_TLS_ENABLED set to true.

The provision one-shot

deploy/provision/provision.sh is the only thing in the stack that holds the OpenBao root token (read from the data volume, which it mounts read-only) and the PostgreSQL admin password. It runs on every up and is idempotent: running it twice leaves the same result. In order, it does this:

  1. The certificate authority, once. pki_setup in deploy/provision/lib.sh creates a dev root CA at pki/ and an intermediate CA at pki_int/ that signs every service certificate. Then pki_role writes one role per service in PKI_SERVICES: the certificate's name (CN) must be exactly the service name, EC P-256 keys, at most 72 hours.
  2. For each service in SERVICES (the manifest is deploy/provision/services.sh, one function per service):
    • gen_once makes a random value (a database password, a hash key) the first time and never overwrites it.
    • sync_env copies a value from deploy/.env into the secret on every run, for example a Keycloak client secret.
    • db_role creates the service's PostgreSQL login role and its own schema, with the password from its secret.
  3. The login. approle writes a policy that may read only that service's secret (plus issue from its own pki_int role, for a PKI service), creates the AppRole, and writes the role-id and a fresh secret-id into the service's volume as two files: spring.cloud.vault.app-role.role-id and spring.cloud.vault.app-role.secret-id.

Fifteen services, fifteen volumes. The PKI list today is mw-crypto, mw-auth, mw-app-gateway, mw-ussd, mw-checkout, mw-audit-dw and mw-admin-api: the two mTLS servers and everyone who calls them. The provision one-shot also creates the partner simulator's key pair for its private_key_jwt login at Keycloak and stores the PKCS#11 PIN mw-crypto uses to log in to the HSM.

How a service reads its secrets

This is the whole binding, from a service's application.yml (mw-admin-api here, every service has the same):

spring:
  config:
    import: "optional:configtree:${MW_APPROLE_DIR:/run/mw/approle/},optional:vault://"
  cloud:
    vault:
      enabled: ${VAULT_ENABLED:false}
      uri: ${VAULT_ADDR:http://openbao:8200}
      authentication: APPROLE
      kv:
        enabled: true
        backend: secret
        default-context: ${spring.application.name}
  • configtree: is a standard Spring Boot feature: every file in a folder becomes a property named after the file. The two files provision wrote become spring.cloud.vault.app-role.role-id and ...secret-id. No secret goes through an environment variable.
  • vault:// tells Spring Cloud Vault to log in with that AppRole and load secret/<application name> as properties. The keys in the secret are plain Spring property names, such as spring.datasource.password, so they simply fill in the config.
  • Both are optional: and VAULT_ENABLED defaults to false, so unit tests and *IT tests run without OpenBao.

For example, secret/mw-app-gateway holds spring.datasource.password, spring.data.redis.password (Valkey) and mw.app-gateway.auth.client-secret (its Keycloak client secret, synced from KC_MW_APP_GATEWAY_SECRET).

Certificates that renew themselves

A service with mw.tls.enabled has a ServiceCertificateManager in its config package. At start it asks pki_int/issue/<its own name> for a 72-hour certificate, through the same AppRole login. The private key stays in an in-memory keystore and is never written to disk. At two thirds of the life (48 hours) it gets a new one and swaps it in without a restart. If it cannot get a certificate at start, the service fails to start: mTLS is mandatory. It also exports the gauge tls.certificate.expiry.seconds.

Worked example: mw-app-gateway starts

Here is everything that happens between docker compose up and mw-app-gateway's first mTLS call to mw-auth:

  1. Provision prepares everything. With the root token it writes the certificate role, the secret secret/mw-app-gateway, the policy and the AppRole, and drops the role-id and secret-id into the app-gateway-approle volume. Then it exits 0.
  2. The service reads its login. Compose starts mw-app-gateway only after provision succeeded. Spring's configtree import turns the two files under /run/mw/approle into properties.
  3. It logs in. Spring Cloud Vault sends the role-id and secret-id to http://openbao:8200 and gets back a token whose policy is mw-app-gateway. That token can read one secret and issue one kind of certificate. Nothing else.
  4. It reads its secrets. The fields of secret/mw-app-gateway become properties: the datasource connects, Valkey connects, and the Keycloak client secret is ready.
  5. It gets its certificate. ServiceCertificateManager issues a 72-hour certificate from pki_int/issue/mw-app-gateway, with CN and DNS name mw-app-gateway.
  6. It calls mw-auth. It asks Keycloak realm services for a client-credentials token (audience mw-auth), then calls https://mw-auth:8443. That internal port demands a client certificate (client-auth: need). mw-auth's InternalCallerPolicy checks that the token's azp is on its allow-list and equals the certificate's CN. A stolen token without the matching certificate is refused.
Where it lives
  • deploy/openbao/dev-unseal.sh (start, unseal, engines; its header explains the dev-only shortcuts) and deploy/openbao/config.hcl.
  • deploy/provision/provision.sh (the order of steps), lib.sh (each step), services.sh (what each service's secret holds). Read services.sh next.
  • The Spring binding: mw-admin-api application.yml (spring.config.import, spring.cloud.vault, the mw.tls block).
  • Certificates: mw-app-gateway config/ServiceCertificateManager.java (the same copy sits in each PKI service).
  • Decisions: D9, D24.

What can go wrong

What can go wrong
  • The root token and unseal key sit in the data volume. That is a dev-only shortcut and a known gap (D9). Production unseals with a KMS, an HSM or key holders, and never keeps the root token next to the data.
  • A service never starts and says it waits for provision. The one-shot failed. Run docker compose logs provision from deploy/. A message like "is not set (cp dev.env.defaults .env first)" means deploy/.env is missing a value.
  • You changed a value in deploy/.env and the stack does not come up. sync_env values are copied again on every run, but the PostgreSQL, Keycloak and etcd volumes were set up with the old values. Run deploy/reset.sh and start again.
  • A service fails at start with a Vault or 403 error. Its policy does not allow the path it asked for. Check that its function in deploy/provision/services.sh writes the key it needs, and for a certificate that the service is listed in PKI_SERVICES.
  • WARN tls.certificate.renew_failed, then ERROR tls.certificate.expiring. The renewal at two thirds failed (it is retried every minute) and less than a third of the life is left. Check that openbao is healthy and not sealed. Once the certificate expires, calls to mw-auth and mw-crypto fail the TLS handshake. The steps are in docs/runbook.md ("Health and alerts").
  • "I need a secret value to debug." Do not paste it anywhere. scripts/creds.sh prints the dev token and logins; the OpenBao UI is on http://127.0.0.1:8200 while the stack is up.
