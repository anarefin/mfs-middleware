JSONata: partner formats as configuration

Every partner wants its request in its own JSON shape and answers in its own shape too. Instead of a Java class per partner, the adapters keep two small JSONata expressions per operation in the partner config: one builds the partner's request from ours, the other turns the partner's answer into one of our outcomes.

In plain English

In plain English

Think of a form translator at a bank counter. You hand over your form; the clerk copies the fields you filled in onto the other bank's form, in their order and with their names. When their answer comes back, the clerk reads it and ticks one box on your form: approved, refused or "we don't know yet". A JSONata mapping is that clerk, written as one short expression.

JSONata is a small query and transformation language for JSON, a bit like XPath for XML or jq on the command line. An expression takes one JSON document as input and produces another JSON value. We use the Java port com.dashjoin:jsonata.

Why we use it here

Spec section 12.1 gives the adapter framework three layers. Layer 2 is the mappings: "Request/response mapping as versioned JSONata expressions (for JSON) ... editable in the admin console with a test bench (paste sample → see output). Error-code map is a table."

The point is that a new partner of a known kind should be configuration only (spec 12, ADR D1). A field renamed by a partner is a one-line config change, not a release. Business rules that are not about the wire format (fail closed, which statuses are believable, the error map) stay in Java, so a mapping cannot accidentally turn an unknown answer into a refund.

Spec 12.1 also names XSLT for XML partners. None is built yet: all three adapters speak REST/JSON today. The admin console's partner page shows each operation's method and path, but it has no mapping editor or test bench yet.

How it is wired

Only the three adapters depend on it. From services/mw-adapter-telco/build.gradle.kts:

// Adapter framework (spec 12): partner request/response mappings in JSONata.
implementation("com.dashjoin:jsonata:0.9.10")
ServiceUses JSONata for
mw-adapter-telcoOCS top-up and status inquiry (the reference copy of the framework).
mw-adapter-billpayBill aggregator: pay, status query, signed callback and bill inquiry (the billagg route).
mw-adapter-bankBank debit: pay (202 PENDING), status query and signed callback (the c2wbank route).

There are no .jsonata files. The expressions are strings in the partner record's mappings, by name (<OPERATION>.request, <OPERATION>.response), next to the record's Camel route (Camel, ADR D28). The route names the mapping it wants: kamelet:mw-map?mapping=PAY.request builds the request body, kamelet:mw-classify?mapping=PAY.response reads the answer. The dev seeds are in application-dev.yml (dev profile only; a production start has no partners). At runtime an approved mw.config.changed.v1 record from mw-admin-api adds or replaces a partner's whole record, mappings included.

All the Java is one small class, partner/mapping/CompiledMapping:

public static CompiledMapping compile(String source) {
  try {
    return new CompiledMapping(Jsonata.jsonata(source));
  } catch (RuntimeException e) {
    throw new IllegalArgumentException(e.getMessage(), e);
  }
}

public Object evaluate(Object input) {
  try {
    return expression.evaluate(input);
  } catch (RuntimeException e) {
    throw new MappingException(e.getMessage(), e);
  }
}
  • compile runs once when a partner record is loaded, for every mapping the route names. A syntax error refuses the whole record, and the last good version stays live.
  • evaluate reuses the compiled expression: dashjoin evaluates on a per-thread copy, so one mapping is shared by concurrent calls. (Camel's own jsonata: component would parse the expression on every call, so the Kamelets do not use it.)
  • Input and output are plain JSON values: maps, lists, strings, numbers and booleans.

What a mapping gets and must give back

Two Kamelet steps decide the input of each mapping and check its output: partner/kamelet/MwMapStep (request) and partner/kamelet/MwClassifyStep (response).

MappingInputOutput
requestThe call's input (txnType, amount with valueMinor, currency and major such as "20.00", debitParty, creditParty, partner, attributes), plus reference (our stable partner reference), operation and txnId. Any JSON value. It becomes the HTTP body.
response{status, body}: the HTTP status code and the parsed JSON body (null when the body is not JSON). {outcome, partnerRef, code, message, reason}, where outcome is SUCCESS, FAILED, PENDING (only where the route passes pending=true), NOT_FOUND (status inquiry only) or UNKNOWN.

MwMapStep builds the request input like this:

Map<String, Object> input = new LinkedHashMap<>(call.input());
input.put("reference", call.reference());
input.put("operation", call.operation());
input.put("txnId", call.txnId());
...
Object mapped = PartnerExchange.runtime(exchange).mapping(name).evaluate(input);

The mapping does not get the last word. The adapter only believes an answer that fits the facts (it fails closed):

  • A 5xx status is UNKNOWN before any mapping runs. The response mapping never sees it.
  • SUCCESS needs a 2xx and a non-empty partnerRef.
  • FAILED needs a code and a status listed in the route's definiteStatuses (a mw-classify parameter). A code listed in ambiguousCodes of the record becomes UNKNOWN instead.
  • Anything else is UNKNOWN: UNEXPECTED_STATUS for a believable answer on the wrong status, MALFORMED_REPLY for the rest.

The partner's own code then goes through the error map, a plain table and not JSONata: partner code → MW-PTR-<PARTNER>-<suffix> plus whether it is retryable. An unlisted code becomes UNMAPPED, not retryable.

Worked example: the OCS top-up

This is the real PAY branch of the ocs partner's route and its two mappings in application-dev.yml:

error-map:
  "[2001]": { suffix: TOPUP_REJECTED, retryable: false }
route: |
  ...
        - simple: "${header.mwOperation} == 'PAY'"
          steps:
            - to: "kamelet:mw-map?mapping=PAY.request"
            - to: "kamelet:mw-http-call?url=...&method=POST&path=/ocs/v1/topup&auth=none"
            - to: "kamelet:mw-classify?mapping=PAY.response&definiteStatuses=400,422"
mappings:
  "[PAY.request]": |
    {"transactionId": reference, "msisdn": creditParty.id, "amount": amount.major}
  "[PAY.response]": |
    status = 200
        ? (body.status = "SUCCESS" and $type(body.ocsRef) = "string" and body.ocsRef != ""
            ? {"outcome": "SUCCESS", "partnerRef": body.ocsRef, "code": body.code}
            : {"outcome": "UNKNOWN", "reason": "MALFORMED_REPLY"})
      : status = 422
        ? ($type(body.code) = "string" and body.code != ""
            ? {"outcome": "FAILED", "code": body.code, "message": body.message}
            : {"outcome": "UNKNOWN", "reason": "MALFORMED_REPLY"})
      : status = 400
        ? {"outcome": "FAILED", "code": "HTTP_400", "message": body.message}
      : {"outcome": "UNKNOWN", "reason": "UNEXPECTED_STATUS"}
  1. Request. The input has reference (for example BITS plus the transaction id without dashes), creditParty.id (the phone number) and amount.major ("20.00" for 2000 minor units). The mapping picks those three fields and renames them. mw-http-call sends the result as the body.
  2. Answer. The OCS says 422 with {"status":"FAILED","code":"2001","message":"Subscriber barred"}.
  3. Response. The mapping sees status = 422 and a non-empty text code, so it returns {"outcome": "FAILED", "code": "2001", ...}.
  4. Checks. 422 is in the route's definiteStatuses and 2001 is not an ambiguous code, so FAILED is believed.
  5. Error map. 2001 maps to suffix TOPUP_REJECTED. The partner id was gp, so the reply carries MW-PTR-GP-TOPUP_REJECTED, not retryable. route/TelcoRequestRouteIT asserts exactly this.

Had the OCS said 200 without an ocsRef, the mapping would return UNKNOWN with MALFORMED_REPLY, and the orchestrator would find out the truth later with a status inquiry (the STATUS_QUERY branch and its STATUS_QUERY.response mapping in the same record).

Where it lives
  • partner/mapping/CompiledMapping.java: compile and evaluate.
  • partner/kamelet/MwMapStep.java (the request input) and partner/kamelet/MwClassifyStep.java: the fail-closed checks and the error map lookup. Its class comment is the rule book.
  • mapper/PartnerCallMapper.java: builds the request mapping's input.
  • application-dev.yml: the OCS mappings; services/mw-adapter-telco/CLAUDE.md: the mapping contract in short; Camel: the route around the mappings.
  • Tests: route/TelcoRequestRouteIT (end to end, the refused top-up below), partner/route/PartnerRouteLoaderTest (the route that names the mappings, no Docker).

What can go wrong

What can go wrong
  • The request mapping throws, or names a field that does not exist. A throw is caught and the call is NOT_SENT with reason MISCONFIGURED: nothing went to the partner. A missing field is quieter: JSONata leaves it out of the object, and the partner will probably refuse the request. Test new mappings against a sample.
  • The response mapping throws or returns no outcome. That is UNKNOWN with MALFORMED_REPLY, never FAILED. A refusal releases the customer's money hold, so the framework never guesses one.
  • You wrote a branch for status 500. It never runs. 5xx answers are UNKNOWN before mapping.
  • The YAML key loses its brackets. Spring Boot keeps a map key exactly as written only inside brackets. Without them it may change the key (for example lower-case it), and the operation PAY or the code 2001 is then not found. Write "[2001]" and "[PAY]", quotes included, as in the seed file.
  • == instead of =. JSONata compares with a single =. A syntax error is caught at config load, and the record is refused with the mapping's name (for example PAY.response), and the live version keeps serving.
  • A mapping leaks a personal value into a log. Mappings never log, but the raw bodies are audited. List personal fields under the record's sensitive-fields (for OCS: msisdn: MSISDN) so the audit masks them.
