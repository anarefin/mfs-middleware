Testcontainers: a real PostgreSQL and Kafka for every test run

Our integration tests do not mock the database or Kafka. Testcontainers starts a real PostgreSQL and a real Kafka in Docker when the tests need them, shares them across the whole test JVM, and throws them away at the end. Without Docker, those tests are skipped and the build still passes.

In plain English

In plain English

Think of a driving test on a real road, not in a simulator. Before the test, a fresh car is brought round; after it, the car is towed away. Testcontainers is the person who brings the car. Your test asks for "a PostgreSQL" and gets a real one, running in a container (a small isolated Linux process started by Docker from an image, for example postgres:18.6-alpine3.24).

Ryuk is a tiny helper container Testcontainers starts first. When the test JVM exits, even after a crash, Ryuk removes every container that run started, so nothing is left behind.

Why we use it here

Mocks of Kafka and SQL tell you that your code calls the mock the way you think. They cannot tell you that a Flyway migration is wrong, that a FOR UPDATE SKIP LOCKED query really skips, or that a record really lands on a retry topic. The spec's testing table (section 22) asks for integration tests with "Service with real infra; each module owns its fixtures (no shared test kit)".

ADR D19 sets the shape: "one PostgreSQL and one Kafka per test JVM (singletons in the module's TestInfrastructure), no reuse, removed by Ryuk when the JVM exits. Each Spring test context gets a fresh database", and "Without Docker the *IT and conformance classes are skipped (DockerAvailableCondition), not failed." One test task per module runs everything: unit, slice, contract, *IT and @Conformance tests in one JVM.

How it is wired

From services/mw-adapter-telco/build.gradle.kts. The versions come from the BOM, written inline (ADR D13):

testImplementation(platform("org.testcontainers:testcontainers-bom:2.0.5"))
...
testImplementation("org.testcontainers:testcontainers")
testImplementation("org.testcontainers:testcontainers-junit-jupiter")

testImplementation("org.testcontainers:testcontainers-kafka")
testImplementation("org.springframework.boot:spring-boot-testcontainers")

The same file limits how many modules test at once, because each test JVM starts its own containers:

val dockerTestSlots = gradle.sharedServices.registerIfAbsent("mwDockerTests", DockerTestSlots::class) {
    maxParallelUsages.set(providers.gradleProperty("mwDockerTests").map(String::toInt).orElse(4))
}

tasks.test {
    usesService(dockerTestSlots)
    useJUnitPlatform {
        if (!providers.gradleProperty("withSlow").isPresent) excludeTags("slow-wait")
    }
    maxHeapSize = "1g"
    ...

TestInfrastructure: one of each per JVM

A test that needs real infrastructure imports the module's TestInfrastructure. The containers are static fields, so there is one of each per JVM:

static final PostgreSQLContainer POSTGRES =
    new PostgreSQLContainer("postgres:18.6-alpine3.24")
        .withCommand("postgres", "-c", "fsync=off", "-c", "max_connections=600");

static final JvmScopedKafka KAFKA = new JvmScopedKafka("apache/kafka-native:4.3.2");

/** Starts both containers once (in parallel); later calls are no-ops. */
static synchronized void start() {
  if (!POSTGRES.isRunning() || !KAFKA.isRunning()) {
    Startables.deepStart(POSTGRES, KAFKA).join();
  }
}
  • Same versions as the stack. PostgreSQL 18 and Kafka 4.3.2. apache/kafka-native is Kafka built with GraalVM: the same broker, but it starts in about a second on little memory.
  • fsync=off makes PostgreSQL skip flushing to disk. Unsafe for real data, fine for a database that lives a few minutes.
  • Startables.deepStart starts both containers in parallel, the first time a Spring context asks for them.
  • No withReuse. Every run starts on new containers, so nothing needs cleaning between runs.

Spring caches test contexts, and several contexts share the one PostgreSQL. So each context gets its own empty database:

@Bean
DynamicPropertyRegistrar testInfrastructureProperties() {
  String url = createContextDatabase();
  return registry -> {
    registry.add("spring.datasource.url", () -> url);
    registry.add("spring.datasource.username", POSTGRES::getUsername);
    registry.add("spring.datasource.password", POSTGRES::getPassword);
    // No @ServiceConnection on the Kafka bean: wire Spring Kafka to it by hand.
    registry.add("spring.kafka.bootstrap-servers", KAFKA::getBootstrapServers);
  };
}

Flyway then migrates the empty ctx_<n>, and no context sees another's rows. Kafka is shared by all contexts: tests keep apart by their own topics, keys and consumer groups. Kafka's stop() is overridden to do nothing, because Spring would otherwise stop the shared container when the first context closes. PostgreSQL is deliberately not a bean at all, for the same reason.

To check what landed on a topic, tests use messaging/KafkaTestConsumer. It reads without a consumer group: it assigns the partitions, seeks to the beginning and polls. No group join means no waiting for a rebalance, and every read sees the whole topic.

Skipping without Docker

The rule (root CLAUDE.md): any test that needs Docker is named *IT. DockerAvailableCondition is a JUnit execution condition (a hook that can switch a test class off) that turns that rule into behaviour:

if (!outer.getSimpleName().endsWith("IT")) {
  return ConditionEvaluationResult.enabled("needs no Docker");
}
return DockerClientFactory.instance().isDockerAvailable()
    ? ConditionEvaluationResult.enabled("Docker is available")
    : ConditionEvaluationResult.disabled("Docker is not available: " + outer.getSimpleName() + " skipped");

No test class carries an annotation for it. JUnit loads it for every class through two small files:

# src/test/resources/junit-platform.properties
junit.jupiter.extensions.autodetection.enabled=true

# src/test/resources/META-INF/services/org.junit.jupiter.api.extension.Extension
mfs.mw.adapter.telco.DockerAvailableCondition

Worked example: TelcoRequestRouteIT

route/TelcoRequestRouteIT tests the whole top-up path of the telco adapter: a request on Kafka in, a reply on Kafka out, with a real database in between and WireMock (a small HTTP server that answers what you tell it to) playing the OCS. Its header:

@CamelSpringBootTest
@SpringBootTest(
    webEnvironment = SpringBootTest.WebEnvironment.NONE,
    properties = {
      "mw.telco.request-consumer.enabled=true",
      "mw.outbox.relay.enabled=true",
      "mw.outbox.relay.period=100ms",
      "mw.partners.instances.ocs.read-timeout-ms=4000",
      "mw.partners.instances.ocs.timeout-ms=1500",
      "resilience4j.circuitbreaker.instances.ocs.sliding-window-type=COUNT_BASED",
      "resilience4j.circuitbreaker.instances.ocs.sliding-window-size=4",
      ...
    })
@Import(TestInfrastructure.class)
@DirtiesContext
class TelcoRequestRouteIT {
  1. Setup. @Import(TestInfrastructure.class) brings the containers and the fresh database. The test switches on the request consumer and the outbox relay, which the test config keeps off for other tests. @DirtiesContext closes this context afterwards, so its running consumer does not compete with later tests.
  2. Fast failure settings. A 1.5 s time limit instead of 20 s, and a 4-call COUNT_BASED breaker window instead of 60 s and 50 calls, keep the timeout and circuit tests quick. @BeforeEach resets WireMock and the ocs breaker.
  3. Act. The test publishes a request with a fresh transaction id (its own Kafka key, so tests never read each other's replies).
  4. Assert. KafkaTestConsumer waits up to 30 s for the reply keyed by that id. Every reply is validated against contracts/events/mw-orchestrator/mw.partner.reply.v1.schema.json before the test checks FAILED and MW-PTR-GP-TOPUP_REJECTED.

Run just this class (Docker running), or the whole module:

./gradlew :mw-adapter-telco:test --tests '*TelcoRequestRouteIT'
./gradlew :mw-adapter-telco:test -PwithSlow     # also the two slow-wait tests in it
Where it lives
  • TestInfrastructure.java: the containers and the per-context database; its class comment explains every choice.
  • DockerAvailableCondition.java, junit-platform.properties, META-INF/services/...Extension.
  • messaging/KafkaTestConsumer.java, src/test/resources/config/application.yml (test-only settings).
  • route/TelcoRequestRouteIT.java: the worked example.
  • Every other module has its own copies, for example services/mw-orchestrator/src/test/java/mfs/mw/orchestrator/TestInfrastructure.java.

What can go wrong

What can go wrong
  • All your *IT tests show as skipped. Docker is not running, or Testcontainers cannot reach it. The skip reason says Docker is not available. A gate run needs Docker.
  • A test needs Docker but is not called *IT. It is not skipped, so it fails on a host without Docker. Rename it.
  • A test reads another test's records. Kafka is shared by the whole JVM. Use your own topic, a fresh key (a new transaction id) or a filter in KafkaTestConsumer.read.
  • A cached context steals your records. A consumer left running in another cached context can take messages from the topic you test. That is why the test config switches off mw.telco.request-consumer.enabled and the outbox relay; switch them on only in the test that needs them, with @DirtiesContext.
  • You added withReuse(true) to go faster. Don't: reused containers keep data between runs and need clean-up scripts. D19 removed exactly that.
  • A test is slow because it waits. If the wait is the point of the test (a timeout, a retry delay, an absence window) and takes 2 s or more, tag it @Tag("slow-wait"). Otherwise shorten the configured timer for the test, as TelcoRequestRouteIT does.
  • Field injection in a test. Not even in tests: inject through the constructor, as TelcoRequestRouteIT does. ./gradlew :checkFieldInjection fails otherwise.
