Apache Camel: the plumbing between Kafka, services and partners

Camel runs inside every Spring Boot service that talks to Kafka. It reads records, hands them to a Spring bean, parks failures on retry topics and publishes our outbox. In the three adapters it also runs the route templates that every partner call goes through.

In plain English

In plain English

Think of a post office sorting room. Letters come in through one door. Each one goes along a fixed path of conveyor belts: it is stamped, checked and dropped into the right bag. Apache Camel is that sorting room for messages. You describe the belts once, in Java, and Camel moves every message along them.

A route is one such path: "take messages from here, do these steps, send them to there". An endpoint is one end of a route, written as a URI such as kafka:mw.partner.request.telco.v1 or direct:partner-ocs. A component is the plug-in that knows how to talk to one kind of endpoint (the Kafka component, the timer component, and so on).

A few Camel words you will see everywhere:

WordMeaningExample here
RouteA path from one endpoint through some steps to others.The consumer of mw.partner.request.telco.v1
RouteBuilderA Java class whose configure() method defines routes. A Spring @Component of this type is picked up by Camel at start.route/TelcoRequestRouteBuilder
ExchangeOne message on its way through a route, with headers and a body.One Kafka record
Endpoint URIWhere a route reads from or writes to.kafka:..., bean:telcoRequestHandler?method=handle, timer:outbox-relay
direct:An in-memory endpoint. Calling it runs the route on the caller's own thread, like a method call.direct:partner-ocs
Route templateA route with blanks (parameters). Fill in the blanks and you get a new real route.rest-json-request-reply, parameter partner
ProducerTemplateA Camel helper that lets plain Java code send a message into an endpoint and wait for the answer.PartnerGateway

Why we use it here

The decision record D1 picks Camel 4 inside every Boot app: "Partner and messaging integration uses Apache Camel 4 (Java and YAML route DSL, no XML DSL) inside the Spring Boot app." Its main payoff is in the adapters: "Camel route templates turn partner onboarding into mostly configuration."

Spec section 12 (the adapter framework) builds on that. A partner of a known kind is a route template plus parameters; a template becomes a live route at runtime through Camel's TemplatedRouteBuilder. So adding a fifth telco is a configuration change, not a new class.

A DSL (domain-specific language) here just means the way you write routes. We write them in the Java DSL (method chains like from(...).to(...)). D1 also allows the YAML DSL, but the repo has no *.camel.yaml files today: every route, templates included, is Java. Virtual threads are on (spring.threads.virtual.enabled), so a blocking partner call does not need a reactive stack.

How it is wired

Every module writes its versions inline in its own build.gradle.kts (ADRs D13 and D14). From services/mw-adapter-telco/build.gradle.kts:

implementation(platform("org.apache.camel.springboot:camel-spring-boot-bom:4.22.2"))
...
// Kafka through Camel (spec 6.1, 19.2): idempotent producer, retry topics, DLQ.
implementation("org.apache.camel.springboot:camel-spring-boot-starter")
implementation("org.apache.camel.springboot:camel-kafka-starter")
...
testImplementation("org.apache.camel:camel-test-spring-junit6")

The Kafka settings live under camel.component.kafka in each service's application.yml (from the telco adapter's):

camel:
  component:
    kafka:
      brokers: ${KAFKA_BOOTSTRAP_SERVERS:kafka:9092}
      # Producer: exactly one copy per send, every in-sync replica acknowledges (6.1).
      request-required-acks: all
      enable-idempotence: true
      max-in-flight-request: 5
      group-id: ${spring.application.name}
      auto-offset-reset: earliest
      break-on-first-error: true
      auto-commit-enable: false
      allow-manual-commit: true
KeyWhat it means
request-required-acks: all, enable-idempotence: trueThe producer waits until every in-sync broker has the record, and Kafka drops a duplicate if the producer resends.
group-idOne consumer group per service: the service name.
auto-commit-enable: false, allow-manual-commit: trueOffsets are never committed on a timer. A route commits each record itself, only after it is handled or parked.
break-on-first-error: trueIf even parking a record fails, the partition stops instead of skipping past it.

The partner framework is not a library. It is written once in mw-adapter-telco and copied into the other two adapters (spec 12, D14). The copies stay identical apart from the package name.

Kafka consumers with retry topics

Every Kafka consumer in the repo is a small subclass of RetryTopicRouteBuilder. The subclass says only which topic to read and which bean handles a record. Here is the whole telco one:

@Component
@ConditionalOnProperty(name = "mw.telco.request-consumer.enabled", havingValue = "true", matchIfMissing = true)
public class TelcoRequestRouteBuilder extends RetryTopicRouteBuilder {

  public static final String TOPIC = "mw.partner.request.telco.v1";
  ...
  @Override
  protected String handlerUri() {
    return "bean:telcoRequestHandler?method=handle";
  }
}

The base class builds the routes. The main route, shortened:

from("kafka:" + topic())
    .routeId(topic() + ".consume")
    .onException(Exception.class)
    .handled(true)
    .useOriginalMessage()
    .process(e -> park(e, 1))
    .to("kafka:" + nextTopic(group, 1))
    .process(RetryTopicRouteBuilder::commit)
    .end()
    .to(handlerUri())
    .process(RetryTopicRouteBuilder::commit);

Read it top to bottom:

  • Happy path: the record goes to the handler bean, then the offset is committed.
  • The handler throws: onException catches it, takes the original record (same key, body and headers), stamps a few mw-* headers (attempt, original topic, error class, not-before time) and sends it to <topic>.<group>.retry.1. Then it commits. The source partition is never blocked by one bad record.
  • Retry topics: one more route per delay reads retry.1, retry.2, retry.3. If the record fails again it moves on; after the last one it lands on <topic>.<group>.dlq (the dead-letter queue). The delays are mw.kafka.retry.delays: 10s,1m,10m (spec 19.2).
  • No sleeping: a retry consumer that gets a record too early pauses the partition (messaging/RetryDelayListener) and checks again every 500 ms. It never calls sleep on the consumer thread.

The topic names carry the consumer group (the service name), so two services that read the same topic never re-read each other's parked records. The retry and DLQ topics are declared in deploy/kafka/topics.txt with retry=<group>, for example mw.partner.request.telco.v1 24 3d retry=mw-adapter-telco.

The commit uses the header Camel puts on every record when manual commit is on (KafkaConstants.MANUAL_COMMIT, value CamelKafkaManualCommit):

KafkaManualCommit commit =
    exchange.getMessage().getHeader(KafkaConstants.MANUAL_COMMIT, KafkaManualCommit.class);
if (commit == null) {
  throw new IllegalStateException("Kafka manual commit is not enabled for this consumer");
}
commit.commit();

The outbox relay is a Camel route too, but on a timer, not Kafka (see the outbox idea):

from("timer:outbox-relay?delay=0&period=" + properties.period().toMillis())
    .routeId("outbox.relay")
    .autoStartup(properties.enabled())
    .process(e -> relay.relayPending());

Route templates for partners

In the adapters, every partner instance (for example ocs, the telco's Online Charging System) gets its own Camel route, made from a template. partner/template/PartnerRouteTemplates defines the two templates the adapters ship today:

for (String template : new String[] {PartnerTemplates.REQUEST_REPLY, PartnerTemplates.ASYNC_CALLBACK}) {
  routeTemplate(template)
      .templateParameter(PARAM, null, "partner instance id")
      .from("direct:partner-{{" + PARAM + "}}")
      .setHeader(INSTANCE_HEADER, constant("{{" + PARAM + "}}"))
      .choice()
      .when(body().isInstanceOf(InboundCall.class))
      .process(this::inbound)
      .otherwise()
      .process(this::outbound)
      .end();
}

REQUEST_REPLY is rest-json-request-reply (one HTTP request, the answer in the reply). ASYNC_CALLBACK is rest-json-async-callback (the partner says PENDING first and calls us back later). The only parameter is partner, the instance id. {{partner}} is Camel's placeholder syntax, so the template for ocs becomes a route that starts at direct:partner-ocs.

Who fills in the blanks? PartnerRouteRegistrar keeps one route per partner in step with the partner config:

TemplatedRouteBuilder.builder(camel, template)
    .routeId(PartnerTemplates.routeId(id))
    .parameter(PartnerRouteTemplates.PARAM, id)
    .add();
  • A new partner appears: a route is added. Its template changes: the route is removed and added again. It is deleted: the route goes.
  • The first sync() runs once Camel has started (a CamelContextConfiguration in partner/PartnerFrameworkConfiguration), because the templates must exist first.
  • After that, a mw.config.changed.v1 record triggers it. partner/config/PartnerConfigRouteBuilder reads that topic from the beginning with a fresh consumer group on every start, so the config rebuilds itself without a restart (hot reload).
  • URL, timeouts, auth and mappings are read from the config at call time, so only a template change recreates the route.

Service code never builds an endpoint URI by hand. It calls PartnerGateway, which uses a ProducerTemplate:

return producer.requestBody(PartnerTemplates.endpoint(instance), call, PartnerResponse.class);

requestBody blocks until the route answers. That is fine on a virtual thread, and never allowed on a Kafka consumer thread (root CLAUDE.md, "Never block on Kafka listener threads").

Worked example: an airtime top-up

The orchestrator asks the telco adapter to top up a phone. Here is the Camel side of it, from Kafka record to Kafka reply:

  1. The orchestrator publishes a request on mw.partner.request.telco.v1, keyed by the transaction id.
  2. The route built by TelcoRequestRouteBuilder reads it and calls bean:telcoRequestHandler?method=handle.
  3. messaging/TelcoRequestHandler only parses the record and hands it to the telcoCallExecutor (a virtual-thread executor). The route then commits the offset. The OCS call (up to 20 s) never runs on the Kafka thread. A record that cannot be parsed throws, so the route parks it on retry.1.
  4. service/TopupService checks the request, gets the stable partner reference for this transaction and calls PartnerGateway.call. The partner id (say gp) has no config of its own, so default-partner: ocs serves it.
  5. PartnerGateway sends the call into direct:partner-ocs. The templated route runs PartnerCallWrapper (bulkhead, circuit breaker, time limiter: see Resilience4j), which runs RestJsonAdapter: a JSONata mapping builds the body, the HTTP POST goes out, another mapping reads the answer.
  6. Back in TopupService, the reply is written to the outbox together with the inbox record of the request, in one database transaction. A redelivered request is then answered only once.
  7. The outbox.relay timer route publishes the reply on mw.partner.reply.v1.

The test route/TelcoRequestRouteIT plays exactly this with a real Kafka and PostgreSQL and WireMock as the OCS (see Testcontainers).

What can go wrong

What can go wrong
  • Your route commits nothing and re-reads the same records after a restart. Auto-commit is off. A new Kafka route must commit through the CamelKafkaManualCommit header, or simply extend RetryTopicRouteBuilder, which does it for you.
  • You set spring.kafka.bootstrap-servers and Camel ignores it. Camel's Kafka component does not read spring.kafka.*. Use camel.component.kafka.brokers (tests set it in TestInfrastructure).
  • A slow call in a handler stalls a whole partition. The handler runs on the Kafka consumer thread. Hand long work to an executor as TelcoRequestHandler does. Never call PartnerGateway or Thread.sleep there.
  • A call during a template change comes back as not sent. While a route is being recreated, direct:partner-<id> has no consumer and Camel throws DirectConsumerNotAvailableException. PartnerGateway turns it into NOT_SENT (reason DISABLED), which is safe because nothing left the building.
  • Records pile up on a DLQ. After three failed retries a record lands on <topic>.<group>.dlq. The log event kafka.dlq.parked names the topic, attempt and error class (never the payload).
  • You wrote a route in XML. D1 rules out the XML DSL. Use the Java DSL like the rest of the repo.
