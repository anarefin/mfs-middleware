Apache Camel: partner routes, and nothing else

Camel runs only in the three partner adapters (mw-adapter-telco, -billpay, -bank), and there only to run the partner routes: one small Camel YAML DSL route per partner, built from a reviewed library of mw-* Kamelets, that turns our canonical partner call into the partner's HTTP, SOAP or SFTP traffic and back. Kafka does not go through Camel anywhere: every module, the adapters included, reads and writes Kafka with Spring Kafka.

Where Camel is, and where it is not

ConcernLibraryWhere
Kafka consumers, retry topics, DLQSpring Kafka (ADR D27) @KafkaListeners in messaging/ (and partner/config/PartnerConfigKafkaListener in the adapters), retry topics <topic>.<group>.retry.1..3 then .dlq from config/KafkaConfig
Kafka producer, outbox relaySpring Kafka messaging/EventPublisher (KafkaTemplate), scheduler/OutboxRelayScheduler (ShedLock)
A call to a partner, an SFTP batch fileCamel (ADR D28) the partner route of that partner, run by partner/route/PartnerRoutes in each adapter

./gradlew :checkIsolation fails a build when any module other than mw-adapter-* declares a Camel dependency or imports org.apache.camel (ADR D1, as amended). The XML DSL is never used; routes are YAML, the adapters' own Java steps live in partner/kamelet/.

The words you need

WordWhat it isIn this repo

KameletA reusable route snippet with typed parameters, called as kamelet:<name>?param=....src/main/resources/kamelets/mw-*.kamelet.yaml
Partner recordThe route plus its JSONata mappings, allowed hosts, error map and timeouts, approved by maker-checker.mw.config.changed.v1, value PartnerConfig
ExchangeOne call on its way through a route, with headers and a body.One partner call (PartnerCall JSON)

The route contract

  • In: from: direct:partner-<id>; the body is the canonical call (partnerId, operation, txnId, reference, input), the headers mwOperation (PAY, INQUIRY, STATUS_QUERY), mwReference, mwCorrelationId, mwPartnerId, mwTxnId, mwPartnerCode. No mw* header ever leaves the service.
  • Branch per biller: mwPartnerCode is the call's billerCode (else its productCode), so one partner can serve some billers over another protocol: the dev billagg route sends KGDCL, JGTDSL, BTCL and LINK3 over SOAP with simple: "${header.mwOperation} == 'PAY' && ${header.mwPartnerCode} in 'KGDCL,JGTDSL,BTCL,LINK3'" before its REST whens.
  • Out: {outcome, partnerRef, code, message, reason} (plus errorSuffix, retryable, attributes), produced and checked by mw-classify. A missing or invalid output is UNKNOWN: fail closed.
  • The route ends with mw-classify (directly, or at the end of every branch of a final choice) and then mw-audit.
  • A batch route starts from kamelet:mw-sftp-source?... instead and ends with mw-recon: it takes no calls, has no dry-run and polls only while the record is enabled.

The Kamelet library

KameletWhat it does
mw-mapThe request body from the canonical call, by a named JSONata mapping of the record (JSONata).
mw-http-callOne call to url + path, signed by mw-auth-<auth>, inside the partner's circuit breaker, time limit and bulkhead (Resilience4j). A PAY is never sent twice; an INQUIRY / STATUS_QUERY at most inquiryRetries times.
mw-soap-callThe SOAP case: XSLT request and response stylesheets, SOAP 1.1 / 1.2, optional WS-Security.
mw-auth-none, -apikey, -hmac-sha256, -basic, -oauth2-cc, -jws The auth schemes. A secret is a field name of the partner's own Vault secret secret/<adapter>/<partnerId>, never a value in the route.
mw-classifyThe partner's answer to the route output, with fail-closed rules no mapping can override.
mw-auditThe masked audit record (mw.audit.event.v1).
mw-sftp-source, mw-sftp-sink, mw-reconBatch files over SFTP: strict host keys, each file once, never deleted; every line becomes mw.partner.recon.v1 through the outbox, a file all or nothing.

A breaking change to a Kamelet ships under a new name (mw-http-call-v2); the old one stays until no LIVE route uses it. The full parameter list per auth scheme is in camel-partner-routes.md.

The guardrails

  1. Maker-checker in mw-admin-api: a record goes out only once a second person approves it. mw-admin-api checks the route at submit with a copy of the loader's rules (MW-VAL-041, with line and construct).
  2. The allowlist on the parsed model (partner/route/PartnerRouteLoader): one route; only choice/when/otherwise, to: kamelet:mw-*, setHeader (not Camel*/mw*), setBody, transform, log (no body), JSON marshal/unmarshal; no property placeholders, error handlers, beans, processors or raw endpoints.
  3. A dry-run before LIVE (partner/route/PartnerDryRun): the approved version is loaded beside the live one as a candidate and its dryRun sample must answer SUCCESS or PENDING against mw-simulators (or the record's sandbox). Pass: swapped in, reported LIVE on mw.partner.route.status.v1. Fail: removed, the live version keeps serving, REJECTED with the problems; mw-admin-api republishes the last LIVE version.
  4. The approved hosts: checked when the route loads and again before every send (PartnerHostGuard, a checked DNS resolver).

What can go wrong

What can go wrong
  • The route is refused with MW-VAL-041. It uses something outside the allowlist (a raw http: endpoint, a bean, a {{...}} placeholder) or does not end with mw-classify then mw-audit. The details name the line and the construct.
  • The version stays "waiting for its dry-run" or turns REJECTED. The partner page lists the problems (for example HTTP_5XX from the simulator); the adapter's log has the rest. The last LIVE version keeps serving.
  • A call is refused for its host. The url (or an OAuth2 tokenUrl) host is not in the record's allowedHosts, or resolves to a refused address.
  • You added Camel to another module. :checkIsolation fails. Kafka work belongs in Spring Kafka (@KafkaListener, KafkaTemplate), copied from templates/mw-service-template.
  • Records pile up on a DLQ. After three failed retries a record lands on <topic>.<group>.dlq; validation and JSON failures go there at once. The log event names the topic, attempt and error class, never the payload.
