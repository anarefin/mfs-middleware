APISIX and etcd: the front door

Every request from outside, whether from an app, a USSD gateway, a shop or the ops console, enters through one gateway: Apache APISIX on port 443. It turns away bad requests before any Spring service sees them. Its configuration lives in etcd, and we fill etcd from JSON files in Git.

In plain English

In plain English

Think of the security desk in an office lobby. Visitors don't walk straight to the desks: the guard checks their badge, turns away anyone carrying something too big, counts how often each person comes in, and gives everyone a visitor number that follows them through the building. APISIX is that guard. It is an API gateway: a reverse proxy (built on nginx) that runs a chain of plugins on each request before passing it on.

etcd is a small key-value database. APISIX keeps its routes and plugin settings there instead of in a config file, so they can change without a restart.

A few APISIX words you will see everywhere:

WordMeaningExample here
Route"Requests for this path go to that service, after these plugins."app-v1: /app/v1/* → mw-app-gateway:8080
PluginOne check or change applied to a request or response.openid-connect (check a token), limit-count (rate limit)
Global rulePlugins that run on every route, even for unknown paths.edge: correlation id, header stripping, error envelope
ConsumerA known caller with credentials.ussd_gp: the Grameenphone USSD gateway's basic-auth login
UpstreamThe service a route forwards to.mw-app-gateway:8080
Admin APIAPISIX's own REST API for creating routes etc. (port 9180, never published).apply.sh PUTs every JSON file through it

Why we use it here

The decision record D3 puts it in one line: "Authentication, quotas, size caps, TLS and a uniform error envelope should be enforced once, before any service." If each of fifteen services did its own token check and rate limit, sooner or later one would get it wrong. With one gateway there is one place to audit, and scripts/edge-test.sh proves the rules on a running stack.

What APISIX does not do is just as important:

  • It does not check request body shapes. Each service validates its own body against its contract. On the app route the device signs the raw request bytes, and APISIX's request-validation plugin re-encodes the JSON, which would break the signature. So body schemas stay in the services (M3 gate decision).
  • It is not the only token check. Services verify the token again (defence in depth). The gateway is the first lock, not the last.
  • It does not verify partner callback signatures. Each partner signs differently, so the adapters check those. APISIX keeps IP allow-lists, size caps and quotas.

How it is wired

The edge is five containers in deploy/docker-compose.yml. None has a profile, so they start with every stack:

ContainerKindWhat it does
etcdlong-runningStores APISIX's configuration. Sits alone on the internal etcd network with APISIX; port 2379 is never published.
etcd-initone-shotTurns on etcd login (deploy/etcd/init-auth.sh): a root user, an apisix user that may only touch the /apisix prefix, and a healthcheck user that can read nothing.
apisixlong-runningThe gateway. Host port 443 (knob MW_HTTPS_PORT) maps to 9443 inside. Static settings in deploy/apisix/config.yaml.
apisix-initone-shotRuns deploy/apisix/apply.sh on every up: PUTs the certificate, global rules, consumers and routes into APISIX, deletes retired ones. Services such as mw-app-gateway wait for it to finish.
apisix-init-testerone-shot, profile testerThe same script again with MW_E2E_ROUTES=1, which adds the test-only routes under /test/* and /tester.

Configuration as code

Nobody clicks routes together in a dashboard. Everything is a file under deploy/apisix/:

deploy/apisix/
  config.yaml            listeners, etcd login, Admin API (loopback only), masked access log
  apply.sh               the one-shot: PUT everything below through the Admin API
  global_rules/edge.json plugins on every request
  routes/<id>.json       one public route per file
  vault/edge.json        secret manager: APISIX reads credentials from the Vault KV v1 mount apisix/
  consumers/<name>.json  known callers (the four MNO USSD gateways), until the client registry owns them
  lua/*.lua              small Lua functions the JSON pulls in with "@lua:lua/<file>"
  retired.txt            routes whose file was deleted: apply.sh deletes them from etcd too
  routes-test/           TEST ONLY routes (core mock, simulators, mail, ...)
  consumers-test/        TEST ONLY consumers of those routes

apply.sh fills three kinds of placeholder before each PUT, so no secret is ever in the JSON:

  • "@lua:lua/edge-request.lua" becomes the file's text (a serverless function).
  • "@env:NAME" becomes an environment variable, for example a USSD gateway password from deploy/.env.
  • "@list:NAME" becomes a comma-separated variable as a JSON array, for example an MNO's allowed source addresses.

An unset variable fails the apply on purpose: a missing allow-list stops the stack instead of opening the route. Every object has a fixed id and is PUT whole, so running the script twice leaves the same configuration (it is idempotent). The README explains why we chose plain Admin API JSON over APISIX's ADC YAML tool.

The global rule: what every request gets

deploy/apisix/global_rules/edge.json runs on every request, including 404s for unknown paths:

  • Strip X-Mw-* headers. Headers starting with X-Mw- carry facts the middleware vouches for, such as the merchant id after HMAC. If a caller could send X-Mw-Merchant-Id themselves, they could pretend to be any shop. lua/edge-request.lua removes every such header before any route plugin runs.
  • Correlation id. The request-id plugin sets X-Correlation-Id (a fresh UUID when absent), forwards it and returns it. Every log line in every service carries it, so one id finds the whole story. The same Lua drops a caller's id if it is over 128 characters or contains a run of six or more digits. The id is logged unmasked, so it must not be able to smuggle in a phone or NID number.
  • One error format. When APISIX itself refuses a request, lua/edge-error-headers.lua and lua/edge-error-body.lua rewrite its answer into the same envelope the services use, for example 401 {"code":"MW-AUTH-001", ...}, 413 MW-VAL-BODY_TOO_LARGE, 429 MW-SYS-RATE_LIMITED, 404 MW-VAL-003.
  • Security headers (HSTS, nosniff) and a masked access log (config.yaml masks MSISDNs and drops query strings).

Rate limits live in Redis

The limit-count plugin keeps its counters in Redis (the redis container), so the count is shared if there is ever more than one APISIX. The password is read as $env://REDIS_PASSWORD, so it is never stored in etcd. Every limiter has allow_degradation: true: if Redis is down, requests pass uncounted rather than all failing, and APISIX logs mw.edge.rate_limit_degraded so someone notices.

Worked example: an app payment

A customer taps Send money. The app sends POST https://localhost/app/v1/transactions with a bearer token and a device-signed body. Here is what deploy/apisix/routes/app-v1.json does with it, in plugin order:

  1. Global rule. Any X-Mw-* header the app sent is removed. A bad X-Correlation-Id is dropped and a fresh UUID is set.
  2. client-control refuses a body over 64 KiB with 413 MW-VAL-BODY_TOO_LARGE.
  3. openid-connect (bearer only) reads mw-auth's discovery document at http://mw-auth:8080/auth/v1/.well-known/openid-configuration, fetches the public keys (JWKS), and checks the token's signature, issuer, audience mw-app and expiry (with only 10 s of clock slack). No token, a forged one or an expired one gives 401 MW-AUTH-001. If mw-auth rotates its signing key, the unknown key id makes APISIX fetch the JWKS again, so new tokens work at once.
  4. consumer-from-jwt.lua reads the now-trusted sub claim and sets the variable mw_consumer = sub:<sub>.
  5. limit-count adds one to that consumer's counter in Redis. Request 121 within a minute gets 429 MW-SYS-RATE_LIMITED (retryable).
  6. The request goes to mw-app-gateway:8080 unchanged, byte for byte, so the device signature still verifies there.

A USSD request takes a different path through the same idea: ip-restriction (is this the MNO's address?), basic-auth (is the password right?), consumer-restriction (is it this MNO's consumer?), then a limit keyed on a hash of the phone number, never the number itself.

The channel client registry (ticket 100a). Who may call the edge is a table in mw-admin-api (admin.channel_client: client id, type, auth method, allowed routes, IP allow-list, rate, daily quota), changed only through maker-checker (/admin/v1/channel-clients). APISIX is a projection of it: once an approval commits, mw-admin-api PUTs the client's consumer (for a BASIC client such as ussd-gp: consumer ussd_gp, basic-auth password $secret://vault/edge/ussd-gp/password, so the password is fetched from Vault and never stored in etcd) and a consumer group client_ussd_gp with limit-req, limit-count and ip-restriction. A job re-applies the whole registry every 5 minutes and removes consumers it labelled but no longer has. Worked example: an integration maker files {"type":"MNO","authMethod":"BASIC","allowedRoutes":["ussd-http-gp"],"ratePerSec":40,...}, an ops checker approves, and a GET of /apisix/admin/consumers/ussd_gp shows the label managed-by: mw-admin-api; from then on apply.sh leaves that consumer alone. Details: deploy/apisix/README.md "Channel client registry".

Where it lives
  • deploy/apisix/README.md: the full route-by-route reference, error code table and every policy. Read this next.
  • deploy/apisix/apply.sh: the one-shot that loads it all; its header explains the placeholders.
  • routes/app-v1.json, global_rules/edge.json, lua/edge-request.lua, lua/consumer-from-jwt.lua.
  • deploy/apisix/config.yaml (static settings), deploy/etcd/init-auth.sh (etcd users).
  • Tests: scripts/test/test_apisix_edge.sh (offline: the JSON and Lua, in ./gradlew :scriptTests) and scripts/edge-test.sh (live: real 401/400/413/429 answers on the running stack).

What can go wrong

What can go wrong
  • You renamed or deleted a route file, and the old route still answers. apply.sh only PUTs; it never deletes what it does not know about. Add the old id to deploy/apisix/retired.txt (for example routes/ussd-http) and it is removed on the next up.
  • 404 MW-VAL-003 or 502 right after you rebuilt one service. Recreating a single container gives it a new IP address, and APISIX still sends to the old one. Run docker compose restart apisix from deploy/. A full start does not hit this.
  • /test/... answers 404. The test-only routes exist only when the stack was started with --profile tester (or after scripts/tester.sh / scripts/api-test.sh, which re-run the one-shot with MW_E2E_ROUTES=1). A later up without the profile removes them again, on purpose.
  • apisix-init exits non-zero. Usually a missing variable, for example a USSD_GP_ALLOWED_CIDRS. Run docker compose logs apisix-init; the fix is usually cp dev.env.defaults .env.
  • The console login breaks on another port. Keycloak's browser login is pinned to the public host on 443, so MW_HTTPS_PORT=8443 breaks it.
  • A direct port skips everything on this page. The dev stack also publishes each service on 127.0.0.1 (8081 and up) for debugging. A call there has no token check, no rate limit and no header stripping. Test edge behaviour through 443 only.
  • Adding a plugin that rewrites the body to app-v1 breaks every app payment, because the device signature covers the raw bytes. The offline test refuses it.
