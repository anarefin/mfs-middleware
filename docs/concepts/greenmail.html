Test double

GreenMail: a mail server that keeps everything

When a bill payment succeeds, the customer gets an email receipt. In the dev stack that email must not reach a real inbox, but a tester still wants to read it. GreenMail is a small mail server that accepts every message and keeps it, so tests and people can look.

In plain English

In plain English

Imagine a post office that never delivers anything. It takes every letter, sorts it into a pigeonhole by the address on it, and lets anyone with a key to the back room read the pigeonholes. That is GreenMail.

A test double is a stand-in for a real system that behaves the same from the outside. Our code talks to GreenMail exactly as it would talk to a real mail server, over SMTP (the protocol for sending email). The difference is only on the far side: nothing leaves, and every mailbox can be read through a small REST API.

WordMeaning
SMTPSimple Mail Transfer Protocol: how a program hands an email to a mail server. GreenMail listens for it on port 3025.
STARTTLSAn SMTP command that switches the connection to TLS. A real mail server needs it; GreenMail does not offer it.
MailboxGreenMail makes one on the fly for every address it receives mail for. No setup needed.

Why we use it here

Spec section 22.2 lists the test doubles the stack needs, and one of them is "SMTP (GreenMail)". ADR M7 puts it among the MVP platform pieces: "notifications (SMS over SMPP to the SMSC simulator, email over SMTP to GreenMail)". The reasons are simple:

  • Real code path. mw-notify uses Spring's normal JavaMailSender. Swapping GreenMail for a real provider is a host name and port, not a code change.
  • Nothing escapes. The seeded test addresses end in example.test, and even those never leave the laptop.
  • Tests can assert on mail. The Newman suite checks that each flow sends exactly one receipt with the right subject.

How it is wired

ContainerPortsNotes
greenmail3025 SMTP (127.0.0.1:3025); 8080 REST API, published as 127.0.0.1:8025No profile, so it starts with every stack. Image greenmail/standalone, pinned by digest. Started with -Dgreenmail.setup.test.all (the standard test ports) and -Dgreenmail.auth.disabled (no SMTP login). Mail is held in memory only.

Only one service sends email: mw-notify. Its block in deploy/docker-compose.yml points it at GreenMail:

SMTP_HOST: greenmail
SMTP_PORT: 3025
SMTP_STARTTLS_REQUIRED: false    # DEV ONLY: GreenMail offers no STARTTLS
MW_NOTIFY_FLYWAY_LOCATIONS: classpath:db/migration,classpath:db/dev
  • STARTTLS. mw-notify's own default requires STARTTLS and checks the server's identity. Only the compose override turns it off for GreenMail. Production keeps the safe default.
  • Who gets mail. An email rule needs the party's address in mw-notify's contact table. In dev the extra Flyway folder db/dev fills it (R__dev_contacts.sql): for example 01711000001 is customer01@example.test. A party with no address is skipped.
  • Which flows email. Today a successful BILL_PAY or ADD_MONEY_BANK sends an email receipt to the initiator. Everything else is SMS only.

Reading the mail

Three ways, from friendliest to rawest:

  1. Test console. https://localhost/tester, page SMS & email: type a number and press Read. It shows the SMS the SMSC simulator got and the email GreenMail holds for that wallet's address (testing guide section 6).
  2. Through the edge. The test-only APISIX route /test/mail/* (deploy/apisix/routes-test/test-mail.json) forwards GET requests to GreenMail's /api/*. It needs the test API key in an apikey header (scripts/creds.sh prints it) and exists only when the test-only routes are on (see APISIX). The Newman suite and the test console both read mail this way.
  3. The direct dev port. curl http://127.0.0.1:8025/api/user/customer01@example.test/messages/ lists that mailbox as JSON. No key; loopback only.

Worked example: a bill-pay receipt

Customer 01711000001 pays a DESCO electricity bill. When the transaction is COMPLETED, a receipt goes out:

  1. The orchestrator publishes the final status of the transaction on Kafka.
  2. mw-notify matches its rules. BILL_PAY success has an EMAIL rule for the initiator, and the dev contact table has an address for 01711000001.
  3. It renders the email template TXN_BILL_PAY_SUCCESS in the customer's language: a subject, a text part and an HTML part.
  4. client/SmtpEmailSender sends one multipart message to greenmail:3025.
  5. GreenMail accepts it and drops it into the mailbox for that address. mw-notify records the message as SENT.
  6. A tester (or the Newman helper in tests/api/lib.js) asks the edge for that mailbox.
  7. APISIX checks the key, rewrites /test/mail/ to /api/, and forwards to GreenMail.
  8. The list comes back. The suite polls until exactly one message with the expected subject is there.
Where it lives
  • deploy/docker-compose.yml: the greenmail block and mw-notify's SMTP_* settings.
  • services/mw-notify/CLAUDE.md ("Email"); the sender client/SmtpEmailSender; the dev addresses db/dev/R__dev_contacts.sql; the receipt templates V7__seed_flow_notifications.sql.
  • The edge route deploy/apisix/routes-test/test-mail.json.
  • Readers: tests/api/lib.js (sim.mail), the test console's src/lib/server/test-apis.ts and src/app/inbox/page.tsx.
  • Tests without the stack: service/EmailFlowIT runs an in-process GreenMail; config/MailTlsDefaultsTest proves STARTTLS is on by default.

What can go wrong

What can go wrong
  • mw-notify against a real server fails, or against GreenMail fails after you removed the override. The service requires STARTTLS by default. GreenMail has none, so only SMTP_STARTTLS_REQUIRED: false in compose lets it send. Never carry that override to a real environment.
  • No email arrives. Check the flow sends one at all (only BILL_PAY and ADD_MONEY_BANK success do), and that the party has an address in contact. A new test wallet without a row there gets SMS only.
  • The mailbox is empty after a restart. GreenMail keeps mail in memory. Restarting the container clears every mailbox.
  • A test sees two receipts. Many API-suite customers share customer01@example.test, so filter by subject or TrxID, as the suite does.
  • "Sent" does not mean delivered. mw-notify has no bounce handling yet: SENT is final once the server accepts the message.
  • /test/mail/... answers 404. The test-only routes are off. Start with --profile tester or run scripts/tester.sh.
