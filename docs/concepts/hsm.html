Keys

SoftHSM, payShield and mw-crypto: where the keys live

The keys that check a PIN or sign a payment approval must never sit in a config file or in a service's memory. They live in an HSM, a locked box that does the maths for you and never hands the key out. In dev we fake that box with SoftHSM and a payShield simulator, and exactly one service, mw-crypto, is allowed to talk to it.

In plain English

In plain English

Think of a notary with a seal. You never borrow the seal. You hand your document through a window, the notary stamps it inside the office and hands it back. Anyone can check the stamp, but nobody outside ever holds the seal.

An HSM (hardware security module) is that office. It is a tamper-resistant device that creates keys, keeps them inside, and runs the crypto operations (sign, decrypt, HMAC) itself. Programs send it data and get results back. The key itself never comes out.

A real HSM costs real money and the production vendor is not chosen yet. So the dev stack uses two stand-ins: SoftHSM (a software HSM that speaks the standard HSM API) and a payShield simulator (a fake of the Thales payment HSM that banks use for card PINs).

Why we use it here

The middleware owns the wallet PIN (ADR D20): "The PIN is stored as HMAC-SHA256 under a PIN key held in the HSM, over walletId and PIN [...] No reversible PIN value is stored anywhere." An HMAC is a keyed hash: without the key you cannot even test guesses against it, so a stolen database is worthless. That only holds if the key is somewhere nobody can copy it.

ADR D23 then decides who talks to the HSM: "One service, mw-crypto, holds the HSM sessions; everyone else calls its internal API by keyId (mTLS only, D24) and never holds key material." One HSM client means one place with HSM credentials and vendor code. A new production vendor is a new provider class behind the same interface, with no change to any caller.

The same ADR names the price: if mw-crypto is down, "PIN checks, logins, assertions and signing fail closed". Nobody can pay, but nobody can pay without a PIN either. The business side (logins, lockout, the assertion) is in tutorial chapter 10. This page is about the mechanics underneath.

How it is wired

All of these run in profiles minimal and core of deploy/docker-compose.yml:

ContainerPortsWhat it does
softhsm5657 (token mw-crypto), 5658 (token paysim); both also on 127.0.0.1SoftHSMv2 with two tokens, built from deploy/softhsm. The token files sit on the volume softhsm-tokens, which no other container mounts. It creates the tokens on a fresh volume and never generates keys.
mw-crypto8080 inside (mTLS), published as 127.0.0.1:8094; 8081 plain, health onlyThe HSM gateway. Waits for a healthy softhsm. Compose turns on MW_CRYPTO_BOOTSTRAP_KEYS (dev: create a missing key of every purpose) and MW_CRYPTO_PAYSHIELD_ENABLED (the payShield provider).
mw-simulators1500 (payShield, internal network only)Hosts the payShield 10K simulator among its other fakes. Keeps its LMK in the paysim token on 5658.
mw-auth8080 public /auth/v1 (127.0.0.1:8095); 8443 internal mTLS, not publishedThe main caller: PIN checks, token and assertion signing. Waits for a healthy mw-crypto.
provisionnone (one-shot)Copies the token user PINs from deploy/.env into Vault (secret/mw-crypto key mw.crypto.pkcs11.user-pin, and the paysim PIN for mw-simulators), so the services read them from Vault, never from a file.

The token labels and PINs are the SOFTHSM_* variables in deploy/dev.env.defaults (fake, documented values). They are applied only when a token is first created, so a change needs a fresh volume (see What can go wrong). Key metadata (keyId, version, purpose, state, provider, HSM label; nothing secret) lives in mw-crypto's own schema crypto.

Keys: purposes, ids and versions

Every key has a purpose. The purpose fixes the algorithm and what the key may be used for, so one key never does two jobs. The list is in service/KeyPurpose:

PurposeAlgorithmUsed for
PIN_TRANSPORTRSA 3072, RSA-OAEP-256Apps and channels encrypt the PIN under its public key. Only the HSM can decrypt.
PIN_HMACHMAC-SHA256The stored PIN value: HMAC over walletId, a zero byte, and the PIN.
JWT_SIGNRSA 3072, RS256mw-auth's access tokens for the app (APISIX verifies them).
ASSERTION_SIGN, AUDIT_ANCHOR_SIGNEC P-256, ES256The transaction assertion the core checks; the signed audit anchor of mw-audit-dw.
TOKENISE_*, HMAC_*, KEK_*HMAC-SHA256, HMAC-SHA256, AES-256Tokens for MSISDN/NID in the warehouse; partner and webhook signatures; envelope encryption of columns.
XMLDSIG, HTTP_SIGN_RSA, HTTP_SIGN_ECRSA 3072 / EC P-256XML signatures and RFC 9421 HTTP signatures for later partners (no caller yet).
ZPK, TPK, PVK, ZPK_AES, TPK_AEStriple DES / AES-128, on the payShieldCard-style PIN blocks and PVVs for ATM and switch adapters.
  • keyId. Unless a caller names one, a key's id is its purpose in lower case with hyphens: JWT_SIGN becomes jwt-sign.
  • Versions and labels. The HSM object is labelled <keyId>.v<n>, for example pin-hmac.v1. The same string is the kid header of every JWS it signs, so a verifier knows which public key to pick.
  • Rotation adds a version. The old ACTIVE one becomes VERIFY_ONLY (it may still check old values, never create new ones), and an older VERIFY_ONLY one becomes RETIRED. New signatures always use ACTIVE. A PIN checked under a VERIFY_ONLY HMAC key comes back with a rehash under the new key, so stored PINs move over as people log in.
  • Where keys come from. In dev the bootstrap creates what is missing on start (and every 30 s). In production keys come only from the dual-control key ceremony in the ops console: two custodians each enter a share, and the HSM combines them.

PKCS#11 over a socket

SoftHSM is a library, not a server. Normally the program that uses it loads it and reads the token files itself. We do not want key files inside mw-crypto's container, so deploy/softhsm/README.md chose "Option A": SoftHSM runs only in its own container and serves each token on its own TCP port.

softhsm container                                mw-crypto container
  socat TCP-LISTEN:5657,fork                        SunPKCS11 (JDK)
    EXEC: p11-kit remote                              loads /usr/lib/libp11-kit.so.0
          --provider libsofthsm2.so                   one module file:
          pkcs11:token=mw-crypto      <-- TCP -->     remote: |socat - TCP:softhsm:5657
  token files on volume softhsm-tokens              slotListIndex = 0
  • One port per token. Port 5657 shows only the mw-crypto token and 5658 only paysim. Each client sees exactly one slot, so slotListIndex = 0 is always the right token, and the payShield simulator simply cannot see mw-crypto's keys.
  • Behaves like a network HSM. Callers get PKCS#11 sessions, never key files. A session still needs the token's user PIN, which is why a plain TCP port is acceptable in dev and test (it is reachable only on the app network and 127.0.0.1).
  • Works in Testcontainers. A TCP port maps to the host. A unix socket would not cross the Docker Desktop VM on macOS.
  • Keys are sensitive and never extractable. They are created as token objects that refuse to be read out, even by mw-crypto.

Two things work differently over this RPC bridge, and the code is shaped around them:

  • OAEP is split. SunPKCS11 has no RSA-OAEP cipher. So the HSM does the raw RSA decrypt (CKM_RSA_X_509, no padding) and client/OaepDecoder removes the OAEP padding in the JVM. That is also why the clear PIN exists briefly in mw-crypto's memory, as a byte[] that is zeroed in a finally block.
  • No AES-GCM or CBC in the HSM. Over the RPC, CKM_AES_GCM fails and drops the connection, and a CBC decrypt is refused. So the key wrap of envelope encryption is AES-256-CTR built from the HSM's plain AES (ECB) on counter blocks. The data itself is AES-GCM in the JVM.

mw-crypto keeps a pool of at most 8 HSM sessions. Each call has a 5 s limit and runs on its own thread, so a hung HSM quickly fails every request with 503 MW-SYS-010 instead of piling them up. scheduler/HsmProbeJob asks the HSM for random bytes every 10 s and sets the metric crypto.hsm.up; the change to down logs ERROR crypto.hsm.down.

The payShield simulator

Card schemes, ATMs and switches do not speak PKCS#11. They expect a payment HSM, and the common one is the Thales payShield 10K. mw-crypto therefore has a second provider, client/PayShieldProvider, that sends payShield host commands over TCP to mw-simulators:1500. In production that address would be a real payShield.

CommandWhat it does
NCHealth check: answers with the LMK's check value. The provider's probe.
A0Generate a key (ZPK, TPK, PVK). It comes back as a blob encrypted under the LMK.
CA / CCTranslate a PIN block from a terminal key (TPK) or zone key (ZPK) to another zone key.
JC / JE, DGTurn a PIN block into a PIN under the LMK, then compute a Visa PVV from it.
DC / ECVerify a PIN block against a stored PVV.
M0 / M2Encrypt / decrypt data under a data key.

The payShield never stores working keys itself. It hands back each key encrypted under its LMK, and the caller stores that blob. So mw-crypto's key table holds the blob as the version's "HSM label", never a clear key. The simulator keeps its LMK as an AES-256 object in the paysim token (client/Pkcs11LmkStore in mw-simulators), so the LMK survives restarts like a real one.

On the mw-crypto side the provider keeps 4 open connections, gives each command 3 s, and sits behind a Resilience4j circuit breaker named payshield: when the simulator stops answering, the breaker opens and calls fail at once with 503 MW-SYS-010. No product flow uses the payShield yet. The ATM and interop adapters will be its first callers.

Who may use which key

Holding keys in one place is only half the story. mw-crypto also decides who may ask for what, and the default answer is no. Every call needs two things (ADR D24):

  1. A client certificate from Vault's internal CA (mTLS). Without one the TLS handshake fails.
  2. A service JWT from Keycloak whose azp (the client that asked for the token) equals the certificate's CN. A token stolen from another service does not match the certificate.

Then security/CallerPolicy checks the operation against mw.crypto.authz in mw-crypto's application.yml:

OperationAllowed callers (dev)
/internal/v1/pin/verify, /pin/derivemw-auth only
/jws/sign with JWT_SIGN or ASSERTION_SIGNmw-auth only
/jws/sign with AUDIT_ANCHOR_SIGNmw-audit-dw only
/tokens (TOKENISE_MSISDN, TOKENISE_NID)mw-auth, mw-audit-dw
generate, rotate, key changes, ceremoniesmw-admin-api (the key-admin client)
/jwks/{purpose}, /keys (public data)every allowed caller

A refusal is 403 MW-AUTH-002 with a WARN security.internal_call_denied, decided before any HSM call. There is deliberately no general "HMAC this under PIN_HMAC" operation: such an oracle would let a caller test every 5-digit PIN in seconds.

Worked example: the PIN of an app payment

Customer 01711000001 sends Tk 10 from the app and types the PIN. Follow the PIN from the phone to the core:

  1. The public key. The app fetches GET /auth/v1/pin-key (through APISIX). mw-auth serves the newest PIN_TRANSPORT version, which it read from mw-crypto's /internal/v1/jwks/PIN_TRANSPORT and caches.
  2. Encrypt on the phone. The app encrypts the 5-digit PIN with RSA-OAEP (SHA-256). From here on only ciphertext travels.
  3. Payment request. The app posts the transaction with encryptedPin to mw-app-gateway.
  4. Ask for an assertion. mw-app-gateway calls mw-auth's internal port 8443 with mTLS and its service token.
  5. Cheap checks first. mw-auth checks the wallet is known and the PIN is not locked. A locked wallet costs no HSM call.
  6. PIN verify. mw-auth sends the ciphertext and the stored HMAC (from its own table auth.credential) to mw-crypto.
  7. Decrypt inside the HSM. The private key never leaves SoftHSM; it returns the raw RSA result.
  8. Unpad in the JVM. OaepDecoder strips the OAEP padding and checks it is exactly 5 ASCII digits (else 400 MW-VAL-014).
  9. HMAC inside the HSM. SoftHSM computes HMAC-SHA256 over walletId, a zero byte and the PIN, under the PIN_HMAC key version named in the stored value. mw-crypto compares in constant time (MessageDigest.isEqual) and zeroes every buffer that held the PIN.
  10. The answer. {match: true}. A wrong PIN is {match: false}, not an error; mw-auth counts it and answers 401 MW-AUTH-040 with the tries left.
  11. Sign the assertion. mw-auth builds the claims: aud core, sub walletId, a fresh jti, exp = iat + 60 s, and txnHash (SHA-256 over the canonical JSON of the transaction). Header typ txn-assertion+jwt.
  12. ES256 in the HSM. SoftHSM signs with the ASSERTION_SIGN private key.
  13. The JWS comes back with kid = the key version, for example assertion-sign.v1.
  14. mw-auth returns it to the channel. The PIN ciphertext stops here.
  15. The channel publishes the request on Kafka with only the assertion.
  16. The orchestrator forwards the assertion in its core commands.
  17. The core checks it. mw-core-mock recomputes txnHash from the command (RFC 8785 canonical JSON, SHA-256), verifies the ES256 signature against mw-auth's /auth/v1/.well-known/assertion-jwks.json (refreshed every 30 s), and claims the jti in its used_assertion table, so the same approval cannot pay twice. See mw-core-mock.

  • The caller side in mw-auth: client/CryptoClient, service/PinVerifier, service/TxnAuthorisationService.
  • The simulator: client/PayShieldServer, client/Pkcs11LmkStore; the field layouts in services/mw-simulators/CLAUDE.md.

What can go wrong

What can go wrong
  • Key generation fails with CKR_DEVICE_MEMORY. The client's p11-kit must speak the same RPC version as the server's. Both images pin Alpine p11-kit=0.26.2-r0; Ubuntu noble's 0.25.3 logs in but fails every key generation. Keep the versions together (scripts/test/test_softhsm.sh checks it).
  • The wrong token answers. A stray module file under /usr/share/p11-kit/modules/ or /etc/pkcs11/modules/ in a client image adds slots, and slotListIndex = 0 may then pick the wrong one. The images delete the package's own module file on purpose.
  • You changed a token PIN or label and now nothing logs in. PINs and labels are set only when a token is first created. Change them in deploy/.env only together with deploy/reset.sh, which drops the softhsm-tokens volume and destroys every key. Every stored PIN HMAC is then useless, so the seeder must set the app PINs again.
  • Logins and payments all answer 503. The HSM is down or unreachable, and everything fails closed: mw-crypto answers MW-SYS-010, mw-auth turns that into MW-SYS-050, and no wrong try is counted. Look for crypto.hsm.down in mw-crypto's log. Once softhsm is back, mw-crypto re-initialises its PKCS#11 library (a JVM loads it only once, so it resets it on purpose) and recovers by itself.
  • You added a caller and it gets 403 MW-AUTH-002. Deny by default: add the client to the purpose's entry in mw.crypto.authz, and check its certificate CN equals its token's azp.
  • Remember what SoftHSM is not. It is not a payment HSM. With PKCS#11 the clear PIN exists for a moment in mw-crypto's JVM (zeroed right after). Only a payment HSM keeps it inside the device; that is open point 22 in the spec. Never use SoftHSM outside dev and test.
