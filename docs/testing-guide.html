The two web UIs

The middleware has no customer UI of its own: the mobile app, USSD handsets, merchant web shops, banks, mobile operators and billers are all outside it. On a test stack two web UIs stand in for them:

Step 0.1: start the stack (whoever runs it, once)

Prerequisites as in the README (Docker, JDK 25, Node.js 24 + pnpm). From the repository folder:

./gradlew bootJar
# the dev settings: fixed fake credentials and short timers (once; the scripts also copy it when deploy/.env is missing)
(cd deploy && cp dev.env.defaults .env)
# fresh volumes: seeded balances, daily limits, users
deploy/reset.sh
# one command: build every image (services, both consoles), start platform + services + consoles, seed
# (users, wallets, partners, templates), turn on the test-only routes; returns once all is healthy and seeded
# (Compose reads deploy/.env itself; with its short timers, timeout tests take seconds, not minutes)
(cd deploy && docker compose --profile core --profile seed --profile tester up -d --build --wait)
# optional: every login and key in the terminal (the test console page Logins & secrets shows the same, section 1)

The first run takes 10-15 minutes (images and dependencies); later ones a few minutes. A non-zero exit names the container that failed: (cd deploy && docker compose --profile core --profile seed --profile tester ps -a), then its logs (the seeder's line seed.step.failed names the step).

Always start with all three profiles. A docker compose up without --profile tester removes the test-only routes and /tester answers 404: run the command above again (or scripts/tester.sh, which adds the console to a stack that is already running).

Sign-in: none. The test console signs in by itself as the user you pick on each page (app users at mw-auth with the app PIN 13579, portal users with the password portal-test-pass and their pre-set one-time code, apikey e2e-test-apikey).

    • test-only routes are on (core-mock wallets) (✖: "fix: scripts/tester.sh (re-applies the test routes)")
    • simulators answer (SMPP binds of mw-ussd): the simulators' bind list answers; whether mw-ussd is actually bound is checked in 4.2 (✖: "fix: start the stack; docker compose logs mw-simulators")

1 Credentials and keys

The logins a tester types are fixed, well-known test values, the same on every machine: they are written below at every step that needs them. They are dev/test values only, never real secrets. The other keys (database, HMAC and gateway secrets) are fixed fake dev-… values. All of them come from the committed file deploy/dev.env.defaults, copied to deploy/.env (step 0.1).

The quickest way: two test console pages, no terminal. Logins & secrets (/tester/credentials) shows every login with its password and a live one-time code, the app PINs and every platform key; Seed data (/tester/seed-data) shows everything the seeder created, with the login of each row next to it and the account tools of 1.5 (1.1). In a terminal, scripts/creds.sh and scripts/totp.sh print the same.

The volumes are set up with the values of deploy/.env. To change a value, edit deploy/.env, then deploy/reset.sh and step 0.1 again; scripts/creds.sh always prints the values your stack has.

  4. Expect the Transactions page; the header shows seed-ops-maker with its roles (among them viewer, ops-maker; Keycloak adds offline_access, uma_authorization, default-roles-ops) and Sign out.

10.1Security checks: mTLS and HSM down

mw-crypto (the only process that talks to the HSM) and mw-auth's internal API accept only callers with an OpenBao service certificate (mTLS, ticket 66). scripts/smoke.sh checks it; expect these lines green:

  • openbao PKI: intermediate pki_int with a role per mTLS service
  • mw-crypto serves its OpenBao certificate (tls_certificate_expiry_seconds on 8081)
  • mw-crypto fails the TLS handshake without a client certificate

By hand: a call without a client certificate never gets an HTTP answer (curl reports a TLS/handshake error, no status code):

curl -vk https://127.0.0.1:8094/internal/v1/keys

HSM down (the dev HSM is the softhsm container): everything that needs a key fails closed and nothing is counted against the customer.

  1. Stop it: 
    docker compose -f deploy/docker-compose.yml stop softhsm
  2. Test console Wallet auth (a wallet made in 3.11) → Log in with the PIN: red ✖ HTTP 503 MW-SYS-050 from mw-auth. App flows: a P2P with PIN 13579: red ✖ HTTP 503 MW-SYS-012 (mw-app-gateway's fail-closed code when mw-auth cannot answer), no balance change. No PIN try is used up while it lasts.
  3. Start it again: 
    docker compose -f deploy/docker-compose.yml start softhsm
    Within about 10 s mw-crypto logs crypto.hsm.up (no restart needed) and the same P2P completes.

The steps for operators are in the runbook (HSM down, Certificate expiry).
