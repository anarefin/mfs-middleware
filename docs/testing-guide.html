0 Before you start

The two web UIs

The middleware has no customer UI of its own: the mobile app, USSD handsets, merchant web shops, banks, mobile operators and billers are all outside it. On a test stack two web UIs stand in for them:

UIURLPlaysSign-in
Test console (dev/test only)https://localhost/tester the mobile app (customer, agent, merchant), a USSD handset, the partners (top-up operator OCS, bill aggregator, bank: simulators you can switch to fail), the core banking fault switch, the checkout shop and buyer, the organisation portal, the SMS and email inboxesnone
Ops consolehttps://localhost/console the operations team: search, timeline, audit trail, reversals, approvals (maker-checker), partners, USSD menus, SMS/email templates, wallet unlockKeycloak, password + one-time code (section 1)

Every action in the test console goes through the API gateway (APISIX) exactly like a real client.

Step 0.1: start the stack (whoever runs it, once)

Prerequisites as in the README (Docker, JDK 25, Node.js 24 + pnpm). From the repository folder:

# fresh volumes: seeded balances, daily limits, users
make reset
# jars and images (the test console image too); 10-15 min the first time
make build
# the stack with short timeouts, so timeout tests take seconds, not minutes
make up TIMERS=fast
# seeded users, wallets, partners, templates
make seed
# turns on the test-only routes and starts the test console
make tester
# prints every login and key you need (section 1)
make creds
Run make tester again after any plain make up: that removes the test-only routes and /tester answers 404.

Step 0.2: open the test console

  1. Open https://localhost/tester. The certificate is self-signed: accept it once (Chrome: Advanced → Proceed to localhost; or type thisisunsafe on the warning page).
  2. The Home page shows three stack checks. Expect three green ✔: the gateway answers, the test-only routes are on, the USSD SMPP gateway is bound. Each ✖ shows its fix.
  3. Below them, the seeded wallets table shows each wallet's balance and amount held.
  4. Press Reset every simulator and core fault. Expect "applied". Do this before and after every failure test.

Fees and limits. The core charges the payer the amount plus a fee into the FEE-POOL account (P2P Tk 5, top-up Tk 2, …). A Tk 10 P2P therefore shows -Tk 15.00 on the payer, Tk 10.00 on the payee and Tk 5.00 on FEE-POOL (a gain has no + sign). Other fees: cash out Tk 10, top-up Tk 2, bill payment Tk 3, merchant payment and add money none. Limits: Tk 5,000 per transaction, Tk 15,000 debited per wallet per UTC day. Five wrong PINs in a row lock the wallet.

1.3Sign in with a pre-set code (quickest)

  1. Open https://localhost/console and press Sign in with Keycloak.
  2. Username seed-ops-maker, password from make creds, press Sign In.
  3. The next page asks for a one-time code. In a terminal run: 
    make totp PERSONA=seed-ops-maker
    It prints e.g. seed-ops-maker: 482913 (valid 17 s more; …). Type the 6 digits, press Sign In.
  4. Expect the Transactions page; the header shows seed-ops-maker with its roles (among them viewer, ops-maker) and Sign out.
A code is accepted once. To sign in a second user within the same 30 seconds, wait until the code changes (run make totp again). Five wrong passwords or codes lock the user for 1 to 15 minutes.

1.4Sign in with your own authenticator app

For ops-maker01 and the other realm users. The codes use SHA-256: use FreeOTP or Aegis (Android) or another app that honours the algorithm in the QR code. Keycloak's setup page also names Google Authenticator, but on many phones it ignores the SHA-256 setting and its codes are refused.

  1. Sign in with Keycloak, user ops-maker01 and the password.
  2. First time only: the page Mobile Authenticator Setup shows a barcode (QR). Scan it in the app (or Unable to scan? shows the key to type in).
  3. Type the app's 6-digit code into One-time code, any Device Name, press Submit.
  4. Later sign-ins: password, then the app's current code.

Lost the phone or enrolled a wrong app? Reset the user's code so the next sign-in enrols again (replace ops-maker01):

docker compose -f deploy/docker-compose.yml exec keycloak sh -c '
  k=/opt/keycloak/bin/kcadm.sh; c="--config /tmp/kc.config"
  $k config credentials $c --server http://localhost:8080 --realm master \
     --user "$KC_BOOTSTRAP_ADMIN_USERNAME" --password "$KC_BOOTSTRAP_ADMIN_PASSWORD" >/dev/null
  id=$($k get users $c -r ops -q username=ops-maker01 --fields id --format csv --noquotes)
  for cid in $($k get users/$id/credentials $c -r ops --fields id,type --format csv --noquotes | awk -F, "\$2==\"otp\"{print \$1}"); do
    $k delete users/$id/credentials/$cid $c -r ops
  done
  $k update users/$id $c -r ops -s "requiredActions=[\"CONFIGURE_TOTP\"]"
  rm -f /tmp/kc.config'

1.5Keycloak administration

The Keycloak admin web console is not published by the gateway (only the ops login pages are). Admin tasks run with kcadm.sh inside the container, as user kc-admin (password in make creds; the container already has it in its environment). Example: list the ops users and whether they enrolled:

docker compose -f deploy/docker-compose.yml exec keycloak sh -c '
  k=/opt/keycloak/bin/kcadm.sh; c="--config /tmp/kc.config"
  $k config credentials $c --server http://localhost:8080 --realm master \
     --user "$KC_BOOTSTRAP_ADMIN_USERNAME" --password "$KC_BOOTSTRAP_ADMIN_PASSWORD" >/dev/null
  $k get users $c -r ops --fields username,requiredActions
  rm -f /tmp/kc.config'

Realms: ops (console), customers (app), portals (org/SP portal), partners, services (service to service). Their definitions are in deploy/keycloak/realms. make reset re-imports them and resets every user.

1.7API keys and tokens (Postman, curl)

Test-only routes (/test/core-mock/…, /test/sim/…, /test/mail/…) need the header apikey: <MW_E2E_API_KEY> and exist only after make tester (or make api-test).

Tokens (JWT) for the business APIs: a form POST to the gateway. All login clients are public: no client secret.

# app user (realm customers) -> /app/v1/*
curl -sk https://localhost/auth/realms/customers/protocol/openid-connect/token \
  -d client_id=mw-app -d grant_type=password -d username=customer01 -d password='<customers password>'
# portal user (realm portals) -> /portal/org/v1/*
curl -sk https://localhost/auth/realms/portals/protocol/openid-connect/token \
  -d client_id=mw-portal -d grant_type=password -d username=org-maker01 -d password='<portals password>'
# ops user (realm ops) -> /admin/v1/*: pre-set code users only, plus the apikey header
curl -sk https://localhost/auth/realms/ops/protocol/openid-connect/token -H 'apikey: <MW_E2E_API_KEY>' \
  -d client_id=mw-e2e-ops -d grant_type=password -d username=seed-ops-viewer -d password='<ops password>' \
  -d totp=<make totp PERSONA=seed-ops-viewer>

Use the access_token from the answer as Authorization: Bearer …. It lasts 5 minutes.

/app/v1/* needs more than a token: a bound device and an ECDSA signature on every request (headers X-Device-Id, X-Timestamp, X-Nonce, X-Signature). Postman cannot do that by hand; use the test console, or the ready collection below.

Postman: import tests/api/mfs-mw.postman_collection.json and tests/api/local.postman_environment.json, then fill the environment's e2eApiKey, kcCustomersPassword, kcPortalsPassword, kcOpsPassword, kcOpsTotpSecret, billaggSecret, checkoutSecret from deploy/.env (the collection signs requests itself). Or run the whole suite: make api-test.

APISIX admin API (developers only; read the live routes):

docker compose -f deploy/docker-compose.yml exec apisix bash -c 'exec 3<>/dev/tcp/127.0.0.1/9180;
  printf "GET /apisix/admin/routes HTTP/1.0\r\nX-API-KEY: %s\r\n\r\n" "$APISIX_ADMIN_KEY" >&3; cat <&3'

2 Reading a test console result

The panel on the right of each page shows the result of the last button you pressed:

  1. Headline: green ✔ or red ✖, the txnId and status, and the error code if refused (e.g. REJECTED MW-CORE-INVALID_PIN).
  2. Final status with the link open in the ops console ↗ (timeline, partner calls, audit trail).
  3. Balances of every wallet involved: before, after, change, amount held now.
  4. SMS received since the submit.
  5. Steps: every API call in order with HTTP status and time. Click a step to see the answer.
A red ✖ is not always a failed test. The headline is red whenever a call answered outside 200/201/202. In a negative case (wrong PIN, maker approving own batch, wrong OTP) red with the expected code is the pass. Some business refusals are answered with HTTP 200 and show a green ✔ with the refused status (checkout result FAILED). Balances, SMS and the final status appear on App flows only; the other pages show the headline and steps: click a step to see the full answer.

Statuses: COMPLETED (done), REJECTED (refused before money moved), FAILED (attempted, nothing moved), PROCESSING / UNKNOWN (outcome being resolved), MANUAL_REVIEW (an operator must decide), REVERSED.

Pick the transaction type first, then the user. Choosing a Transaction type resets the user, counterparty and amount to that type's defaults (the defaults below already fit each case).

5.2Lost core reply → status inquiry → COMPLETED

  1. Apply Core: the reply of the next transfer is lost (TSQ -> COMPLETED).
  2. App flows: P2P to 01711000002, Tk 10, Submit.
  3. Expect a step poll the transaction until it is final (was PROCESSING), then COMPLETED; payer debited once (-Tk 15.00); SMS "processing", then "sent".

5.3Lost refusal → status inquiry → FAILED

  1. Apply Core: the next transfer is refused and the refusal lost (TSQ -> FAILED).
  2. App: P2P. Expect FAILED (code MW-TMO-003 in the ops console), no balance changed.

5.7Custom faults

Set … applies, Reset … clears.

9.6MANUAL_REVIEW: force commit, force release, manual TSQ

  1. Create one (5.6), open it as the maker. Buttons: Request manual TSQ, Request force commit, Request force release.
