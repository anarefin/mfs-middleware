Sign-in: none. The test console signs in by itself as the user you pick on each page (customers password app-test-pass, portals password portal-test-pass, apikey e2e-test-apikey).

1 Credentials and keys

The logins a tester types are fixed, well-known test values, the same on every machine: they are written below at every step that needs them. They are dev/test values only, never real secrets. The other keys (database, HMAC and gateway secrets) are random per machine; scripts/creds.sh prints them.

The fixed values hold on a stack started after deploy/reset.sh. A stack whose deploy/.env was created before keeps its old random values (the volumes were set up with them): scripts/gen-dev-env.sh then warns "… differ from the documented test values", and scripts/creds.sh prints the values that work. To switch: deploy/reset.sh, then step 0.1 again.

1.3Sign in with a pre-set code (quickest)

  1. Open https://localhost/console (accept the self-signed certificate once, as in 0.2) and press Sign in with Keycloak.
  2. Username seed-ops-maker, password ops-test-pass, press Sign In.
  3. The next page asks for a one-time code. In a terminal, in the repository folder, run: 
    scripts/totp.sh seed-ops-maker
    It prints e.g. seed-ops-maker: 482913 (valid 17 s more; …). Type the 6 digits, press Sign In. With less than 5 s left, wait for the next code.
  4. Expect the Transactions page; the header shows seed-ops-maker with its roles (among them viewer, ops-maker; Keycloak adds offline_access, uma_authorization, default-roles-ops) and Sign out.
  5. The checker, for every maker-checker case: open a private/incognito window, same URL, user seed-ops-checker, password ops-test-pass, code scripts/totp.sh seed-ops-checker.
A code is accepted once. Two users have different codes, so the maker and the checker may sign in in the same 30 seconds; the same user twice (e.g. after a sign-out) must wait for the next code. Five wrong passwords or codes lock the user for 1 to 15 minutes (wait, or unlock in 1.5).

1.4Sign in with your own authenticator app

For ops-maker01 and the other ops-*01 users. The codes use SHA-256: use FreeOTP or Aegis (Android) or another app that honours the algorithm in the QR code. Keycloak's setup page also names Google Authenticator, but on many phones it ignores the SHA-256 setting and its codes are refused.

  1. Sign in with Keycloak, user ops-maker01, password ops-test-pass.
  2. First time only: the page Mobile Authenticator Setup shows a barcode (QR). Scan it in the app (or Unable to scan? shows the key to type in).
  3. Type the app's 6-digit code into One-time code, any Device Name, press Submit.
  4. Later sign-ins: ops-test-pass, then the app's current code.

Lost the phone or enrolled a wrong app? Reset the user's code with the first block of 1.5.

2 Reading a test console result

The panel on the right of each page shows the result of the last button you pressed:

  1. Headline: green ✔ or red ✖, the txnId and status, and the error code if refused (e.g. REJECTED MW-CORE-INVALID_PIN).
  2. Final status with the link open in the ops console ↗ (timeline, partner calls, audit trail).
  3. Balances of every wallet involved: before, after, change, amount held now.
  4. SMS received since the submit.
  5. Steps: every API call in order with HTTP status and time. Click a step to see the answer.

Each action adds its own panel (titled Submit, Resend, Device, Lookup, …); the newest is on top. A submit also shows the hint Idempotency-Key <key> it used. "No SMS yet (notifications can take a few seconds: see Inbox)." means the SMS had not arrived when the panel was drawn: check SMS & email (6.1). open in the ops console ↗ when you are not signed in to the console leads to its login page and, after the sign-in (1.3), back to that transaction.

A red ✖ is not always a failed test. The headline is red whenever a call answered outside 200/201/202. In a negative case (wrong PIN, maker approving own batch, wrong OTP) red with the expected code is the pass. Some business refusals are answered with HTTP 200 and show a green ✔ with the refused status (checkout result FAILED). Balances, SMS and the final status appear on App flows only; the other pages show the headline and steps: click a step to see the full answer.

Statuses: COMPLETED (done), REJECTED (refused before money moved), FAILED (attempted, nothing moved), PROCESSING / UNKNOWN (outcome being resolved), MANUAL_REVIEW (an operator must decide), REVERSED.

9.5Reversal

Sign in as: window A seed-ops-maker, window B seed-ops-checker (both ops-test-pass).

  2. Maker sees "your request: another checker decides" and no Approve button.
  3. Back on the transaction: "REVERSAL requested by seed-ops-maker on …, waiting for approval in Approvals."
  4. Checker: Approvals → Approve: "Decision recorded."
  5. Reload the transaction: status REVERSED (the original itself; no separate transaction is created). The approval row shows reversal <id>: the core's booking reference; the Reversed by link on the transaction opens that id and answers MW-VAL-003 (known, not a transaction). In the test console the balances are restored (A wallet in core-mock).
  6. Reject instead (with a Rejection reason): status stays COMPLETED.
  7. Core refuses: apply preset Core: the next reversal is refused (-> MANUAL_REVIEW), request and approve a reversal: the transaction goes to MANUAL_REVIEW with an audit entry. Resolve it as in 9.6 (force commit keeps it as paid).
