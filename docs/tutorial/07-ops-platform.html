The ops console and maker-checker

Bits staff use the ops console (https://localhost/console, app mw-admin-ui) to search transactions, see each one's timeline of states, manage partner settings, SMS templates and USSD menus, and fix stuck transactions. Behind it is mw-admin-api.

In plain English

Maker-checker is the four-eyes rule: any action that changes money or configuration needs two different people. The maker asks for the change ("force-release this stuck hold", "reverse this payment", "change this partner's URL"); a checker who is not the maker approves or rejects it. Only then does it happen. A request nobody decides on expires after 72 hours.

  • Operator actions on transactions: FORCE_COMMIT, FORCE_RELEASE, INQUIRE (ask again now) and reversal.
  • Roles are Keycloak roles in the ops realm, for example ops-maker and ops-checker (transactions), integration-maker / integration-checker (partner settings), compliance-officer, auditor and viewer (enum dto/AdminRole). Logging in needs a password and a TOTP code (an authenticator app); for test users, scripts/totp.sh prints the current code.
  • The browser never calls mw-admin-api directly: the Next.js server does, with the operator's token.
Where it lives
  • service/ChangeRequestService (the maker-checker engine), controller/ChangeRequestController, dto/AdminRole.
  • The orchestrator side: route/TxnActionRoute → service/OperatorActionService.
  • The UI: ui/mw-admin-ui/ (pages under src/app/(console)/). Spec section 15.

Notifications: SMS and email

mw-notify sends messages for two reasons:

  1. Transaction updates. It listens to mw.txn.status.v1. Rules stored in its database decide who gets what: for a completed P2P, the sender gets "sent" and the receiver "received"; a failure or "still processing" goes to the person who started it. Templates exist in Bangla and English.
  2. Direct requests. Other services publish on mw.notify.request.v1, for example an OTP. The messageId is the idempotency key, so a repeat is never sent twice.

Messages are first stored, then a dispatch job sends them: OTPs first, transient errors retried after 2 s, 10 s and 30 s, promotional messages held during quiet hours (22:00 to 08:00, Dhaka time). SMS go out over SMPP to the SMS centre (the simulator, in dev); email over SMTP (the GreenMail test server).

Where it lives (mw-notify)
  • service/RuleEngine, service/TxnStatusService, service/DispatchService, client/SmppSmsSender.
  • Spec section 10.

The audit trail

Every saga state change, every operator decision and every partner call (masked) produces an event on mw.audit.event.v1. mw-audit-dw stores them in its own schema with a database user that can only insert: no update, no delete.

On top of that, each month's records form a hash chain: every record stores a SHA-256 hash of its own content plus the previous record's hash. Change one old record and every hash after it stops matching. A scheduled job checks the chain.

Where it lives (mw-audit-dw)
  • messaging/AuditEventListener, service/AuditService, service/HashChain, scheduler/AuditChainVerifyJob, the search API controller/AuditSearchController. Spec section 14.
Not built yet

Despite the "dw" (data warehouse) in its name, the MVP has no separate warehouse feed: the audit store is what exists.

Logins: Keycloak realms

A Keycloak realm is a separate set of users with its own login rules. There is one per kind of user:

RealmWhoTest users
customersapp users: customers, agents, merchantscustomer01, customer02, agent01, merchant01
opsBits staff (password + TOTP)seed-ops-maker, seed-ops-checker and the ops-* users
portalsorganisation and service-provider portal usersorg-maker01, org-checker01
servicesservice accounts for internal calls between servicesmw-portal-api, mw-admin-api
partnerspartner systemspartner-sim

The test users' passwords are fixed, documented dev values (ops ops-test-pass, customers app-test-pass, portals portal-test-pass); the other secrets are generated per laptop into the gitignored deploy/.env. scripts/creds.sh prints them all. Realm files: deploy/keycloak/.

The app has one extra layer: device binding. A login alone is not enough to move money; the phone must also be bound (an OTP by SMS, then a key stored on the device) and must sign each request. A stolen password on another phone cannot pay.

The gateway: APISIX

APISIX is configured from files in deploy/apisix/, applied on every docker compose up by the apisix-init one-shot:

  • global_rules/: what applies to every request (correlation id, size limits, stripping internal X-Mw-* headers a caller tries to send, the standard error envelope).
  • routes/: one JSON file per public path, with its plugins (JWT check for the app, HMAC for merchants and partner callbacks, IP allow-list and basic auth for USSD gateways, rate limits).
  • routes-test/: test-only routes (to the core mock and simulators), added only by the test tools.

Request body shapes are not checked at the edge; each service validates against its OpenAPI contract. scripts/edge-test.sh tests the edge rules on the running stack.

Secrets: OpenBao

No secret is ever in code, a config file or a test. Services read database passwords, partner keys and signing secrets from OpenBao at start-up; each service has its own login (AppRole) and can read only its own secrets. On a laptop the one-shot provision container creates everything on the first docker compose up and checks it again on every later one (idempotent).

Logs

Every service writes JSON to stdout, one event per line, with the same fields: ts, level, service, correlationId, txnId, traceId, partnerId, channel, event, message, durationMs, errorCode, among others. Business events have stable names such as txn.state.changed and partner.call.completed. Masking runs before anything is printed.

Try it yourself
  • Log in to the console as seed-ops-maker (TOTP from scripts/totp.sh), open a transaction and read its timeline. Raise a change request, then approve it as seed-ops-checker (scripts/totp.sh seed-ops-checker).
  • Test console page SMS & email shows what mw-notify sent.
  • Automated: scripts/api-test.sh "10, 11, 13, 14, 15, 17" and scripts/ui-e2e.sh (the console's browser tests).
