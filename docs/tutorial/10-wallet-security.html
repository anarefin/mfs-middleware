Chapter 10

Wallet security: mw-auth and mw-crypto

Who may move money is decided by two services. mw-auth proves who the wallet user is and holds their PIN; mw-crypto is the only process that talks to an HSM, so no other service ever holds a key. This chapter follows a login, a payment and a PIN reset through both (spec 18.7 and 18.8, ADRs D20 to D24).

The two services

In plain English

The phone never sends a PIN in clear. It encrypts it with a public key whose private half lives in the HSM. mw-auth passes the encrypted PIN to mw-crypto, which opens it inside its own memory, compares a keyed hash and wipes it. mw-auth stores only that keyed hash. When a payment is approved, mw-auth signs a short-lived note, the assertion, that says "this wallet's owner approved exactly this transaction"; the core checks the signature and pays nothing without it.

Binding a phone and logging in

  • Every sensitive request is signed by the phone's EC P-256 key over method, path, body hash, timestamp, nonce and device id; a nonce works once (MW-AUTH-006), a changed body fails (MW-AUTH-004).
  • A wallet without a PIN logs in once with a LOGIN OTP and must set its first PIN (POST /auth/v1/pin).
  • APISIX checks the access token on /app/v1/* against mw-auth's JWK Set; mw-app-gateway then asks mw-auth whether the session is still live, so a logout or a new binding ends access within seconds.
  • A refresh token is used once: reusing a rotated one revokes the whole family (MW-AUTH-048).

Paying: the transaction assertion

  • The txnHash is the SHA-256 of the canonical JSON of type, amount, currency, payer, payee, idempotency key and channel: change one value on the way and the core refuses it.
  • A wrong PIN is refused before anything is published: the orchestrator never sees the request.
  • A resend with the same idempotency key within the 60 s gets the same assertion back without a second PIN check; another transaction under that key is 409 MW-IDEM-001.
  • The assertion carries newDevice: true for 24 h after a binding, a cooling-off flag the core can act on.

The PIN's life: policy, lockout, change, reset

  1. Policy. 5 digits; no repeated digit, no run (34567, 09876), not part of the MSISDN, not the birth year, not one of the last 3 PINs: 400 MW-AUTH-044 naming the rule.
  2. Lockout. 3 wrong PINs (any channel) lock the PIN for 1 h, then 24 h, then until a reset (MW-AUTH-041 with retryAfter, then 042). A locked wallet costs no HSM call. The dev stack shortens them (MW_AUTH_LOCK_LEVEL1=1m, MW_AUTH_LOCK_LEVEL2=3m).
  3. Change. Logged in with the PIN, the current PIN as step-up: the session is replaced, an SMS goes out.
  4. Self-service reset. A reset OTP on the bound phone plus NID last 4 and birth date, which the core checks (they leave mw-auth only as tokens); then the new PIN, every session ended.
  5. Care reset. Phone lost: care asks PIN_RESET in the ops console, a second operator approves (maker-checker); mw-auth opens the reset from auth.wallet-lock.v1 and the customer finishes it on the new phone.
  6. Ops unlock. UNLOCK with maker-checker lifts every PIN level at once.

Inside mw-crypto: keys and the HSM

mw-crypto has two providers behind one interface: PKCS#11 (SoftHSMv2 in dev and test, the production HSM later) and the Thales payShield 10K host-command protocol (a simulator in dev). A key has a purpose (PIN_TRANSPORT, PIN_HMAC, JWT_SIGN, ASSERTION_SIGN, AUDIT_ANCHOR_SIGN, TOKENISE_*, KEK_*, XMLDSIG, HTTP_SIGN_RSA, HTTP_SIGN_EC, and on the payShield ZPK, TPK, PVK, ZPK_AES, TPK_AES) and versions: rotation adds a version and keeps the previous one for verification until it is retired.

  • Deny by default: each caller is bound to the purposes it may use (mw.crypto.authz); anything else is 403 MW-AUTH-002.
  • Key changes and the key ceremony are dual-control in the ops console (two security-admin users, each with a fresh sign-in; a ceremony takes each custodian's own component).
  • An HSM outage fails closed: no login, no payment, nothing counted.
Where it lives (mw-crypto)
  • client/Pkcs11Provider, client/PayShieldProvider, security/CallerPolicy, service/PinService, service/KeyService, service/CeremonyService.
  • services/mw-crypto/CLAUDE.md; the SoftHSM tokens: deploy/softhsm/README.md; spec 18.8; ADR D23.

Service to service: mTLS

mw-crypto's API and mw-auth's internal API take only callers with a client certificate from OpenBao's pki_int (72 h, renewed by each service at two thirds of its life) and a Keycloak service token whose azp equals the certificate's name (D24). A token stolen from one service is useless from another.
