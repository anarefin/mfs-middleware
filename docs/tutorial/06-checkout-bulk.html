Checkout and bulk disbursement

Two business features built on top of the same saga: a shopper paying a web shop with their wallet, and an organisation paying hundreds of people from one file. Both add their own records and safety checks around a plain post-style transaction.

Merchant web checkout

In plain English

It works like any "pay with ..." button. The shop's server asks us for a payment session for order 123, Tk 500. We give back a link to our own payment page. The shopper opens it, types their wallet number, gets an OTP by SMS, enters the OTP and PIN, and pays. We send the shopper back to the shop with a signed result, and separately tell the shop's server with a signed message (the IPN).

  1. Create a session. The merchant's server signs the request with its HMAC key; APISIX checks the signature and tells mw-checkout which merchant it is. Sending the same order and amount again returns the same session (idempotent). A merchant can only ever see its own sessions.
  2. The hosted page. The shopper never types their PIN into the shop's website, only into ours.
  3. OTP. A one-time code goes by SMS through mw-notify at the highest priority. Each wrong guess uses up one of a limited number of tries.
  4. Confirm. Exactly one MERCHANT_PAY transaction per session. The request thread waits for the status (the same waiter pattern as the app gateway).
  5. Close the session safely. The session moves PAYING → PAID (or FAILED) with a conditional database update, so two racing requests cannot both pay. Cancelled sessions are CANCELLED; an expired session answers 410.

Telling the shop: IPN

An IPN (instant payment notification) is a server-to-server message to the shop: "order 123 is paid". The shop must not trust the shopper's redirect alone, because a shopper could fake it.

  • The IPN row is written in the same database transaction as the session outcome, so a paid session always has an IPN to send (the outbox idea again).
  • A scheduled job sends due IPNs. The body is signed: header X-Bits-Signature is an HMAC-SHA256 over a version string, the X-Bits-Timestamp and the body.
  • A 2xx answer means delivered. Otherwise it tries again after 1 min, 5 min, 30 min, 2 h and 6 h.
  • The shop's URL is checked before every send (https only, no private addresses), so nobody can use the IPN to reach our internal network (SSRF).
Where it lives (mw-checkout)
  • Merchant API: controller/MerchantSessionController, service/MerchantSessionService.
  • Hosted page: controller/HostedPageController, service/CheckoutPayService, service/SessionOutcomes.
  • IPN: service/IpnDeliveryService, service/IpnRetrySchedule, security/IpnSigner, security/IpnUrlPolicy. The fake shop that receives IPNs is in mw-simulators.

Bulk disbursement

In plain English

A company wants to pay 500 salaries. One person (the maker) uploads a CSV file. A different person from the same company (the checker) reviews and approves it. Then the system pays each row as its own small transaction, at a steady pace, and produces a result file.

  • All or nothing on upload: one bad row (bad number, more than 2 decimals, a repeated reference) refuses the whole file with MW-VAL-031. Too many rows is MW-VAL-030. A half-uploaded payroll is worse than none.
  • Maker-checker: the checker must be a different user of the same organisation. A batch nobody decides on within 72 hours expires.
  • Pacing: rows are sent at bulk.dispatch.rate-per-second (a token bucket), so a big file does not flood the core. Batches can be paused and resumed.
  • No double pay: each row's txnId is derived from the row itself, so sending a row twice (after a crash, say) hits the orchestrator's idempotency check.

Batch states: PENDING_APPROVAL → APPROVED → EXECUTING (↔ PAUSED) → COMPLETED or COMPLETED_WITH_EXCEPTIONS; or REJECTED / EXPIRED before it starts.

Reconciling stuck rows

What if a row was sent but its status never came back? A reconcile job looks for rows still SUBMITTED after a while and asks the orchestrator's internal transaction query API what happened (logging in as the mw-portal-api service account). A row that cannot be settled in time is marked UNRESOLVED and the batch ends COMPLETED_WITH_EXCEPTIONS. It never sends the row again: re-sending without knowing is how people get paid twice.

Where it lives (mw-portal-api)
  • controller/BulkBatchController, service/BatchService, service/BulkCsvParser.
  • service/BulkExecutionService (dispatch), route/TxnStatusRoute (settle), service/BulkReconcileService, client/OrchestratorQueryClient.
  • The orchestrator side: saga/BulkDisburseFlow.
