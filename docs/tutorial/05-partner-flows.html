Chapter 5

Partner flows: top-up, bill pay, add money from a bank

These flows need a company outside Bits to do its part. The orchestrator still runs the saga, but now one step is "ask the partner", done by an adapter. Partners are slow, flaky and all different, so this is where the "never guess" rule earns its keep.

Mobile top-up (airtime)

In plain English

The customer buys Tk 20 of airtime. We do not know yet whether the operator will deliver it, so we hold Tk 20 in the wallet first (chapter 3, idea 7). Then the telco adapter asks the operator's OCS to add the airtime. If the operator says yes, we commit the hold (take the money). If it says no, we release it (give it back). If it does not answer, we ask again until we know.

The three possible partner answers

Partner saysOrchestrator doesCustomer sees
SUCCESSCOMMITTING: CommitHold → COMPLETEDairtime arrives, money taken
FAILED (a definite no)RELEASING: ReleaseHold → FAILED with MW-PTR-<PARTNER>-<reason>"recharge failed", money back
UNKNOWN, or nothing within 30 sUNKNOWN: the adapter sends a STATUS_QUERY to the partner on the inquiry schedule. Success → commit; failed → release; "never heard of it" → release, but only after the deadline has passed"processing", then an SMS with the result
What can go wrong
  • The adapter is slow to read the request (for example it was restarted). A PAY request that is already past its deadline is not sent to the partner; the adapter answers FAILED. Otherwise the orchestrator might release the hold while the operator delivers airtime.
  • The partner answers with a code nobody understands. The adapter is fail closed: anything it cannot clearly classify is UNKNOWN, never FAILED. Releasing money for a top-up that actually happened is a real loss.
  • The hold times out (no FundsHeld in 5 s). The orchestrator asks the core: if the hold exists it releases it, otherwise the transaction is REJECTED.
  • CommitHold or ReleaseHold fails. This should never happen, so the transaction goes to MANUAL_REVIEW with a top-priority alert.
Where it lives
  • Orchestrator: saga/TopupFlow; partner answers in route/PartnerReplyRoute → service/PartnerReplyService.
  • Adapter: route/TelcoRequestRouteBuilder → messaging/TelcoRequestHandler → service/TopupService.
  • Spec sections 11.1 and 11.2.
Not built yet

Operators can also send a callback later. The telco adapter has no callback endpoint yet, so a telco top-up is settled only by the reply or by the status inquiry. Bill pay and bank do take callbacks.

Bill pay

Bill pay is the top-up pattern with two additions: first the app fetches the bill to show the amount due (a plain HTTP lookup, no money involved), and the aggregator often answers "accepted, pending" and sends the real result later as a callback.

  • The callback comes from outside, so APISIX lets it in and the adapter checks its HMAC signature and that the reference is one we sent. The orchestrator checks again that the callback belongs to that transaction.
  • Callbacks can arrive twice, late or out of order. The inbox and the state machine keep that harmless: a callback for a transaction that is already COMPLETED changes nothing.
Where it lives
  • saga/BillPayFlow; callbacks: route/PartnerInboundRoute → service/PartnerInboundService.
  • Adapter: controller/BillerController, service/BillFetchService, service/BillPaymentService.

Add money from a bank

Here the money comes in, so there is nothing to hold. The bank debits the customer's bank account, and only when the bank confirms do we credit the wallet.

Flow class: saga/AddMoneyBankFlow; adapter: service/BankDebitService, controller/PartnerCallbackController.

The adapter framework

In plain English

Each new partner should be configuration, not code. The three adapters share a small framework (copied into each, in a package called partner/): the partner's URL, timeouts, authentication, how to build its request, how to read its answer and how to translate its error codes are all written in YAML. The framework does the HTTP call safely and turns the answer into one of SUCCESS, FAILED, UNKNOWN or PENDING.

A partner, written as configuration

This is the real OCS configuration from mw-adapter-telco's application-dev.yml, trimmed:

mw:
  partners:
    instances:
      ocs:
        template: rest-json-request-reply      # which Camel route template to use
        base-url: ${OCS_BASE_URL:http://mw-simulators:8080}
        timeout-ms: 20000
        auth:
          scheme: none
        ambiguous-codes: ["9876"]              # these codes mean "we do not know": UNKNOWN
        error-map:
          "[2001]": { suffix: TOPUP_REJECTED, retryable: false }
        operations:
          "[PAY]":
            method: POST
            path: /ocs/v1/topup
            request: |                         # JSONata: our request → their JSON
              {"transactionId": reference, "msisdn": creditParty.id, "amount": amount.major}
            response: |                        # JSONata: their answer → our outcome
              status = 200
                ? {"outcome": "SUCCESS", "partnerRef": body.ocsRef, ...}
                : ...
          "[STATUS_QUERY]":
            method: GET
            path: /ocs/v1/topup/{reference}

JSONata is a small expression language for transforming JSON. Here it translates between our standard partner request and the partner's own format, so adding a similar partner needs no Java.

Key rules of the framework (spec section 12):

  • One attempt, never an automatic retry of a money call. A retry could pay twice; the status inquiry is the safe way to find out.
  • Circuit breaker and bulkhead (Resilience4j): if a partner keeps failing, stop calling it for a while, and never let one slow partner use up every thread.
  • Fail closed: any status code or body the mapping does not recognise is UNKNOWN.
  • Config can change at runtime: an approved change in the ops console arrives on mw.config.changed.v1, checked against an allow-list of hosts.
Where it lives (telco; billpay and bank have identical copies)
  • partner/template/PartnerRouteTemplates, PartnerCallWrapper, RestJsonAdapter.
  • partner/mapping/JsonataMapping; auth schemes in partner/auth/; config in partner/config/.
  • The framework is described in mw-adapter-telco's CLAUDE.md.

The simulators

mw-simulators fakes every partner. You steer it with "magic" values, so you can test every failure from the app without touching code:

InputWhat the fake partner does
phone number ending in 999a business failure (for example "subscriber not eligible")
amount ending in .13 (for example Tk 20.13)never answers (timeout)
amount ending in .77does the work, then returns HTTP 500
amount ending in .99answers with the unknown code 9876
amount ending in .55sends a broken reply
bill number ending in 404 / 000 / 999bill not found / already paid / refused

There is also a control API (/sim/{partner}/scenario) to force a mode or have callbacks arrive twice, late or out of order. The test console's Simulators page has buttons for all of it.

Where it lives
  • service/MagicAmounts, service/ScenarioStore, one controller per fake partner. Spec section 22.2.
