Chapter 8

Your first day

Hands on: run the whole system on your laptop, send money, follow it through the logs and the ops console, break things on purpose, then change one service and run its tests. Plan about half a day.

2. Build and start the stack

make build              # build every service jar, then every Docker image (first time: 10+ min)
make up TIMERS=fast     # start everything with short timers; waits until all containers are healthy
make seed               # create test users, wallets and balances
make smoke              # quick live checks: is everything up?
make tester             # start the test console: https://localhost/tester
make creds              # print every test login and password

What just happened:

  • make build ran ./gradlew bootJar inside every services/mw-* folder, then built the images.
  • make up first generated passwords for your laptop into deploy/.env (never committed), then started the containers. TIMERS=fast shortens the timeouts and the status-inquiry schedule so failures resolve in seconds, not hours. Later commands remember it.
  • The first start also ran one-shot jobs: kafka-init created the topics, provision created each service's database schema and OpenBao secrets, apisix-init loaded the gateway routes.

Your browser will warn about the certificate: it is self-signed for localhost; accept it.

If something fails

deploy/RUNNING.html has the same steps with a troubleshooting section. The most common laptop problem is Docker Desktop with too little memory.

3. Send money in the test console

The test console (https://localhost/tester) plays every outside party: the apps, a USSD phone, the partners, a shop and the org portal. Open it and:

  1. Go to App flows. Choose transaction type Send money (P2P). The defaults are user customer01, counterparty 01711000002, amount 10, PIN 1234.
  2. If it says the device is not bound, press Re-bind (new device) first: you will see the OTP being requested, read from the fake SMS centre and used. That is device binding (chapter 7).
  3. Press Submit. Expect COMPLETED, the payer down Tk 15.00 (10 + the Tk 5 fee), the payee up Tk 10.00.
  4. Copy the txnId from the result. You need it for the next two steps.
  5. Go to SMS & email, number 01711000001, Read: the "you sent" SMS is there, with the other number masked.

4. Follow it in the logs

Every service logs JSON lines carrying the txnId. From the deploy/ folder:

cd deploy
docker compose logs --no-log-prefix mw-orchestrator | grep 'PASTE-TXN-ID' | jq -c '{ts, event, message}'
docker compose logs --no-log-prefix mw-app-gateway  | grep 'PASTE-TXN-ID' | jq -c '{ts, event, message}'
docker compose logs --no-log-prefix mw-core-mock    | grep 'PASTE-TXN-ID' | jq -c '{ts, event, message}'

Line them up by time and you have figure 4.1 from chapter 4, live. Look for the txn.state.changed events in the orchestrator: RECEIVED, VALIDATING, POSTING, COMPLETED.

5. Find it in the ops console

  1. Open https://localhost/console. Log in as seed-ops-maker with the ops password from make creds.
  2. When asked for a code, run make totp in a terminal and type the 6 digits (a code works once; for a second login, wait for the next one).
  3. Open Transactions, search for your txnId, open it. The timeline shows each state, when it happened and which command was sent to the core. Notice the phone numbers are masked even here.

Failure handling is most of this system, so watch it happen. Back in App flows:

For every row, open the transaction in the ops console and read its timeline. The complete manual test list, with the expected result of every step, is docs/testing-guide.html.

The same checks, automated, are the Newman API suite. Run one folder, then all of them:

make api-test FOLDER=01     # the P2P folder
make api-test               # every folder (needs the fast timers and the seed from step 2)

7. Change a service and test it

A safe first change: read the saga state machine through its test, break it, watch the test catch it, put it back.

  1. Open SagaMachineTest.java. The top of the file is the whole state table of spec section 7.2, one row(from, event, to, effect) per transition. Find: 
    row(Status.POSTING, new DeadlineExpired(), Status.UNKNOWN, Effect.SCHEDULE_INQUIRY);
    That is idea 8 in one line: a posting that times out becomes UNKNOWN and schedules an inquiry.
  2. Run the orchestrator's unit tests (no Docker needed): 
    cd services/mw-orchestrator
./gradlew test --tests 'mfs.mw.orchestrator.service.saga.SagaMachineTest'
  3. Now pretend you "simplify" it: change Status.UNKNOWN to Status.FAILED in that row and run the test again. It fails, because SagaMachine does not do that. Think about why the real rule is right: on a posting timeout the money may already have moved, so failing it would lie to the customer.
  4. Put the line back (git checkout -- src/test) and check the test is green again.

When you change real code in a service, the loop is:

cd services/mw-orchestrator
./gradlew test                         # unit, slice and contract tests: fast, no Docker
./gradlew integrationTest              # the *IT tests with Testcontainers (Docker)
cd ../..
make build M=mw-orchestrator           # rebuild that one jar and image
make up M=mw-orchestrator              # restart it (and what it needs)
make api-test FOLDER=01                # the API folder for your feature
make verify-changed                    # the full gate for every module you touched

Chapter 9 explains the test tiers and what "done" means.

End-of-day checklist

  • I sent money in the test console and found the transaction in the logs and in the ops console.
  • I saw a REJECTED, an UNKNOWN that settled, and a FAILED with a released hold.
  • I ran one API test folder.
  • I ran a module's unit tests, broke one on purpose and fixed it.
  • I can explain, without notes, why a posting timeout goes to UNKNOWN and not to FAILED.
