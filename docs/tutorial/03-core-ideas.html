Chapter 3

Ten ideas to know first

Every flow in chapters 4 to 7 is built from the same ten ideas. Learn them once here and the flows become easy to read. Most of them exist for one reason: money must never be lost, created or moved twice, even when networks fail and services crash.

1. txnId and correlationId

Two ids follow every request through every service, every Kafka message and every log line:

  • txnId: the id of one transaction (one payment). A UUID, created once by the channel service when the request arrives (the app gateway, USSD, checkout, portal). Ask anyone in the team about a payment and they will want its txnId.
  • correlationId: the id of one request chain, sent as the X-Correlation-Id HTTP header (APISIX creates one if the caller did not). It ties together all the log lines caused by one click, across all services.

Kafka messages carry both as headers (mw-txn-id, mw-correlation-id), and every log line has them as JSON fields. So to follow a payment you search the logs for its txnId. You will do that in chapter 8.

2. Idempotency: doing it once

In plain English

"Idempotent" means "doing it twice has the same effect as doing it once". A customer presses Send, the network drops, the app tries again. Without protection, the customer pays twice. With it, the second try is recognised as the same request and gets the first one's answer.

The middleware applies this at every hop:

HopHow a repeat is recognised
App → middlewareThe app sends an Idempotency-Key header. Same key and same body: you get the existing transaction's status. Same key, different body: error MW-IDEM-001. A 60-second lock in Valkey also stops a double tap from racing.
USSD → middlewareA basic phone cannot send a key, so mw-ussd derives one from the session, the menu path, the amount and the target.
Middleware → coreEvery command has a commandId built from the txnId and the step, for example <txnId>:post. The core answers a repeat from its log instead of moving money again.
Middleware → partnerA stable partner reference (for top-up, BITS followed by the txnId in hex), so a partner can spot a repeat too.
Kafka listenerThe inbox: a table of message ids already handled.
Where it lives
  • IdempotencyGate in mw-orchestrator: decides proceed, duplicate or conflict.
  • Spec section 7.3.

3. Kafka topics

Kafka is a log of messages split into named topics. A service publishes to a topic; any number of services can listen to it, each as its own consumer group, and each group sees every message. Messages stay on the topic after they are read, so a service that was down simply catches up.

Topic names follow <domain>.<entity>.<kind>.v<n>. The ones you will meet all the time:

TopicCarriesFrom → to
mw.txn.request.v1"Please do this transaction"channel services → orchestrator
mw.txn.status.v1Every state change of every transactionorchestrator → channel services, notify
core.wallet.command.v1 / core.payment.command.v1Commands to the core (the three hold commands use the payment topic)orchestrator → core
core.wallet.event.v1 / core.payment.event.v1The core's answerscore → orchestrator
mw.partner.request.telco.v1 (also .billpay, .bank)"Call this partner"orchestrator → one adapter
mw.partner.reply.v1 / mw.partner.inbound.v1The partner's answer / a partner's later callbackadapters → orchestrator
mw.notify.request.v1"Send this SMS or email" (OTPs, for example)any → notify
mw.audit.event.v1Something worth recordingany → audit
mw.txn.action.v1An approved operator action (force commit, release, inquire)admin API → orchestrator
mw.config.changed.v1Approved config change (partner settings, templates, menus)admin API → adapters, notify, USSD

Three details that matter: every message's key is the txnId, and Kafka keeps messages with the same key in order, so the steps of one transaction never overtake each other. Every message has a JSON Schema in contracts/. And when a listener fails on a message, it moves it to a retry topic (<topic>.<group>.retry.<n>) and finally a dead-letter topic (.dlq) instead of blocking everything behind it.

4. Outbox and inbox

Here is a classic trap. The orchestrator must do two things when a step completes: save the new state in its database, and publish the next command to Kafka. If it saves and then crashes before publishing, the payment is stuck. If it publishes and then crashes before saving, the core moves money the orchestrator does not know about. Two separate systems cannot be updated "at the same time".

  1. Outbox: instead of publishing directly, the service writes the message as a row in its own outbox table, in the same database transaction as the business change. Either both are saved or neither is.
  2. A small background relay reads unsent outbox rows, publishes them to Kafka and marks them sent. If it crashes after publishing but before marking, it publishes the row again later. So a message can arrive twice, but is never lost.
  3. Inbox: every listener records the id of each message it has handled in an inbox table, in the same transaction as its own work. A message it has already seen is ignored. Together this gives "effectively once" delivery.
Where it lives (copied into every service)
  • messaging/OutboxWriter, messaging/OutboxRelay, route/OutboxRelayRouteBuilder, messaging/Inbox.
  • Every service runs the same @Conformance tests on them (chapter 9). Spec section 6.4.
One exception

A channel service that changes nothing in its own database before publishing (the app gateway sending a transaction request, for example) publishes straight to Kafka. There is no business row to keep in step with. The orchestrator's idempotency check handles a repeat.

6. Sagas and the state machine

In plain English

A saga is a job made of several steps across several systems, where you cannot undo everything with one database rollback. Instead, each step is saved before the next starts, and if a later step fails, the saga runs a compensating step (for example "release the hold") to put things right. The orchestrator keeps one saga per transaction, as a row in its database with the current state.

There are 14 states. A transaction moves between them as events arrive:

The code splits the saga into three parts. This split is worth understanding before you read any flow:

  • A Flow per transaction type describes its steps: does it need a hold, which partner family, which command posts the money. P2pFlow, TopupFlow, BillPayFlow, and so on.
  • The SagaMachine is a pure function: given the current state and an event, it returns the next state and the effects to perform ("send PostTransfer", "start a 5-second timer"). It touches no database and no Kafka, so it is easy to unit test.
  • The SagaEngine carries the effects out in one database transaction: saves the new state, writes the next command, the status update and an audit event to the outbox, and stores the timer.
Where it lives
  • saga/Status, saga/SagaMachine, saga/FlowRegistry and the flows next to it.
  • service/SagaEngine; timers: service/SagaTimerService.
  • Spec sections 7.1 and 7.2.

7. Post versus hold

There are two ways to move money, and every flow uses one of them:

Post (one step)Hold, then commit or release
StepsValidateTransaction → PostTransferValidateTransaction → HoldFunds → (partner works) → CommitHold or ReleaseHold
Used whenBoth sides are wallets inside Bits: P2P, cash in, cash out, merchant pay, bulk.An outside partner must do something before we know whether to charge: top-up, bill pay.
LikePaying cash over the counter.A hotel blocking an amount on your card at check-in, and charging or releasing it at check-out.

Why hold? If we took the money first and the operator then failed to deliver the airtime, we would have to send it back as a refund. Holding means the customer cannot spend the money twice in the meantime, and nothing needs to be refunded if the partner says no.

8. Unknown outcomes and status inquiry

In plain English

You ask the core to move money and the answer never comes. Did the money move? You do not know: maybe the request was lost, maybe only the answer was lost. Guessing either way is a bug that costs real money. So the middleware marks the transaction UNKNOWN and asks again ("what happened to transaction X?") on a schedule until it gets a clear answer. This is the status inquiry, or TSQ (transaction status query).

  • Every waiting state has a timer (for example 5 seconds for a core answer, 30 seconds for a partner). The SagaTimerJob checks timers every second.
  • A timeout before any money could move (validation) just fails the transaction. A timeout after money might have moved (posting, partner) goes to UNKNOWN.
  • For partner steps the same idea applies, but the adapter asks the partner (a STATUS_QUERY).
  • If 24 hours pass, or an answer makes no sense, the transaction goes to MANUAL_REVIEW: a person in the ops console decides (chapter 7).
  • A late answer that contradicts what the saga already decided changes nothing; it is logged and audited as a conflict.
Where it lives
  • service/InquiryService, saga/InquirySchedule. Spec section 7.4.

9. Waiting for an answer

The app makes an HTTP call and wants an answer, but the work happens over Kafka. How does the app gateway turn one into the other?

  1. The gateway registers a waiter in memory, then publishes the request with a header mw-reply-to naming this gateway instance.
  2. The orchestrator copies that header onto every status update it publishes.
  3. Each gateway instance listens to mw.txn.status.v1 in its own consumer group and wakes the waiter for a final status.
  4. If no final status comes within the reply budget (25 seconds for the app), the gateway answers 202 PROCESSING with a link to poll. The transaction is not cancelled; it finishes in the background and the customer gets an SMS.

mw-ussd (8-second budget, then a "processing" screen) and mw-checkout do the same thing.

Where it lives
  • service/ReplyWaiters and route/StatusReplyRoute in mw-app-gateway. Spec section 7.5.

Masking personal data

Logs, audit records and console screens must never show full personal data. Each service's util/MaskingPolicy masks it, and a log filter applies it before anything is written:

DataShown as
Phone number (MSISDN)0171****789

The PIN

The customer's PIN is encrypted on the phone (or, for USSD, the moment mw-ussd receives it) with the core's public key (RSA-OAEP with SHA-256). The middleware only ever carries the ciphertext to the core and cannot decrypt it. It is never logged and never stored. Card numbers never enter the middleware at all.

What can go wrong

Logging a whole request body "just to debug" can leak a phone number or a PIN ciphertext. scripts/log-scan.sh scans every container log for exactly that and fails the security check. Log through SLF4J with fields, and let the masking do its job.
