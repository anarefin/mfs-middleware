Chapter 2

The architecture

The middleware is about a dozen small Spring Boot services that talk to each other mostly through Kafka, sitting behind one gateway. This chapter names every piece and shows how they connect.

The big picture

In plain English

Think of an airport. APISIX is security at the entrance: it checks your ticket (login token), throws out anything too big or too frequent, and sends you to the right gate. The channel services are the check-in desks, one per kind of traveller (app, USSD, web shop, portal, staff). Kafka is the conveyor belt that carries bags between desks without anyone waiting for anyone. The orchestrator is the control tower that decides what happens next for each trip. The adapters are the people who phone other airlines. The core is the bank next door that holds the money.

Two ways services talk

HTTP (synchronous)Kafka (asynchronous)
LikeA phone call: you ask and hold the line until you get the answer.A post box: you drop a letter and carry on; someone picks it up and later posts a reply.
Used forEverything coming in from outside (apps, USSD over HTTP, merchants, portals, partner callbacks), calls out to partners, and a few internal lookups (bill fetch, transaction query, audit search).Everything between services inside: transaction requests, commands to the core, partner requests and replies, status updates, notifications, audit events.
WhyThe outside world expects an answer to its request.If a service is down or slow, messages wait on the topic instead of being lost, and no thread sits blocked.

The interesting part: an app calls over HTTP and expects an answer, but the work inside happens over Kafka. Chapter 3 explains how a service waits for the Kafka answer and turns it back into an HTTP response.

The service map

Notice what the picture says: only mw-orchestrator sends commands to the core. The channel services never talk to the core or to partners themselves. They hand a transaction request to the orchestrator and wait for its status updates. This one rule keeps the money logic in one place.

Network zones and profiles

Everything runs in Docker Compose from one file, deploy/docker-compose.yml. Two ideas in that file are worth knowing on day one.

Zones. The containers sit on separate Docker networks (dmz, app, data, ops, etcd), like the security zones of a real data centre. APISIX is the edge (port 443, so https://localhost/...): every client goes through it, and only there do the edge policies (auth, rate limits, size limits) apply. For debugging, the services and platform containers are also published on 127.0.0.1 only (8081-8093 the services, 3000/3001 the two UIs, 5432 PostgreSQL, 9094 Kafka, 8180 Keycloak, ...; MW_PORT_<NAME> moves one). The database is only on the data network, and etcd only talks to APISIX.

Profiles. A profile decides which containers start. Every command runs from deploy/ after cp dev.env.defaults .env (the committed dev settings; Compose reads deploy/.env by itself):

ProfileStartsCommand
(none)The platform: Kafka, PostgreSQL, Valkey, Keycloak, OpenBao, etcd, APISIX, a test mail server, and one-shot setup jobs.always

No shared code, on purpose

In plain English

Every service is its own little project with its own Gradle build file, its own dependency versions and its own Dockerfile. The root Gradle build only lists the service folders, so one ./gradlew clean build builds them all; it holds no shared build logic. No service may depend on another service's code, and there is no shared library. Code every service needs (error handling, masking, the outbox, correlation ids) is copied from the template into each service. That looks wasteful, but it means a team can change, build and release one service without touching or breaking any other.

The only thing services share is the contracts/ folder: the OpenAPI files for HTTP APIs and the JSON Schemas for every Kafka message. A contract is the agreement between two services, and each file has one owning service (contracts/OWNERS.yml). Chapter 9 covers the rules.

Where it lives
  • The template every service is copied from: templates/mw-service-template/ (scripts/new-service.sh mw-x copies it).
  • The isolation check: scripts/check-isolation.sh (./gradlew :checkIsolation, part of ./gradlew build).
  • Why: docs/adr/ (decisions D13 and D14).

Inside one service

Every service uses the same package layout, so once you know one you can find your way in all of them. The package name is mfs.mw.<service>: mw-adapter-telco becomes mfs.mw.adapter.telco. Each sub-package holds one kind of class:

Here is the orchestrator, trimmed, as an example:

services/mw-orchestrator/src/main/java/mfs/mw/orchestrator/
  OrchestratorApplication.java   // the only class in the root package
  controller/   // internal transaction query API
  route/        // Camel routes: TxnRequestRoute, CoreWalletEventRoute, PartnerReplyRoute, ...
  messaging/    // listeners, OutboxWriter, OutboxRelay, Inbox
  service/      // TransactionService, SagaEngine, InquiryService, IdempotencyGate
    saga/       // SagaMachine, Status, one Flow per transaction type (P2pFlow, TopupFlow, ...)
  scheduler/    // SagaTimerJob: fires timeouts every second
  repository/   entity/   dto/   mapper/   exception/   util/   filter/   logging/   config/

The adapters have one extra package, partner/, the adapter framework; chapter 5 explains it.
