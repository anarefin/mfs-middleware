Chapter 9

How we work

The rules for changing this codebase. They are strict because the code moves money, and most of them are checked by scripts, so breaking one fails the build rather than a review.

Contracts first

Two services agree through a contract, not through shared code:

  • contracts/api/<owner>/: OpenAPI files for HTTP APIs.
  • contracts/events/<owner>/: a JSON Schema for every Kafka message, with sample messages.
  • contracts/OWNERS.yml: which service owns each file. Only the owner may change it. If you need a change in someone else's contract, ask the owning team.
  • Each service lists what it produces and consumes in its own contracts.yml, for example services/mw-orchestrator/contracts.yml. Its contract tests (ProducedContractsTest, ConsumedContractsTest) check real messages against those schemas, so keep the file in step with the code in the same commit.

./gradlew :contractsLint checks all of it, including that every event has both a producer and a consumer.

Module rules

  • A service never depends on another service's code, the template or the root build (the root settings.gradle.kts only lists the service folders; there are no allprojects, no buildSrc, no convention plugins). Each service writes its own dependency versions in its build.gradle.kts; Gradle plugin versions must be the same in every module.
  • A service never and never references a path outside its own folder (except contracts/, read by tests). ./gradlew :checkIsolation enforces this, as part of every ./gradlew build.
  • Copied code (masking, errors, correlation, outbox, inbox) is meant to be copied. Do not "fix" it by creating a shared library.
  • A service reads and writes only its own database schema.
  • Package layout and dependency direction as in chapter 2: controllers only map and validate, business logic is in service/, entities never leave the service layer.
  • Constructor injection only; never @Autowired on a field, in tests too (scripts/check-field-injection.sh).

Tests

Every service has one Gradle test task, run from the repo root: ./gradlew :mw-orchestrator:test. It runs everything in one JVM:

  • unit tests (service, mapper, util), @WebMvcTest controller slices and the contract tests;
  • the *IT classes: a real PostgreSQL and Kafka in Testcontainers, for example the repository tests;
  • the @Conformance suite: the same tests in every service proving its outbox, inbox and HTTP basics behave.

The test JVM starts one PostgreSQL and one Kafka container and gives each Spring test context a fresh database. Testcontainers removes the containers when the JVM exits. Without Docker the *IT and conformance tests are skipped, not failed. There is no coverage gate.

Above the modules, against the running stack: scripts/api-test.sh (Newman, black-box API scenarios in tests/api/), scripts/ui-e2e.sh and scripts/tester-e2e.sh (Playwright for the two web apps), scripts/edge-test.sh (gateway rules). Tests are written first: a failing test, then the code that makes it pass.

The build is the pipeline

There is no CI server and no Makefile in the MVP. The root Gradle build is the pipeline: one Gradle daemon builds every module, with the build cache, so unchanged modules are restored instead of rebuilt.

Command (from the repo root)Use it when
./gradlew clean buildBefore you open a pull request: every module's tests and jar, plus the repo checks (:checkIsolation, :checkFieldInjection, :contractsLint, :composeCheck, :scriptTests).
./gradlew :mw-orchestrator:buildOne module: its tests and its jar.
./gradlew :scriptTestsYou changed a script or a doc that names commands or paths.
./gradlew :contractsLintYou changed a contract or a contracts.yml.
scripts/security.sh, scripts/log-scan.shSecret scan, dependency and image scan, and the "no PIN or unmasked number in any log" check.

The README lists every script.

Definition of done

  • Tests written first; ./gradlew clean build green (it covers every module you touched and the repo checks).
  • The relevant scripts/api-test.sh "<your folders>" green on a stack started with the dev settings (deploy/.env, with its test timers) and the seed profile.
  • The service's CLAUDE.md and contracts.yml updated if what it owns or uses changed.
  • A new script, knob or decision is also added to the docs (README, runbook, ADR) in the same change: scripts/test/test_repo_docs.sh fails otherwise.
  • The command output pasted into the pull request template.

Never do this

Never
  • Put a secret in code, a config file or a test. Use OpenBao; test fixtures use obviously fake values.
  • Use System.out, System.err or printStackTrace. Log through SLF4J.
  • Log a PIN, or an unmasked phone number, national ID, account number or name.
  • Block a Kafka listener thread: no waiting for replies, no sleeps, no long partner calls on it.
  • Use field injection.
  • Depend on, include or reference another module, the template or the root build.
  • Change a contract your service does not own.
  • Read or write another service's database schema.
  • Retry a money call to a partner or the core "just in case". Ask (status inquiry) instead.

Adding a new service

scripts/new-service.sh mw-x            # copies templates/mw-service-template and prints the compose block to add
./gradlew :mw-x:build                  # the root build picks the new folder up by itself

Then add the printed block to deploy/docker-compose.yml, give the service a CLAUDE.md (responsibilities, contracts owned and used), its contracts and its contracts.yml. Read the template's CLAUDE.md first.
