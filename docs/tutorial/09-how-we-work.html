Chapter 9

How we work

The rules for changing this codebase. They are strict because the code moves money, and most of them are checked by scripts, so breaking one fails the build rather than a review.

Contracts first

Two services agree through a contract, not through shared code:

  • contracts/api/<owner>/: OpenAPI files for HTTP APIs.
  • contracts/events/<owner>/: a JSON Schema for every Kafka message, with sample messages.
  • contracts/OWNERS.yml: which service owns each file. Only the owner may change it. If you need a change in someone else's contract, ask the owning team.
  • Each service lists what it produces and consumes in its own contracts.yml, for example services/mw-orchestrator/contracts.yml. Its contract tests (ProducedContractsTest, ConsumedContractsTest) check real messages against those schemas, so keep the file in step with the code in the same commit.

make contracts-lint checks all of it, including that every event has both a producer and a consumer.

Module rules

  • A service never depends on another service's code, the template or the root build, and never references a path outside its own folder (except contracts/, read by tests). make check-isolation enforces this.
  • Copied code (masking, errors, correlation, outbox, inbox) is meant to be copied. Do not "fix" it by creating a shared library.
  • A service reads and writes only its own database schema.
  • Package layout and dependency direction as in chapter 2: controllers only map and validate, business logic is in service/, entities never leave the service layer.
  • Constructor injection only; never @Autowired on a field, in tests too (scripts/check-field-injection.sh).

The test tiers

Every service has the same three Gradle test tasks:

Command (inside services/mw-<name>)RunsNeeds Docker
./gradlew testUnit tests (service, mapper, util), @WebMvcTest controller slices, contract tests. No class ending in IT.no
./gradlew integrationTestThe *IT classes: a real PostgreSQL and Kafka in Testcontainers, for example the repository tests.yes
./gradlew conformanceThe @Conformance suite: the same tests in every service proving its outbox, inbox and HTTP basics behave.yes
./gradlew checkAll three, plus a JaCoCo gate: 80% line coverage on service, mapper and client.yes

Above the modules, against the running stack: make api-test (Newman, black-box API scenarios in tests/api/), make ui-e2e and make tester-e2e (Playwright for the two web apps), make edge-test (gateway rules). Tests are written first: a failing test, then the code that makes it pass.

The Makefile is the pipeline

There is no CI server in the MVP. The Makefile is the pipeline, and every target works for all modules or one with M=:

CommandUse it when
make verify-changedBefore you open a pull request: the full gate for the modules you changed since main.
make verify M=mw-orchestratorThe full gate for one module: isolation, field-injection, contracts lint, ./gradlew check.
make test-scriptsYou changed the Makefile, a script or a doc that names commands or paths.
make contracts-lintYou changed a contract or a contracts.yml.
make security, make log-scanSecret scan, dependency and image scan, and the "no PIN or unmasked number in any log" check.

The README lists every target.

Definition of done

  • Tests written first; ./gradlew test integrationTest green for every module you touched.
  • make test-scripts / make contracts-lint green if you changed scripts or contracts.
  • The relevant make api-test FOLDER=<your folders> green on make up TIMERS=fast and make seed.
  • The service's CLAUDE.md and contracts.yml updated if what it owns or uses changed.
  • A new Makefile target, knob or decision is also added to the docs (README, runbook, ADR) in the same change: scripts/test/test_repo_docs.sh fails otherwise.
  • The command output pasted into the pull request template.

Never do this

Never
  • Put a secret in code, a config file or a test. Use OpenBao; test fixtures use obviously fake values.
  • Use System.out, System.err or printStackTrace. Log through SLF4J.
  • Log a PIN, or an unmasked phone number, national ID, account number or name.
  • Block a Kafka listener thread: no waiting for replies, no sleeps, no long partner calls on it.
  • Use field injection.
  • Depend on, include or reference another module, the template or the root build.
  • Change a contract your service does not own.
  • Read or write another service's database schema.
  • Retry a money call to a partner or the core "just in case". Ask (status inquiry) instead.

Adding a new service

make new-service NAME=mw-example      # copies templates/mw-service-template and prints the compose block to add

Then add the printed block to deploy/docker-compose.yml, give the service a CLAUDE.md (responsibilities, contracts owned and used), its contracts and its contracts.yml. Read the template's CLAUDE.md first.
