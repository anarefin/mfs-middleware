Money flows: send money, cash in, cash out

Send money (P2P) from the app

In plain English

Customer A (01711000001) sends Tk 10 to customer B (01711000002). The app asks the app gateway; the gateway hands the job to the orchestrator; the orchestrator asks the core "is this allowed?" and then "move it"; the core says "done"; the orchestrator announces "COMPLETED"; the gateway tells the app, and the notify service texts both people.

Step by step

  1. The app calls APISIX. The request carries a Keycloak login token (realm customers), an Idempotency-Key, and a signature made with a key stored on the phone when the device was bound. APISIX checks the token and size limits and forwards to the app gateway.
  2. The app gateway checks the request. Is this user allowed this transaction type (a customer may P2P; only an agent may cash in)? Is the device bound and the signature right? Is the customer not paying themself? Then it creates the txnId and registers a waiter (chapter 3, idea 9).
  3. It publishes the request on mw.txn.request.v1. No database write is needed here, so it publishes directly.
  4. The orchestrator receives it, checks idempotency (a repeat gets the existing transaction), picks the flow for P2P, creates the saga row in state RECEIVED and moves it to VALIDATING. In the same database transaction it writes the ValidateTransaction command to its outbox, plus a status update and an audit event, and starts a 5-second timer.
  5. The core validates: PIN (decrypted only inside the core), wallet states, limits, fee. It answers TransactionValidated on core.wallet.event.v1.
  6. The orchestrator moves to POSTING and sends PostTransfer (commandId <txnId>:post).
  7. The core writes the ledger (debit A Tk 10 + Tk 5 fee, credit B Tk 10, credit the fee pool Tk 5) and answers TransferPosted.
  8. The orchestrator moves to COMPLETED and publishes the status, with the gateway's mw-reply-to header copied across.
  9. The gateway's waiter wakes up and the app gets 200 with the status. The gateway also stores the result, so GET /app/v1/transactions/{txnId} works later.
  10. mw-notify sees the same status event, finds its rules for a completed P2P (one SMS to the sender, one to the receiver), stores two messages and sends them to the SMS centre over SMPP. Numbers in the text are masked.
Where it lives
  • mw-app-gateway: controller/TransactionController → service/TransactionService; device checks in security/DeviceBindingInterceptor.
  • mw-orchestrator: route/TxnRequestRoute → messaging/TxnRequestListener → service/TransactionService → saga/P2pFlow / SagaMachine / SagaEngine. Core answers come in through route/CoreWalletEventRoute → service/CoreEventService.
  • mw-core-mock: service/CoreCommandService; fees and wallet-type rules in its application.yml.
  • mw-notify: route/TxnStatusRoute → service/TxnStatusService → service/RuleEngine; sending in service/DispatchService.
  • API contract: contracts/api/ (the app API is owned by mw-app-gateway). Spec sections 7 and 9.1.

Send money from a USSD phone

In plain English

A basic phone has no app. The customer dials *268# and gets text menus: "1 Send money, 2 Cash out...". Each screen is one short request from the phone operator's USSD gateway to mw-ussd and one reply. Once the customer has entered the number, the amount and the PIN, mw-ussd starts exactly the same transaction as the app does.

  • Two transports, one engine. Some operators connect over SMPP (a long-lived telecom connection; in dev, Grameenphone), others over HTTP through APISIX (in dev, Robi, Banglalink, Teletalk). The transport/ package turns both into the same call to the menu engine.
  • Menus are data, not code: a JSON file, stored in versions in the database and editable in the ops console (with maker-checker). A menu node of type ACTION starts a transaction.
  • The session lives in Valkey, so any mw-ussd instance can serve the next screen.
  • USSD supports P2P, cash out, top-up and bill pay. There is no cash in over USSD.
Where it lives
  • service/UssdEngine (one step per request), service/KafkaTransactionFlow (starts the transaction).
  • Transports: transport/HttpUssdTransport, transport/SmppUssdTransport; the menus: menus/main-v2.json. Spec section 9.2.

Cash in and cash out

These are the same two-step flow as P2P (validate, then post, no hold). Only the parties, the fee and the rules differ:

P2PCash inCash out
Who starts ita customeran agent (agent app only)a customer (app or USSD)
Money movescustomer → customeragent → customercustomer → agent
Real worldthe customer hands the agent cashthe agent hands the customer cash
Fee in the core mockTk 5noneTk 10
Wrong counterpartyMW-CORE-INVALID_COUNTERPARTY (for example cash in to a merchant)

The orchestrator flows are CashInFlow and CashOutFlow. Compare them with P2pFlow: they are almost the same.

Reversal

A completed transaction is undone by a new transaction of type REVERSAL. Customers cannot start one: it comes from the system channel, in practice from an operator's approved change request in the ops console (chapter 7). The orchestrator moves the original from COMPLETED to REVERSING, sends ReverseTransaction, and on TransactionReversed marks it REVERSED. If the core refuses, or does not answer even after a query, it goes to MANUAL_REVIEW.
